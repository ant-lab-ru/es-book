## Ход работы

>[!info] Зачем разбирать работающую программу
>Пятьдесят строк в одном файле читаются легко, и вынос модуля именно сейчас ничего не улучшает. Но в модуле 3 в суперцикле будет около десятка дел, каждое со своим состоянием. Управлять таким исходным кодом в одном файле невозможно. Освоим этот приём на программе, которая целиком помещается на экран.
>
>Заодно вы впервые соберёте проект из нескольких исходных файлов. До сих пор `add_executable()` знал только `main.c`.

### 1. Создать проект по образцу

Создайте папку `134-led-module`, скопируйте в неё четыре файла проекта `133-led-button-usb` (папку `build` не копируйте) и впишите новое имя `134_led_module` в `project()`.

Внутри проекта создайте папку `led`:

``` bash
cd ~/Repositories/pico/es-student/134-led-module
mkdir led
```

Модуль — будет представлять собой пару файлов, которые будут лежать в папке `led`. Создайте в ней `led.h` — объявления функций модуля, и `led.c` — их реализацию. Мы заполним файлы в следующих двух шагах.

### 2. Написать заголовочный файл модуля

Заголовочный файл — это «договор». Компилятору он сообщает, что такие функции существуют, а программе обещает, что они будут написаны. Сдержано ли обещание, выяснится только при сборке, когда линкер попытается связать вызовы с реализацией.

``` c
#ifndef LED_H
#define LED_H

#include "pico/stdlib.h"

void led_init(void);
void led_set(bool on);
void led_toggle(void);
bool led_is_on(void);

#endif
```

Четыре функции покрывают всё, что программе нужно от светодиода: подготовить вывод, задать состояние, переключить, спросить текущее состояние.

Первые две строки и последняя — защита от повторного включения. Если один и тот же заголовок попадёт в файл дважды (а это обычное дело, когда модулей много), объявления повторятся и компилятор сообщит об ошибке. Проверка `#ifndef` пропускает содержимое только в первый раз: имя `LED_H` ещё не определено — определяем его и читаем файл; во второй раз имя уже есть, и всё до `#endif` пропускается. Работает это [[Препроцессор#^def|препроцессором]] — тем же, что подставляет `#include`.

Того же добивается одна строка `#pragma once` в начале файла. В стандарт языка она не входит, но её понимают все компиляторы, которые встречаются на практике, — в том числе тот, которым вы собираете прошивку.

``` c
#pragma once

#include "pico/stdlib.h"

void led_init(void);
void led_set(bool on);
void led_toggle(void);
bool led_is_on(void);
```

Мы в своей практике используем `#pragma once`. В этом вариант одна строка одна, и нет имени, в котором можно ошибиться.

У варианта с `#ifndef` имя должно быть уникальным на всю программу. Если скопировать заголовок в соседний модуль, забыв его сменить, файл молча не попадёт в сборку. И ошибка найдётся не там, где сделана и потребует усилий для поиска. Чтобы этого избежать, рекомендуем для ваших заголовочных файлов использовать `#pragma once`. Дальнейшие примеры будут в одном варианте, только этой директивой.

Автоматическая проверка примет любой из двух вариантов [[Защита от повторного включения#^def|защиты от повторного включения]].

### 3. Перенести работу со светодиодом в led.c

Перенесите в `led.c` весь код, который относится к светодиоду. Номер вывода, его настройку и текущее состояние.

``` c
#include "led.h"
#include "hardware/gpio.h"

const uint LED_PIN = 25;

static bool led_state = false;
```

Слово `static` перед переменной означает, что она видна только внутри этого файла. Состояние светодиода — дело модуля, и лезть в него снаружи никто не должен; спросить можно функцией `led_is_on()`.

Дальше — четыре функции. `led_init()` настраивает вывод на выход и гасит светодиод, `led_set()` выставляет уровень и запоминает состояние, `led_toggle()` вызывает `led_set()` с обратным значением, `led_is_on()` возвращает запомненное.

>[!success] Должно получиться так
> ```c
> #include "led.h"
> #include "hardware/gpio.h"
>
> const uint LED_PIN = 25;
>
> static bool led_state = false;
>
> void led_init(void)
> {
>     // инициализируем пин светодиода и настраиваем его на выход
>     led_set(false);
> }
>
> void led_set(bool on)
> {
>     led_state = on;
>     gpio_put(LED_PIN, led_state);
> }
>
> void led_toggle(void)
> {
>     led_set(!led_state);
> }
>
> bool led_is_on(void)
> {
>     return led_state;
> }
> ```

Обратите внимание: `led_toggle()` не трогает вывод сам, а вызывает `led_set()`. Работа с железом остаётся в одном месте — и если завтра светодиод переедет на другой вывод или начнёт зажигаться нулём, поправить придётся одну функцию.

### 4. Убрать код светодиода из main.c

Подключите заголовок модуля:

``` c
#include "led.h"
```

Дальше замените обращения к светодиоду вызовами модуля:

| Было в `main.c` | Стало |
| --- | --- |
| `gpio_init(LED_PIN)` и `gpio_set_dir(LED_PIN, GPIO_OUT)` | `led_init()` |
| `led = !led; set_led(led);` по кнопке | `led_toggle()` |
| `led = true; set_led(led);` по команде `e` | `led_set(true)` |
| `led = false; set_led(led);` по команде `d` | `led_set(false)` |
| `bool handle_command(int command, bool led)` | `void handle_command(int command)` |

Обратите внимание на последнюю строку: у `handle_command()` пропали и параметр состояния, и возвращаемое значение. Передавать состояние стало незачем — его хранит модуль, и функция спрашивает его сама. Так вынос модуля упрощает не только `main()`, но и всё, что работает со светодиодом.

Переменная `led` и функция `set_led()` из `main.c` уходят: состояние теперь хранит модуль, а сообщение о нём печатается строкой `printf("led %s\n", led_is_on() ? "on" : "off");` после каждого изменения. Константа `LED_PIN` в `main.c` тоже больше не нужна — номер вывода знает только `led.c`.

>[!success] Должно получиться так
> ```c
> // заголовочные файлы: добавился led.h, константы LED_PIN больше нет
>
> bool get_button_debounce(uint pin)
> {
>     // читаем вывод устойчиво к дребезгу
> }
>
> void handle_command(int command)
> {
>     if (command == 'e')
>     {
>         led_set(true);
>         printf("led %s\n", led_is_on() ? "on" : "off");
>     }
>     else if (command == 'd')
>     {
>         led_set(false);
>         printf("led %s\n", led_is_on() ? "on" : "off");
>     }
>     else
>     {
>         printf("unknown command: %c\n", command);
>     }
> }
>
> int main()
> {
>     // включаем стандартный ввод-вывод
>
>     led_init();
>
>     // инициализируем и настраиваем вывод кнопки
>
>     // объявляем переменные
>
>     while (1)
>     {
>         // читаем состояние пина кнопки с задержкой
>
>         if (previous == true && current == false)
>         {
>             led_toggle();
>             printf("led %s\n", led_is_on() ? "on" : "off");
>         }
>
>         // запоминаем текущее состояние пина кнопки, как предыдущее
>
>         int command = getchar_timeout_us(0);
>
>         if (command == PICO_ERROR_TIMEOUT)
>         {
>             continue;
>         }
>

>     }

Печать состояния встречается трижды — по кнопке и по каждой из двух команд. Раньше её прятала `set_led()`, теперь строка стоит рядом с каждым изменением: модуль отвечает за светодиод, а за разговор с компьютером — `main.c`.

### 5. Добавить модуль в сборку

Файл, которого нет в описании сборки, не компилируется — про вызовы его функций компоновщик скажет `undefined reference`. Добавьте `led.c` в список исходных файлов:

``` cmake
add_executable(${PROJECT_NAME}
    ${CMAKE_CURRENT_SOURCE_DIR}/main.c
    ${CMAKE_CURRENT_SOURCE_DIR}/led/led.c
)
```

И укажите компилятору, где искать заголовочные файлы модуля, — иначе `#include "led.h"` придётся писать с путём:

``` cmake
target_include_directories(${PROJECT_NAME} PRIVATE
    ${CMAKE_CURRENT_SOURCE_DIR}/led
)
```

Слово `PRIVATE` означает, что путь нужен только при сборке этой цели и никуда дальше не передаётся.

>[!bug] undefined reference to 'led_init'
>Компилятор нашёл объявление в `led.h` и не возражал, а компоновщик не нашёл самой функции: `led.c` не попал в `add_executable()`. Ошибка компоновки — почти всегда про сборку, а не про код. Как устроены эти два этапа, разобрано в [[т1.3.3 От исходного кода к прошивке#^intro|теории занятия]].
