### Как проверить

1. **Плата управляется аналоговым и цифровым образом.** В терминале нажмите `e` — светодиод загорится, `d` — погаснет, `q` — приходит сообщение о неизвестной команде. Нажмите кнопку — светодиод переключился, и об этом тоже пришла строка.
2. **Лог остался на диске.** В `device-1-3-4.log` видно обе стороны разговора: строки со стрелкой `-->` отправлены плате, со стрелкой `<--` приняты от неё.

## Ход работы

>[!info] Что меняется с приёмом команд
>Пока прибор только рассказывал о себе, он оставался закрытым: повлиять на работающую прошивку было нечем, кроме перепрошивки. С приёмом команд появляется вторая половина канала — и вместе с ней первый в курсе прибор, который слушается снаружи. Отсюда же вырастет командный протокол занятия 2.3: там команд станет много и они будут со словами и аргументами, а устройство обмена останется тем же.

### 1. Прочитать символ, не останавливая суперцикл

На компьютере ввод ждут: программа стоит, пока пользователь думает. В микроконтроллере остановка означает остановку всего — кнопка не опрашивается, светодиод не обновляется, прибор перестаёт быть прибором. Поэтому символ читают функцией, которая не ждёт:

``` c
        int command = getchar_timeout_us(0);
```

Ноль в аргументе функции означает не ждать вовсе. Если символ пришёл, функция возвращает его код, если нет — значение `PICO_ERROR_TIMEOUT`. Поэтому возвращаемое значение `int`, а не `char`: кодов символов не хватило бы, чтобы сказать «символа не было».

За проход читается ровно один символ. Если вы наберёте в терминале `ede`, они разберутся за три итерации суперцикла — быстрее, чем это можно заметить.

### 2. Разобрать команду в отдельной функции

Для исполнения команды нужно сопоставить прочитанный символ с действием. Разбор не стоит писать прямо в суперцикле. Со временем команд станет больше, и действие цикле, которое должно читаться как «прими команду», заполоняют ветки. Чтобы этого избежать создайте функцию:

``` c
bool handle_command(int command, bool led)
{
    if (command == 'e')
    {
        led = true;
        set_led(led);
    }
    else if (command == 'd')
    {
        led = false;
        set_led(led);
    }
    else
    {
        printf("unknown command: %c\n", command);
    }

    return led;
}
```

Функция получает пришедший символ и текущее состояние светодиода, а возвращает новое. Если команда была — изменённое, если нет — то же самое. Состояние по-прежнему хранится в `main()`, и никаких скрытых связей между функциями не появляется.

В суперцикле сначала отсекается случай «символа не было», и только потом идёт разбор:

``` c
        int command = getchar_timeout_us(0);

        if (command == PICO_ERROR_TIMEOUT)
        {
            continue;
        }

        led = handle_command(command, led);
```

Одиночные кавычки в C означают код символа: `'e'` — это число 101, код буквы `e` в таблице [[ASCII#^def|ASCII]]. Сравнивается именно число, пришедшее из порта, с числом, записанным в программе.

`continue` заканчивает итерацию суперцикла и начинает следующую. Читается это так: символа нет — делать нечего, идём на новый круг. Приём называется [[Ранний выход#^def\|ранним выходом]], и он избавляет от лишней вложенности. Разбор команды остаётся на том же уровне, что и остальные дела цикла, а не уезжает внутрь `if`.

Проверка стоит в цикле, а не внутри `handle_command()`, и это не случайно. `PICO_ERROR_TIMEOUT` — свойство способа чтения, а не команды. Функция разбора знает только свой алфавит: `e`, `d` и всё остальное. Поэтому последняя ветка отвечает на всё прочее без оговорок — до неё доходят только настоящие символы.

>[!warning] Чтение команды — последнее дело в суперцикле
>`continue` пропускает весь остаток итерации. Пока за разбором команды ничего нет, это безопасно, но дело, дописанное ниже, будет молча пропускаться в каждом проходе без символа — а символа нет почти всегда. Новые функции добавляйте выше чтения команды.

>[!info] Почему прибор отвечает на неизвестную команду
>Промолчать проще, но молчание неотличимо от поломки: отправитель не знает, потерялась команда, не понята или прибор завис. Ответ на всякий ввод — правило хорошего протокола, и в занятии 2.3 оно станет частью формального разбора команд.

### 3. Свести два источника управления в одном шаге

Теперь состояние светодиода меняют два события: кнопка и приход символа. Оба обрабатываются в одном шаге суперцикла не блокируя друг друга. Сначала опрос кнопки, потом чтение символа.

Порядок здесь не безразличен. Если нажатие и команда придутся на один шаг, последним отработает разбор команды — и светодиод останется в том состоянии, которое задала она. Этот случай решён явно: **при одновременном действии приоритет имеет команда из порта**. Причина простая: кнопку жмёт человек, стоящий у прибора, и он видит результат сразу, а отправитель команды находится на другом конце провода и о нажатии не знает.

>[!success] Должно получиться так
> ```c
> // заголовочные файлы и константы — без изменений
>
> bool get_button_debounce(uint pin)
> {
>     // читаем вывод устойчиво к дребезгу
> }
>
> void set_led(bool on)
> {
>     // выставляем уровень на выводе и сообщаем о состоянии в порт
> }
>
> bool handle_command(int command, bool led)
> {
>     // разбираем команду и возвращаем новое состояние светодиода
> }
>
> int main()
> {
>     // включаем стандартный ввод-вывод
>     // инициализируем и настраиваем выводы
>
>     // объявляем переменные
>
>     while (1)
>     {
>         // читаем состояние пина кнопки с задержкой
>
>         // если состояние сменилось — переключаем светодиод
>
>         // запоминаем текущее состояние пина кнопки, как предыдущее
>
>         int command = getchar_timeout_us(0);
>
>         if (command == PICO_ERROR_TIMEOUT)
>         {
>             continue;
>         }
>
>         led = handle_command(command, led);
>     }
> }
> ```

>[!bug] Плата не отвечает на символы
>Если вывод работает, а на ввод реакции нет, проверьте `CMakeLists.txt`: канал включается целиком, обеими строками `pico_enable_stdio_*`. Вторая причина — терминал, который отправляет строку только по `Enter`; в PuTTY символы уходят сразу, в других программах это бывает настройкой.

### 5. Создать скрипт проверки

Создайте в папке `133-led-button-usb` файл `check-1-3-4.py` — рядом с `main.c`.

Скрипт этого задания говорит с платой сам. Посылает команду, читает ответ и записывает сообщения в обе стороны. Последовательность задана списком — в нём есть повтор `e`, `d` и неизвестная команда:

``` python
COMMANDS = ["e", "d", "e", "e", "d", "x"]
```

>[!success] Должно получиться так
> ```python
> # Проверка задания п1.3.4 на устройстве: посылает плате команды,
> # читает ответы и записывает обмен в файл device-1-3-4.log.
>
> import time
> from datetime import datetime
>
> import serial
> from serial.tools import list_ports
>
> VENDOR_ID = 0x2E8A
> PRODUCT_ID = 0x000A
>
> TASK = "1.3.4"
> PROJECT = "133-led-button-usb"
> LOG_NAME = "device-1-3-4.log"
> COMMANDS = ["e", "d", "e", "e", "d", "x"]
> ANSWER_TIMEOUT_S = 1
>
>
> def find_board():
>     for port in list_ports.comports():
>         if port.vid == VENDOR_ID and port.pid == PRODUCT_ID:
>             return port
>     return None
>
>
> def talk(board):
>     exchange = []
>     with serial.Serial(board.device, timeout=ANSWER_TIMEOUT_S) as port:
>         time.sleep(0.2)
>         port.reset_input_buffer()
>         started = time.monotonic()
>         for command in COMMANDS:
>             port.write(command.encode("ascii"))
>             exchange.append((time.monotonic() - started, "-->", command))
>             answer = port.readline().decode("ascii", "replace").strip()
>             exchange.append((time.monotonic() - started, "<--", answer))
>             print("%s → %s" % (command, answer), end="\r\n")
>             time.sleep(0.5)
>     return exchange
>
>
> def write_log(board, exchange):
>     with open(LOG_NAME, "w", encoding="utf-8") as log:
>         log.write("задание: " + TASK + "\n")
>         log.write("проект: " + PROJECT + "\n")
>         log.write("устройство: %04x:%04x\n" % (board.vid, board.pid))
>         log.write("серийный номер: " + str(board.serial_number) + "\n")
>         log.write("порт: " + board.device + "\n")
>         log.write("начало: " + datetime.now().isoformat(timespec="seconds") + "\n")
>         for moment, direction, text in exchange:
>             log.write("%8.3f %s %s\n" % (moment, direction, text))
>         log.write("итог: отправлено команд %d\n" % len(COMMANDS))
>
>
> board = find_board()
>
> if board is None:
>     print("Плата не найдена. Проверьте кабель и запишите на плату прошивку задания.", end="\r\n")
> else:
>     print("Плата на порту " + board.device + ", посылаю команды", end="\r\n")
>     exchange = talk(board)
>     write_log(board, exchange)
>     print("Обмен записан в " + LOG_NAME, end="\r\n")
> ```

### 7. Проверить приоритет своими руками

Запустите скрипт ещё раз и, пока он работает, нажимайте кнопку. Светодиод будет переключаться и от неё, и от команд, ни одна не потеряется — а если нажатие совпадёт с командой, победит команда.

Два источника управления в одном приборе — обычное дело. Каждый раз стоит явно и однозначно решить, какой канал управления более приоритетный: аналоговые кнопки или цифровые команды.
