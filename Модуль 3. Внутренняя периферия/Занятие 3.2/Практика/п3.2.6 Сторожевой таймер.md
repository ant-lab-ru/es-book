**Результат** — рекордер `321-audio-recorder` сам выходит из зависания. Сторожевой таймер обновляется в суперцикле после всех задач, и, если суперцикл встал, через заданный таймаут плата перезапускается. После перезапуска прибор сообщает, что причиной был сторожевой таймер и сколько раз подряд он срабатывал.
^intro

## Задание

### Что должно получиться

- [ ] `platform` включает и обновляет сторожевой таймер, а при запуске узнаёт причину прошлого сброса
- [ ] Счётчик перезапусков подряд хранится в scratch-регистре и переживает сброс по сторожевому таймеру
- [ ] Суперцикл обновляет сторожевой таймер после всех задач, обработчики прерываний его не трогают
- [ ] Команды `wdt_enable <timeout_ms>`, `hang` и `reset_reason` работают
- [ ] Лог `device-3-2-6.log` снят, коммит отправлен, проверка `3.2.6` зелёная

### Как проверить

1. **Плата перезапускается сама.** После `wdt_enable 2000` и `hang` светодиод индикатора ещё мигает, а через 2 с плата перезапускается, и порт на компьютере пропадает и появляется снова.
2. **Лог прогона лежит в проекте.** Скрипт задания записывает обмен в `device-3-2-6.log`, переподключаясь к плате после перезапуска.
3. **Автоматическая проверка курса принимает задание.** В коде она ищет `watchdog_enable()`, `watchdog_enable_caused_reboot()`, scratch-регистр и обновление в суперцикле `main.c`, а в обработчиках прерываний обновления быть не должно. В логе прибор должен прожить дольше таймаута, после `hang` перезапуститься, а `reset_reason` должен назвать сторожевой таймер.

## Ход работы

Это задание выполняет требование Р6 [[ТЗ 3.2 Рекордер|ТЗ на рекордер]]. Где обновлять сторожевой таймер, как выбрать таймаут и как узнать причину сброса, разобрано в [[т3.2.9 Сторожевой таймер#^intro|т3.2.9]].

### 1. Включить сторожевой таймер в platform

Добавьте в `platform.h` три функции.

```c
// сторожевой таймер; false — таймаут больше 8388 мс или равен нулю
bool platform_watchdog_enable(uint32_t timeout_ms);
void platform_watchdog_feed(void);

// был ли последний сброс по сторожевому таймеру и сколько таких сбросов подряд
bool platform_watchdog_caused_reset(uint32_t *restarts);
```

Подключите в `platform.c` заголовок `hardware/watchdog.h`. Причину сброса нужно узнать в самом начале `platform_init()`, до того как прошивка что-нибудь изменит. Функция `watchdog_enable_caused_reboot()` отличает настоящее срабатывание от перезапуска после прошивки через picotool, который тоже идёт через сторожевой таймер. Scratch-регистр 0 сброс по сторожевому таймеру не стирает, и в нём живёт счётчик перезапусков подряд. После любого другого сброса счётчик начинается с нуля.

```c
// наибольший таймаут сторожевого таймера RP2040 (RP2040-E1)
#define WATCHDOG_MAX_MS 8388

static bool watchdog_reset;
static uint32_t watchdog_restarts;

void platform_init(void)
{
    // причина прошлого сброса; счётчик сбросов подряд хранит scratch-регистр 0,
    // его не стирает сброс по сторожевому таймеру
    watchdog_reset = watchdog_enable_caused_reboot();
    if (watchdog_reset)
    {
        watchdog_hw->scratch[0]++;
    }
    else
    {
        watchdog_hw->scratch[0] = 0;
    }
    watchdog_restarts = watchdog_hw->scratch[0];

    stdio_init_all();
    ...
}

bool platform_watchdog_enable(uint32_t timeout_ms)
{
    if (timeout_ms == 0 || timeout_ms > WATCHDOG_MAX_MS)
    {
        return false;
    }

    // true — не считать, пока ядро остановлено отладчиком
    watchdog_enable(timeout_ms, true);
    return true;
}

void platform_watchdog_feed(void)
{
    watchdog_update();
}

bool platform_watchdog_caused_reset(uint32_t *restarts)
{
    *restarts = watchdog_restarts;
    return watchdog_reset;
}
```

Предел 8388 мс задаёт ошибка кристалла RP2040-E1. Счётчик сторожевого таймера убывает на два за тик, и SDK удваивает заданное значение ([[RP2040 Datasheet.pdf#page=546|RP2040 Datasheet, раздел «4.7.3. Watchdog Counter»]]). Scratch-регистры с 4-го по 7-й занимает SDK, поэтому счётчику отдан нулевой ([[RP2040 Datasheet.pdf#page=546|раздел «4.7.4. Scratch Registers»]]).

### 2. Обновлять в суперцикле

Признак жизни прибора — итерация суперцикла. Поэтому обновление стоит в `main.c` в конце итерации, после обработчиков всех задач. Пока сторожевой таймер не включён, `watchdog_update()` ничего не меняет, и вызов можно оставить в суперцикле всегда.

>[!success] Должно получиться так
> ```c
> // в суперцикле, после обработчиков всех задач
>
> // все задачи вернули управление — суперцикл жив
> platform_watchdog_feed();
>
> profiling_stop(STOPWATCH_LOOP);
> ```

Не ставьте обновление в обработчик будильника индикатора, хотя он вызывается ровно и сам. Будильник срабатывает и при зависшем суперцикле, и сторожевой таймер исправно обновлялся бы у прибора, который уже не работает.

### 3. Добавить команды

Команда `hang` вешает суперцикл навсегда. Это и есть то зависание, от которого защищает сторожевой таймер, только вызванное нарочно.

```c
static void cmd_hang(const command_t *command)
{
    printf("hang: superloop stopped\n");

    // суперцикл больше не идёт, прерывания приходят как прежде
    while (1)
    {
    }
}
```

>[!success] Должно получиться так
> ```c
> // cmd_wdt_enable(): аргумент не один или не число — error: usage wdt_enable <timeout_ms>
> // platform не принял таймаут — error: timeout_ms must be 1..8388
> // ответ wdt: enabled, timeout <таймаут> ms
>
> // cmd_reset_reason(): ответ reset: watchdog, restarts <число>
> // или reset: other, restarts <число>
> ```

| Что нужно написать | Где это разбиралось |
| --- | --- |
| обязательный числовой аргумент | `timer_blink_start`, [[п3.2.1 Индикатор записи#3. Добавить команды\|п3.2.1]] |
| значение, которое функция возвращает через указатель | `pi_task_get_result()`, [[п2.3.4 Расчёт по шагам#^intro\|п2.3.4]] |

### 4. Проверить в терминале

Соберите проект, запишите прошивку, включите сторожевой таймер и мигание.

>[!success] Должно получиться так
> ```
> reset_reason
> reset: other, restarts 0
> wdt_enable 2000
> wdt: enabled, timeout 2000 ms
> timer_blink_start 250
> timer_blink: started, period 250 ms
> uptime
> uptime: 43646 ms
> hang
> hang: superloop stopped
> ```

После `hang` прибор перестаёт отвечать, но светодиод ещё мигает. Прерывания будильника приходят, как прежде, и снаружи прибор выглядит живым. Через 2 с плата перезапускается, светодиод переходит к обычному миганию задачи светодиода, а порт на компьютере пропадает. Откройте терминал заново.

>[!success] Должно получиться так
> ```
> reset_reason
> reset: watchdog, restarts 1
> uptime
> uptime: 1666 ms
> ```

Если повторить `wdt_enable 2000` и `hang`, счётчик вырастет до двух. После выключения питания он снова начнётся с нуля. После перезапуска сторожевой таймер выключен, и `wdt_enable` нужно дать заново.

### 5. Выбрать таймаут для рекордера

Таймаут в 2 с удобен для опыта, но для рекордера он велик. Выберите его сами, между двумя границами из [[т3.2.9 Сторожевой таймер#Выбор таймаута|т3.2.9]]. Нижняя граница — худшая итерация суперцикла. В [[п3.2.4 Поток с двойной буферизацией#5. Проверить время задачи потока|п3.2.4]] профилирование показало её во время потока, 1,5 мс. Верхняя граница — допустимый простой. Буфер заполняется за 11,6 мс, и каждый буфер, который прибор не отправил, — это потерянный кусок записи. Запишите в `README.md` проекта, какой таймаут вы бы выбрали для рекордера и почему. Проверка этого не читает, это ваше инженерное решение.

### 6. Снять лог

Скопируйте [[check-3-2-6.py]] в папку проекта и запустите.

``` bash
python check-3-2-6.py
```

Скрипт спрашивает причину сброса, пробует таймаут больше предела, включает сторожевой таймер на 2 с и ждёт 3 с, чтобы убедиться, что исправный прибор не сбрасывается. Затем он отправляет `hang`, ждёт, пока плата пропадёт и появится снова, переподключается и спрашивает причину сброса.

>[!success] Должно получиться так
> ```
> reset_reason
> reset: other, restarts 0
> wdt_enable 9000
> error: timeout_ms must be 1..8388
> wdt_enable 2000
> wdt: enabled, timeout 2000 ms
> uptime
> uptime: 7373 ms
> uptime
> uptime: 10410 ms
> hang
> hang: superloop stopped
> reset_reason
> reset: watchdog, restarts 1
> uptime
> uptime: 1666 ms
> Обмен записан в device-3-2-6.log
> ```

Первый `reset_reason` отвечает `other`, если перед прогоном вы записали прошивку или переподключили плату. Если вы уже вешали прибор, ответ будет `watchdog`, а проверке это не мешает.
