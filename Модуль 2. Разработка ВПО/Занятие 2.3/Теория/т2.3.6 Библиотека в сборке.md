В прошлом разделе модуль получил средства языка: заголовок определяет, что модуль открывает другим, а остальное язык позволяет закрыть от компоновщика. Но всё это происходит внутри кода. Для системы сборки модуль по-прежнему лишь несколько файлов прошивки. Его исходники, путь к его заголовкам и библиотеки SDK, которые нужны его реализации, записаны в описании сборки прошивки, и всё, что модуль подключил для себя, становится доступно каждому её файлу. Может ли модуль сам описать свою сборку: что нужно ему и что получают те, кто им пользуется?
^intro

## Перенос описания сборки в модуль

Посмотрим, как модуль подключается к прошивке сейчас. В задании [[п1.3.7 Паспорт устройства#^intro|Паспорт устройства]] модуль `device` из файлов `device.h` и `device.c` читает серийный номер платы функцией SDK, и для его сборки в `CMakeLists.txt` прошивки понадобились три строки:

```cmake
add_executable(${PROJECT_NAME} main.c device/device.c)
target_include_directories(${PROJECT_NAME} PRIVATE device)
target_link_libraries(${PROJECT_NAME} pico_stdlib pico_unique_id)
```

Все три строки описывают `device`, но записаны в описании прошивки. Прошивка знает, из каких файлов состоит модуль, где лежит его заголовок и что `device.c` нужна библиотека SDK `pico_unique_id`. Чтобы взять модуль в другой проект, все три строки придётся повторить там, причём по `CMakeLists.txt` не видно, что `pico_unique_id` нужна именно `device`, а не прошивке.

Перенести эти сведения к самому модулю позволяет библиотека.

![[Библиотека#^def]]

Описание сборки библиотеки лежит в собственном `CMakeLists.txt` в её папке:

```cmake
add_library(device STATIC
    src/device.c
)

target_include_directories(device PUBLIC
    include
)

target_link_libraries(device PRIVATE
    pico_unique_id
)
```

`add_library` устроена так же, как `add_executable`, но описывает не прошивку, а библиотеку; слово `STATIC` означает, что её код при сборке войдёт в образ прошивки. В описании прошивки от модуля остаётся только имя:

```cmake
# Добавить к сборке проекта описание из device/CMakeLists.txt
add_subdirectory(device)

target_link_libraries(${PROJECT_NAME} pico_stdlib device)
```

Прошивка больше не знает ни файлов `device`, ни того, что модулю нужна `pico_unique_id`: всё это записано у самого модуля и переезжает вместе с его папкой. Поэтому устройство библиотеки можно менять, не трогая проект. Можно разделить `device.c` на несколько файлов, подключить ещё одну библиотеку SDK или отказаться от неё. Пока заголовок библиотеки остаётся прежним, править не придётся ни описание сборки прошивки, ни код, который вызывает функции `device`.

## Видимость зависимостей библиотеки

Пользователем библиотеки будем называть всё, что её подключает: прошивку или другую библиотеку. Для каждой своей зависимости библиотека указывает, кому та нужна. `PRIVATE` значит, что зависимость нужна только файлам самой библиотеки. `PUBLIC` — что она нужна и её пользователям, и те получают её вместе с библиотекой. У `device` путь к папке `include` объявлен `PUBLIC`: без него пользователь не найдёт `device.h`. Библиотека `pico_unique_id` объявлена `PRIVATE`: серийный номер читает только `device.c`, а пользователи вызывают функции `device` и о SDK ничего не знают.

Так делят три вида зависимостей: пути к заголовкам (`target_include_directories`), библиотеки (`target_link_libraries`) и определения макросов (`target_compile_definitions`). Деление повторяет то, что в прошлом разделе мы делали с `.h` и `.c`, только на уровне сборки:

| | Модуль на **C** | Библиотека в сборке |
| --- | --- | --- |
| открыто пользователям | прототипы, типы и константы в заголовке | `PUBLIC`: путь к заголовку, библиотеки и макросы, без которых заголовок не соберётся |
| закрыто | `static`-функции и переменные в `.c` | `PRIVATE`: всё, что нужно только файлам `.c` |

Отсюда правило выбора. `PUBLIC` — ровно то, без чего заголовок библиотеки не соберётся у пользователя, всё остальное — `PRIVATE`. Решают это не пробами, а по тексту заголовка. Каждая строка `#include` в нём и каждый макрос, от которого зависит его текст, попадут к пользователю, поэтому соответствующая зависимость — `PUBLIC`. Если, например, заголовок библиотеки подключает заголовок другой библиотеки ради типа, эта другая библиотека нужна пользователю тоже. То, что подключают только файлы `.c`, — `PRIVATE`.

Ошибку в выборе видно по сообщению компилятора. Журнал из задания [[п1.3.6 Макросы логирования#^intro|Макросы логирования]] пользуется модулем `device`: в задании п1.3.7 он стал печатать паспорт устройства при запуске. Пусть обе части оформлены библиотеками, и `logging` подключает `device` как `PRIVATE`, потому что `device_info()` вызывает только `log.c`. Если строку `#include "device/device.h"` поставить не в `log.c`, а в `log.h`, сборка остановится у пользователя журнала, который сам `device` не подключает, — например, в `main.c` прошивки, где паспорт не нужен:

```text
In file included from main.c:2:
log.h:3:10: fatal error: device/device.h: No such file or directory
    3 | #include "device/device.h"
      |          ^~~~~~~~~~~~~~~~~
compilation terminated.
```

Первая строка показывает, что заголовок не нашёлся в заголовке библиотеки, который подключил `main.c`, а не в коде самого `main.c`. Исправить это можно двумя способами, и выбор между ними — по правилу о заголовках из прошлого раздела. Если `log.h` действительно нужно что-то из `device.h`, например константа для макросов журнала, зависимость становится `PUBLIC`. Если `device.h` нужен только `log.c`, `#include` переносят туда, и зависимость остаётся `PRIVATE`. Если же объявлять `PUBLIC` всё подряд, проект соберётся, но каждый пользователь получит всё, что библиотека подключала для себя, и по описанию сборки уже не будет видно, что кому нужно.

Те же правила действуют и на файлы самой библиотеки: компилируются они только с тем, что библиотека объявила себе, и с тем, что её зависимости объявили `PUBLIC`. Заголовок, путь к которому не пришёл ни с одной из этих сторон, компилятор в файлах библиотеки не найдёт.

## Раскладка папок библиотеки

В прошлом разделе мы договорились подключать заголовок с именем модуля — `"device/device.h"` — и отложили вопрос, как сборка находит такой путь. Ответ — в раскладке папок библиотеки:

```
device/
├── CMakeLists.txt
├── include/
│   └── device/
│       └── device.h       интерфейс
└── src/
    └── device.c           реализация
```

Библиотека открывает пользователям путь к `include`, а заголовок лежит в `include/device/`. Препроцессор склеивает открытый путь с тем, что написано в `#include`, и находит `include/device/device.h`. Так же устроен и SDK: строка `#include "pico/unique_id.h"` из задания П1.3.6 находит файл `pico_unique_id/include/pico/unique_id.h`.

Путь к `src/` библиотека не открывает никому, а её собственные файлы свои заголовки из `src/` находят и без него: заголовок в кавычках препроцессор сначала ищет в папке того файла, который его подключает. Поэтому в `src/` кладут внутренние заголовки модуля из нескольких файлов. Файлы самого модуля подключают их по имени, а у пользователя на такой `#include` компилятор ответит `No such file or directory`.

## Настройка библиотеки макросом

Определения макросов — третий вид зависимостей, и правило выбора для них то же. Модуль `profiling` из задания [[п2.2.4 Профилирование#^intro|Профилирование]] замеряет каждую итерацию суперцикла, а замер не бесплатен ([[т2.2.5 Профилирование#^intro|Профилирование]]). В сборке, где мерить не нужно, вызов удобно убирать совсем. Для этого заголовок модуля выбирает, что объявить, по макросу `PROFILING_ENABLED`, а если макрос не задан, берёт значение по умолчанию:

```c
// По умолчанию профилирование включено
#ifndef PROFILING_ENABLED
#define PROFILING_ENABLED 1
#endif

#if PROFILING_ENABLED
void profiling_iteration(void);
#else
// Профилирование выключено: вызов ничего не делает
#define profiling_iteration() ((void)0)
#endif
```

Так же задаёт свои параметры и SDK: номер вывода светодиода `PICO_DEFAULT_LED_PIN` определён в заголовке платы через `#ifndef`, и проект может его переопределить. Проект, которому замер не нужен, выключает его в своём `CMakeLists.txt`:

```cmake
add_subdirectory(profiling)

target_compile_definitions(profiling PUBLIC
    PROFILING_ENABLED=0
)
```

Значение макроса должно быть одним и тем же в `profiling.c` и во всех файлах, которые подключают `profiling.h`. Будь определение `PRIVATE`, его получил бы только `profiling.c`, и библиотека собралась бы без функции `profiling_iteration()`. В `main.c` макрос оказался бы не задан, заголовок взял бы значение по умолчанию и оставил вызов функции, которой в библиотеке нет. Сборка остановилась бы на `undefined reference to 'profiling_iteration'`. Макрос нужен, чтобы заголовок правильно собрался у пользователя, поэтому его место в `PUBLIC`.

Теперь у модуля есть два средства закрыть лишнее: `static` закрывает имена внутри файла, а `PRIVATE` закрывает то, что модулю нужно для сборки, и компилятор следит, чтобы модуль не взял больше объявленного. Но ни одно из них не говорит, где провести границу между модулями и какие модули стоит держать без SDK. Этим займёмся в следующем разделе.
