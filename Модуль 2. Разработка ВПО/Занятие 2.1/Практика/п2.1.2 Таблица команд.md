**Результат** — цепочка сравнений в `211-command-usb` заменена таблицей команд: массивом пар «имя команды — обработчик». Добавить прибору команду теперь значит написать функцию и дописать одну строку в массив, а разбор принятой строки при этом не меняется вовсе.

## Задание

### Что должно получиться

- [ ] Объявлен тип `command_handler_t` — указатель на функцию без аргументов и без возвращаемого значения
- [ ] Объявлен тип `struct command_t` с именем команды и её обработчиком
- [ ] Действие каждой команды вынесено в отдельную функцию с этой сигнатурой
- [ ] Заведён массив `commands` с модификатором `const`, и разбор строки ищет имя в нём
- [ ] Обработчик вызывается по указателю, а указатель перед вызовом проверен на `NULL`
- [ ] Команда `ping` отвечает `pong`, и ради неё в разбор принятой строки не дописано ни строки
- [ ] Рядом с `main.c` лежит `device-2-1-2.log` с обменом на живой плате

### Как проверить

1. **Прибор ведёт себя как до переделки.** `enable`, `disable`, `info` и `version` работают по-прежнему, незнакомое слово по-прежнему не меняет состояния светодиода и возвращается в сообщении об ошибке. Переделка внутренняя: снаружи прибор остался тем же.
2. **Новая команда стоит ровно две вещи.** Посчитайте, что вы написали ради `ping`: одну функцию-обработчик и одну строку в массиве. В `handle_command()` не добавилось ни символа — и это главный результат задания.
3. **Автоматическая проверка курса принимает задание.** Она читает `main.c`: есть `typedef` указателя на функцию, есть тип с полями имени и обработчика, массив объявлен с `const`, разбор строки идёт циклом по массиву, обработчик вызывается по указателю и проверен на `NULL`, а сравнения `strcmp()` с именем команды в тексте разбора не осталось — сравнивается только `commands[i].name`. И читает лог прогона: `ping` ответила `pong`, остальные команды отработали как прежде.

## Ход работы

Теория задания — [[т2.1.7 Указатели на функции#^intro\|т2.1.7]].

>[!info] Почему это задание стоит вторым
>Цепочка `if`/`else` из прошлого задания работает и на четырёх командах не мешает. Мешать она начнёт дальше: в оставшихся четырёх заданиях занятия прибор получит команды `mem_info`, `fw_info` и `boot_info`, в занятии 2.2 — команды управления временем, в занятии 2.3 — команды с аргументами. Каждая новая ветка означала бы правку общей функции разбора, то есть риск сломать разбор всех остальных команд.
>
>Таблица разводит два разных дела: **что прибор умеет** — это массив, и **как он ищет команду** — это цикл, написанный один раз. Дальше формулировка каждого задания сводится к «реализовать такую-то команду», и вы уже знаете, что за этим стоит: функция и строка в массиве.

### 1. Описать тип обработчика

Все команды прибора устроены одинаково: у них нет аргументов и они ничего не возвращают. Значит, у них одинаковая [[Сигнатура функции#^def|сигнатура]], и её можно назвать одним именем:

``` c
typedef void (*command_handler_t)(void);
```

Читается запись изнутри наружу: `(*command_handler_t)` — это указатель, `void (…)(void)` — на функцию без аргументов и без возвращаемого значения. Теперь `command_handler_t` — такой же тип, как `uint32_t`, только переменная этого типа хранит адрес функции.

>[!info] Зачем `typedef`, если можно объявить и без него
>Без `typedef` поле структуры пришлось бы описывать как `void (*handler)(void)`, а массив таких функций — как `void (*handlers[])(void)`. Запись читается тяжело и повторяется в каждом месте, где встречается обработчик. Если использовать `typedef`, то же самое пишется как `command_handler_t handler` — сигнатура названа один раз, в одном месте. Так же поступает и Pico SDK: обработчик прерывания в нём объявлен как `irq_handler_t`.

### 2. Вынести действие каждой команды в свою функцию

Тела веток `if` из прошлого задания переезжают в отдельные функции — по функции на команду. Меняется только оболочка: код внутри остаётся тем же, что вы уже написали.

>[!success] Должно получиться так
> ```c
> void cmd_enable(void)
> {
>     // включаем светодиод и сообщаем новое состояние
> }
>
> void cmd_disable(void)
> {
>     // выключаем светодиод и сообщаем новое состояние
> }
>
> void cmd_info(void)
> {
>     // печатаем паспорт устройства
> }
>
> void cmd_version(void)
> {
>     // печатаем строку журнала о версии прошивки
> }
> ```

>[!quote] Из практики
>Складывая обработчики в один массив, вы обнаружите, что в него подходят не все. У команды `enable` действие — `gpio_put()` с единицей, у `disable` — то же с нулём, и напрашивается одна функция с аргументом. Но тип у массива один на все элементы, а сигнатура входит в тип: `void led_enable(void)` и `void led_set(bool on)` в одном массиве не лежат. Значит, различие уходит внутрь обработчика — две функции без аргументов, каждая со своим вызовом `gpio_put()`. Так же устроен и Pico SDK: `irq_handler_t` не принимает ничего, а что обработчику нужно знать, он берёт из своих переменных. Команды с аргументами вроде `led_period 1000` потребуют другой сигнатуры, одной сразу на все команды, — этим вы займётесь в занятии 2.3.

### 3. Собрать таблицу команд

Команда прибора — это пара: слово, которое набирает человек, и функция, которая на него отвечает. Опишите эту пару типом и соберите из пар массив:

``` c
struct command_t
{
    const char *name;
    command_handler_t handler;
};

const struct command_t commands[] = {
    { "enable", cmd_enable },
    { "disable", cmd_disable },
    { "info", cmd_info },
    { "version", cmd_version },
};

#define COMMAND_COUNT (sizeof(commands) / sizeof(commands[0]))
```

Поле `name` — указатель на строку, поле `handler` — адрес функции. В фигурных скобках стоят имена функций без скобок вызова: имя функции без скобок и есть её адрес, и это ровно то, что разбирает [[т2.1.7 Указатели на функции#^intro\|т2.1.7]].

`COMMAND_COUNT` считает длину массива сам: размер всего массива, делённый на размер одного элемента. Число команд нигде не записано цифрой, поэтому оно не разойдётся с массивом, сколько бы строк вы в него ни дописали.

>[!info] Зачем массиву `const`
>`const` говорит компилятору, что таблица не меняется во время работы. Компилятор верит и кладёт её во флеш-память, рядом с кодом, — вместо того чтобы занимать ею ОЗУ, которого в микроконтроллере в двадцать раз меньше. Одно слово в объявлении, и несколько десятков байт ОЗУ остаются свободными.
>
>Верить на слово здесь не нужно: в задании [[п2.1.3 Системная память#^intro\|п2.1.3]] вы снимете `const`, пересоберёте проект и увидите, как массив переезжает из флеш-памяти в ОЗУ, — прибор покажет это сам, изменением чисел в своём же выводе.

### 4. Заменить цепочку поиском по таблице

Теперь разбор принятой строки перестаёт знать команды по именам. Он делает одно: идёт по массиву, сравнивает принятое слово с очередным именем и, найдя совпадение, вызывает обработчик по указателю.

``` c
void handle_command(const char *command)
{
    for (uint i = 0; i < COMMAND_COUNT; i++)
    {
        if (strcmp(command, commands[i].name) == 0)
        {
            if (commands[i].handler != NULL)
            {
                commands[i].handler();
            }

            return;
        }
    }

    LOG_ERR("unknown command: %s\n", command);
}
```

Строка `commands[i].handler()` — и есть вызов по указателю: скобки после указателя означают «передать управление по этому адресу». Никакого особого синтаксиса язык здесь не требует, вызов выглядит как обычный.

Сообщение об ошибке осталось прежним и стоит после цикла: до него доходят только те слова, которых в таблице не нашлось.

>[!failure] Не вызывайте обработчик без проверки на `NULL`
>Пустое поле `handler` в таблице — это адрес `0x00000000`. Вызов по такому адресу не даст ни ошибки компиляции, ни внятного сообщения: ядро передаст управление в начало Boot ROM, и прибор поведёт себя непредсказуемо — от молчания до перезагрузки. Одна строка проверки превращает забытый обработчик в «команда ничего не сделала», а это уже можно отладить.

### 5. Добавить команду ping

Теперь проверьте, чего стоила переделка. Задача: прибор должен отвечать `pong` на команду `ping` — это дежурная команда связи, по которой спрашивают «ты жив?».

Напишите функцию-обработчик и допишите строку в массив. Больше ничего.

>[!success] Должно получиться так
> ```c
> void cmd_ping(void)
> {
>     printf("pong\n");
> }
> ```
>
>И строка в таблице:
>
> ```c
>     { "ping", cmd_ping },
> ```

Загляните в `handle_command()` — он не изменился. Это и есть то, ради чего задание сделано: разбор команд написан один раз и дальше живёт сам по себе, а прибор растёт таблицей.
