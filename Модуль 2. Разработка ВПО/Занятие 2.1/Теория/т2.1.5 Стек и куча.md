Три предыдущих раздела занятия описывали память, размеченную заранее: компилятор рассортировал содержимое программы по секциям, компоновщик раздал им адреса, стартап-код разложил байты — и всё это произошло до того, как прибор включили. Но так можно поступить не со всяким содержимым. Часть данных появляется только тогда, когда программа уже работает, и ни размера, ни места для них при сборке не знает никто. Эту память программа размечает себе сама, на ходу. Один пример уже попадался: локальная переменная `delay` из раздела [[т2.1.2 Состав образа ВПО. Секции#^intro|Состав образа ВПО. Секции]] не попала ни в одну секцию, и в таблице напротив неё остался знак вопроса.
^intro

## Память, которой нет в образе

Разбирать это будем на одной программе, к которой вернёмся в каждом разделе. Прибор принимает из терминала команды из одного символа. По команде `m` он снимает два показания таймера и печатает их сумму, а по команде-цифре от `1` до `9` снимает столько показаний подряд, сколько названо, и печатает их все. Вот программа целиком:

```c
#include <stdio.h>
#include <stdlib.h>
#include "pico/stdlib.h"

// один замер: показание таймера
uint32_t read_timer(void)
{
    uint32_t value = time_us_32();
    return value;
}

// команда m: сумма двух замеров подряд
uint32_t measure_pair(void)
{
    uint32_t first = read_timer();
    uint32_t second = read_timer();
    return first + second;
}

// объявление: сама функция разбирается в разделе «Куча»
void measure_window(uint32_t count);

void handle_command(char command)
{
    if (command == 'm')
    {
        printf("%u\n", measure_pair());
    }
    else if (command >= '1' && command <= '9')
    {
        measure_window(command - '0');
    }
}

int main()
{
    stdio_init_all();

    while (true)
    {
        // опрос без ожидания: символ забирается, только если уже принят
        int c = getchar_timeout_us(0);
        if (c != PICO_ERROR_TIMEOUT)
        {
            handle_command((char)c);
        }
    }
}
```

Опрос терминала в `main()` вам знаком по занятию 1.3, разбор команды в `handle_command()` — по заданию [[п2.1.1 Многосимвольные команды#^intro|п2.1.1]]; новое здесь — функции замеров. Они упираются в разные ограничения. Функции `measure_pair()` память нужна лишь на то время, пока она считает: два показания и сумма. Такой памятью распоряжается **стек**. Функции `measure_window()` нужен массив, размер которого до запуска неизвестен: сколько замеров просить, решает оператор. Такую память даёт **куча**. Границы обеих областей компоновщик оставляет символами линкера, но что окажется внутри, решается уже в приборе.

## Как работает стек

Начнём со стека: он нужен программе с первой команды `main()`. Разобравшись, как он движется, легче понять, зачем его так используют.

![[Стек#^def]]

Место под стек отводит линкер-скрипт, разобранный в разделе [[т2.1.3 Линкер-скрипт#^intro|Линкер-скрипт]]. У RP2040 два ядра, и стек у каждого свой: одним указателем два потока команд не обслужить. Поэтому в блоке `MEMORY` помимо региона `RAM` описаны два банка по 4 КБ — `SCRATCH_Y` под стек ядра 0 и `SCRATCH_X` под стек ядра 1. Сам стек занимает в своём банке 2 КБ, от символа `__StackBottom` со значением `0x20041800` до `__StackTop` со значением `0x20042000`. Два килобайта на всю программу — и есть весь её бюджет.

Заполняется этот участок сверху вниз: первая порция данных ложится под `__StackTop`, следующая — под неё, и так далее в сторону младших адресов. Освобождается он в обратном порядке: последнее положенное снимается первым. Так устроен всякий стек, отсюда и LIFO в определении — *Last In, First Out*, «последним пришёл, первым ушёл». Весь учёт заполнения стека сводится к одному числу, границе занятой части: чтобы занять память, границу двигают вниз, чтобы освободить — вверх. Ни списка занятых участков, ни поиска свободного места не нужно, и выделение стоит одной команды.

Это число ядро хранит в отдельном регистре процессора.

![[Указатель стека#^def]]

Собственный регистр выделен под указатель стека потому, что обращается к нему почти каждая команда работы со стеком; в машинных командах и в дизассемблере он обозначается `SP`. Начальное значение указатель получает раньше, чем начнёт работать хоть одна ваша команда: как мы видели в разделе [[т2.1.4 Цепочка загрузки RP2040#^intro|Цепочка загрузки RP2040]], загрузчик второй стадии читает первую ячейку таблицы векторов — а там лежит `__StackTop` — и загружает её в `SP`. К первой команде `main()` стек готов и пуст.

Верхнюю границу переходить незачем: указатель стартует ровно на `__StackTop` и в исправной программе только опускается и возвращается обратно. А вот нижнюю, `__StackBottom`, не сторожит никто. Если программа уйдёт в вызовы слишком глубоко или заведёт крупные локальные данные, указатель опустится ниже неё, и запись пойдёт в чужую память. Ни компилятор, ни компоновщик об этом не предупредят: размеры секций им известны, а глубина вызовов — нет. Не спасёт и аппаратура: блок защиты памяти в ядре Cortex-M0+ есть, но SDK по умолчанию границу стека им не сторожит, и для шины запись ниже `__StackBottom` — обычная запись в ОЗУ. Программа продолжит работать, испортив чужие данные, и авария всплывёт в другом месте и в другое время; ошибка «прибор раз в час перезагружается неизвестно почему» — обычно именно такая.

![[Переполнение стека#^def]]

>[!INFO] Дополнительно
>Сторожа границе приставить можно, и в ответственных прошивках так делают. Первый способ — настроить блок защиты памяти: запретить запись в небольшую область прямо под `__StackBottom`, и тогда переполнение остановит программу немедленно, в точке причины, а не через час в чужой переменной. Второй обходится без аппаратуры: при старте дно стека засевают известным узором, а затем время от времени проверяют, цел ли он; узор затёрт — значит, стек хотя бы раз доходил до дна. Pico SDK не делает ни того ни другого: в простой прошивке дешевле посчитать расход стека при сборке, чем тратить на проверку такты и области защиты.

Как переполнение выглядит на конкретной функции, во что обходится четырёхкилобайтный локальный массив при стеке в два килобайта и чем измерить расход стека до загрузки в плату, разобрано в приложении [[пр2.3 Вызов функции в машинных командах#^intro|пр2.3 Вызов функции в машинных командах]]; для заданий занятия оно не требуется.

## Зачем нужен стек

Теперь, когда видно, как стек движется, разберём, что в него кладут. Назначение у него одно: хранить данные, которые нужны программе не всё время, а ровно столько, сколько работает та её часть, которая их завела. Отсюда и совпадение с порядком LIFO: части программы вложены друг в друга, и та, что начала работать последней, закончит первой.

Проще всего это увидеть на локальных переменных. Функции `measure_pair()` нужны два показания таймера, `first` и `second`: они нужны, пока функция складывает их, и не нужны ни секундой дольше. Постоянное место под такую переменную расточительно: под локальные переменные всех функций программы пришлось бы отвести ОЗУ сразу, хотя одновременно работают две-три. Но оно ещё и попросту не сработает. Одна и та же функция может оказаться запущенной дважды одновременно, если она вызывает саму себя, а двум вызовам нужны два разных набора переменных. Стек решает обе задачи разом: память отводится при входе в функцию, отбирается при выходе, а второй вызов получает свой участок ниже первого.

Локальными переменными дело не ограничивается, и здесь начинается вторая, менее очевидная половина работы стека. Вызов функции — это не только передача управления: уходя в чужой код, программа должна оставить след, по которому вернётся, и сберечь всё, что понадобится ей после возврата. В стек при этом уходят три рода данных: адрес возврата, сохранённый контекст и аргументы, не поместившиеся в регистры процессора.

Адрес возврата — это адрес команды, следующей за вызовом: управление уходит в другое место программы, и потерять дорогу назад нельзя. Сохранённый контекст — та часть содержимого регистров процессора, которая понадобится после возврата: вызванная функция пользуется регистрами свободно и не может знать, что в них было до неё.

![[Контекст исполнения#^def]]

К контексту мы вернёмся в занятии 2.2, когда программу начнёт прерывать периферия; пока достаточно того, что это регистры процессора и что при вызове часть их приходится складывать в память. Аргументы попадают в стек лишь отчасти: на Cortex-M первые четыре аргумента и результат передаются в регистрах процессора и стека не касаются вовсе, а в стек уходит только лишнее — пятый и последующие аргументы, крупные структуры. Как именно, разберём в разделе [[т2.1.7 Указатели на функции#^intro|Указатели на функции]]. Эти три рода данных и складываются в стек при каждом вызове, и решает, что именно складывать, не программист.

## Участие стека в вызове функций

В исходном тексте функции на **C** нет ни слова о сохранении регистров процессора, а в машинных командах оно есть: вставляет его компилятор. Делает он это по правилам, заданным заранее и одинаковым для всего кода в образе, включая чужой код SDK: иначе ваша функция не смогла бы вызвать библиотечную, а библиотечная — вашу.

![[Соглашение о вызове#^def]]

Распределение ответственности устроено так. Одни регистры процессора — `r0`–`r3` и `r12` — вызываемая функция вправе использовать по своему усмотрению и вернуть изменёнными; их называют не сохраняемыми при вызове, и если вызывающей функции их содержимое ещё нужно, она сохраняет его сама перед вызовом. Другие — `r4`–`r11` — вызываемая обязана вернуть нетронутыми; их называют сохраняемыми при вызове, и если они ей нужны, сохраняет их она. Обе стороны складывают сохранённое в стек, и обе делают это руками компилятора: соблюдение соглашения — его работа, а не ваша. Всё, что одна функция откладывает в стек на время своей работы, лежит одним куском.

![[Кадр вызова#^def]]

Посмотрим на цепочку вызовов целиком по листингу из начала статьи. Команда `m`, пришедшая из терминала, принимается в `main()` и передаётся обработчику `handle_command()`; тот вызывает `measure_pair()`, которая снимает два показания таймера и складывает их, а она, в свою очередь, дважды вызывает `read_timer()`. Каждый вызов кладёт свой кадр вызова под предыдущий, и указатель стека опускается:

![[Цепочка вызовов.excalidraw|100%]]

Четвёртое состояние на схеме стоит разобрать отдельно: `read_timer()` вызвана, а указатель стека не сдвинулся. Кадр вызова ей не понадобился. Она никого не вызывает, значит, адрес возврата никто не перезапишет и сохранять его незачем, а её единственная локальная переменная всю жизнь провела в регистре процессора. Так часто бывает с функциями на конце цепочки вызовов. У `measure_pair()` кадр вызова, наоборот, есть, хотя локальных массивов в ней нет. Результат первого замера должен пережить второй вызов, а вызванная функция распоряжается регистрами свободно. Поэтому компилятор переносит его в регистр, сохраняемый при вызове, а прежнее содержимое этого регистра прячет в стек. Вместе с адресом возврата получается восемь байт. Вот этот кадр вызова в разрезе:

![[Кадр вызова.excalidraw|100%]]

Из трёх частей кадра вызова, названных в определении, у `measure_pair()` заняты две: адрес возврата и один сохранённый регистр вызывающей функции; под локальные переменные места не понадобилось. Аргументы, если их больше четырёх, лежат выше — в кадре вызова той функции, которая их и положила.

На обратном ходе — это пятое состояние на схеме — то же происходит в зеркальном порядке. Каждая функция перед выходом возвращает указатель стека туда, где он был на входе, и снятый кадр вызова перестаёт существовать — вместе со всеми локальными переменными, которые в нём лежали. Отсюда правило, о которое спотыкаются чаще всего: адрес локальной переменной перестаёт быть действительным в момент возврата из функции. Вернуть его наружу можно, пользоваться им — нельзя: на этом месте очень скоро окажется кадр вызова следующей функции.

>[!ATTENTION] Внимание!
>Ответ «локальная переменная лежит на стеке» верен как правило, но не как обещание. Переменная `delay` из раздела [[т2.1.2 Состав образа ВПО. Секции#^intro|Состав образа ВПО. Секции]], с которой мы начали, не получила ни места в секции, ни места в кадре вызова: компилятор увидел, что она равна 250 и нигде не меняется, и подставил число прямо в команды. Памяти у такой переменной нет, а значит, нет и адреса. Как только вы напишете `&delay` — а в задании [[п2.1.4 Память программы#^intro|п2.1.4]] вы возьмёте адрес локальной переменной именно так, — компилятор будет обязан положить её в кадр вызова: у объекта, чей адрес взят, адрес должен существовать.

Порядок величины стоит запомнить, но снимать его надо с оглядкой на тип сборки. В сборке Release компилятор встраивает все четыре функции этой программы прямо в `main()`, и отдельных кадров вызова у них не остаётся вовсе — вызовов-то больше нет. Чтобы увидеть кадры, программу собирают отладочно. В такой сборке (Pico SDK 2.3.0, GCC 10.3, `-Og`) кадры вызова `main()`, `handle_command()` и `measure_pair()` заняли по 8 байт каждый — адрес возврата и один сохранённый регистр, — а кадр вызова `measure_window()` — 24: ей пришлось сберечь больше регистров, чтобы пережить вызовы `malloc()`, `printf()` и `free()`. Единицы и десятки байт на вызов при бюджете в два килобайта: запаса на глубину вызовов хватает с избытком, и кончается он обычно не от глубины, а от одного крупного локального массива.

## Куча

Вернёмся ко второй команде прибора — цифре и функции `measure_window()`. В листинге выше стояло только её объявление; вот она целиком:

```c
// команда-цифра: столько замеров подряд, сколько назвал оператор
void measure_window(uint32_t count)
{
    // массив под замеры берётся из кучи: размер известен только сейчас
    uint32_t *samples = malloc(count * sizeof(uint32_t));
    if (samples == NULL)
    {
        return;
    }

    // сначала все замеры подряд, вывод потом: printf() медленный
    for (uint32_t i = 0; i < count; i++)
    {
        samples[i] = read_timer();
    }
    for (uint32_t i = 0; i < count; i++)
    {
        printf("%u\n", samples[i]);
    }

    // блок возвращается в кучу
    free(samples);
}
```

Массив `samples` под названное число замеров нельзя ни отвести компоновщиком точно по размеру, ни положить в кадр вызова: при большом N он переполнит стек. Такие данные размещают в куче.

![[Куча#^def]]

Работа с кучей сводится к двум вызовам стандартной библиотеки **C**: `malloc()` получает размер в байтах и возвращает адрес блока, `free()` получает адрес обратно и объявляет блок свободным. На Raspberry Pi этим занимался за вас интерпретатор **Python**: память под список он брал сам и сам же возвращал, когда список переставал быть нужен. В **C** обе границы срока жизни блока ставит программист, и в отличие от стека, где кадр вызова отводится и снимается сам собой, ошибиться можно в обе стороны: забыть `free()` — блок останется занятым навсегда, вызвать `free()` дважды или обратиться по адресу после освобождения — испортить учёт свободных участков. Ведёт этот учёт часть библиотеки времени выполнения.

![[Аллокатор#^def]]

На Pico куча начинается сразу за `.bss`, по символу `__end__`, и растёт вверх, навстречу стеку. Потолок ей ставит конец региона `RAM`: по умолчанию там стоят сразу два символа с одинаковым значением, `__HeapLimit` и `__StackLimit`, и со вторым из них сверяет запросы сам аллокатор. Когда свободного блока нужного размера нет, `malloc()` возвращает `NULL`. На компьютере такой отказ означает, что пора закрыть приложение с сообщением об ошибке; в приборе, который должен работать месяцами без присмотра, закрываться некуда, а разумного поведения при нехватке памяти чаще всего не существует.

Отказать `malloc()` может и тогда, когда свободной памяти хватает: программа, которая долго работает, выделяет и освобождает блоки разного размера вперемешку, и свободное место оказывается разрезано занятыми блоками на куски. Суммарно свободных байт много, а непрерывного участка под очередной запрос нет — это называют фрагментацией кучи, и предсказать её при сборке нельзя, потому что порядок команд задаёт оператор. Время самого выделения тоже не ограничено сверху: аллокатор перебирает список свободных участков. Для прибора, обязанного ответить на прерывание за фиксированное время, такая неопределённость неприемлема.

Отсюда общая практика встраиваемых систем: кучи по возможности избегают. Вместо массива переменной длины заводят массив максимальной длины на этапе компиляции — он попадёт в `.bss`, займёт свои байты раз и навсегда, а компоновщик сразу скажет, помещается ли он в ОЗУ. Прошивка выходит менее гибкой, зато её потребление памяти известно до загрузки в плату, а не выясняется на третьей неделе работы. Это не запрет: в задании [[п2.1.4 Память программы#^intro|п2.1.4]] вы воспользуетесь `malloc()`. Но каждый его вызов стоит рассматривать как решение, которое нужно обосновать.

Прежде чем переходить к заданию, стоит предсказать, что покажут повторные вызовы одной и той же функции: сначала для стека, потом для кучи. Адрес локальной переменной в функции, которую вызывают из одного и того же места, будет от вызова к вызову один и тот же: глубина вызовов та же, значит, и указатель стека на входе тот же, и кадр вызова ложится на то же место. Адрес блока в куче зависит от того, освобождали ли предыдущий: `measure_window()` вызывает `free()` перед выходом, поэтому при следующем вызове аллокатор найдёт тот же освободившийся блок и вернёт тот же адрес. Если `free()` убрать, каждый вызов займёт новый блок, и адреса поползут вверх. Так выглядит утечка памяти: в терминале вы увидите её собственными глазами, растущим числом.

## Итог

Стек заполняется сверху вниз и освобождается в обратном порядке, а весь учёт занятого сводится к одному регистру процессора — указателю стека. Отведено ему у каждого из двух ядер RP2040 по 2 КБ в своём банке, и нижнюю границу никто не сторожит: переполнение выполняется как обычная запись в ОЗУ и проявляется не там, где причина. Служит стек данным, нужным программе на время работы одной её части: локальным переменным, адресу возврата, сохранённому контексту и аргументам сверх четырёх. Складывать их в кадр вызова и снимать его при возврате — работа компилятора по правилам соглашения о вызове. Куча решает другую задачу, данные неизвестного при сборке размера: `malloc()` берёт блок, `free()` возвращает, учёт ведёт аллокатор, а платой за гибкость становятся непредсказуемое время выделения и фрагментация.

Обе области, а вместе с ними и всё, что разложили по ОЗУ компоновщик и стартап-код, умещаются на одной карте:

![[Карта ОЗУ.excalidraw|100%]]

Между `__end__` и концом региона `RAM` лежат почти 250 килобайт — единственная память, которой программа распоряжается во время работы. Куча забирает её снизу вверх, стек ядра 0 подходит сверху, из отдельного банка. Классическая картина «стек растёт вниз, куча растёт вверх, встреча посередине — авария» на RP2040 буквально неверна: стеки ядер вынесены в собственные банки, и переполнившемуся стеку ядра 0 придётся пройти шесть килобайт `SCRATCH_Y` и `SCRATCH_X`, прежде чем он доберётся до кучи. Запас, но не защита: авария не исчезает, а только откладывается и делается ещё менее заметной.

Мы закончили разбор памяти: знаем, что в ней лежит, кто это разложил и что появляется во время работы. Всё это время мы говорили об адресах, но обращались к ним чужими руками — читали `.map`, смотрели дизассемблер, брали `&__StackTop` по готовому рецепту. Пора взять адрес в руки как инструмент: получить адрес любой переменной, прочитать и записать байты по произвольному числу, добраться до регистра периферии без посредника.
