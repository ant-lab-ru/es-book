**Результат** — прибор `321-audio-recorder` умеет снимать отсчёты по будильнику таймера. Команда `cap_start` запускает захват заданного числа отсчётов с заданным периодом, а `cap_dump` выводит их вместе с разбросом интервалов и долей времени ядра в обработчике. По этим числам вы сами увидите, почему звук так не оцифровывают.
^intro

## Задание

### Что должно получиться

- [ ] Обработчик будильника в `platform` снимает отсчёт `adc_read()`, записывает его время и время своей работы
- [ ] Команды `cap_start <N> <period_us>` и `cap_dump` работают, `cap_dump` начинается строкой с интервалами и долей обработчика
- [ ] Пока идёт захват, команды, которым нужен АЦП, отвечают `error: adc busy`
- [ ] Вы сравнили захват с периодом 125 и 23 мкс и можете объяснить, почему для звука нужен делитель АЦП
- [ ] Лог `device-3-2-2.log` снят, коммит отправлен, проверка `3.2.2` зелёная

### Как проверить

1. **Интервалы видно в ответе.** `cap_start 1000 125`, затем `cap_dump` показывает интервалы около 125 мкс и тысячу кодов.
2. **Лог прогона лежит в проекте.** Скрипт задания записывает обмен в `device-3-2-2.log`.
3. **Автоматическая проверка курса принимает задание.** В коде она ищет `add_repeating_timer_us()` и `adc_read()` в обработчике будильника и проверяет, что обработчик не печатает. В логе она читает первую строку `cap_dump` после захвата 1000 отсчётов по 125 мкс и 2000 по 23 мкс. Интервалы должны окружать период, число кодов совпадать с N, а коды лежать от 0 до 4095.

## Ход работы

Это задание выполняет требование Р2.3 [[ТЗ 3.2 Рекордер|ТЗ на рекордер]] и проверяет на плате строку «Задать шаг отсчётов» его таблицы выбора инструментов. Почему будильник не годится для звука, рассуждением выведено в [[т3.2.2 Таймер#Будильник и шаг отсчётов|т3.2.2]]. Здесь вы получите числа.

### 1. Снимать отсчёты в обработчике будильника

Захват — работа с железом, он живёт в `platform`. Добавьте в `platform.h` его интерфейс.

```c
// занят ли АЦП захватом
bool platform_adc_busy(void);

// захват count отсчётов GP26 по будильнику с периодом period_us;
// false — АЦП занят или count больше PLATFORM_CAPTURE_MAX
#define PLATFORM_CAPTURE_MAX 2000
bool platform_capture_start(uint32_t count, uint32_t period_us);
bool platform_capture_done(void);

// итог захвата по будильнику: отсчёты, разброс интервалов
// и доля времени ядра внутри обработчика, в процентах
typedef struct {
    const uint16_t *samples;
    uint32_t count;
    uint32_t period_us;
    uint32_t min_interval_us;
    uint32_t max_interval_us;
    float handler_percent;
} platform_capture_t;

void platform_capture_get(platform_capture_t *capture);
```

В `platform.c` обработчик на каждом срабатывании записывает время, снимает отсчёт и прибавляет время своей работы к общему. Время он берёт у `time_us_32()`, младших 32 бит счётчика таймера. Это одно слово, его чтение атомарно ([[т3.2.5 Обработчик прерывания#Атомарность|т3.2.5]]). Когда отсчёты набраны, обработчик возвращает `false`, и SDK снимает будильник сам.

```c
// кто сейчас работает с АЦП; меняют и функции, и обработчики прерываний
typedef enum {
    ADC_FREE,
    ADC_CAPTURE,
} adc_user_t;

static volatile adc_user_t adc_user;

static repeating_timer_t capture_timer;
static uint16_t capture_samples[PLATFORM_CAPTURE_MAX];
static uint32_t capture_times[PLATFORM_CAPTURE_MAX];
static uint32_t capture_count;
static uint32_t capture_period_us;
static volatile uint32_t capture_index;
static volatile uint32_t capture_handler_us;

// обработчик будильника захвата: время и отсчёт, затем время своей работы
static bool on_capture(repeating_timer_t *timer)
{
    uint32_t start_us = time_us_32();
    capture_times[capture_index] = start_us;
    capture_samples[capture_index] = adc_read();
    capture_index++;
    capture_handler_us += time_us_32() - start_us;

    if (capture_index < capture_count)
    {
        return true;
    }

    // захват окончен: АЦП свободен, будильник снимается
    adc_user = ADC_FREE;
    return false;
}

bool platform_capture_start(uint32_t count, uint32_t period_us)
{
    if (adc_user != ADC_FREE || count == 0 || count > PLATFORM_CAPTURE_MAX || period_us == 0)
    {
        return false;
    }

    adc_select_input(ADC_CHANNEL);
    capture_count = count;
    capture_period_us = period_us;
    capture_index = 0;
    capture_handler_us = 0;
    adc_user = ADC_CAPTURE;

    if (!add_repeating_timer_us(-(int64_t)period_us, on_capture, NULL, &capture_timer))
    {
        adc_user = ADC_FREE;
        return false;
    }
    return true;
}
```

Остальные три функции короткие, их логику напишите сами.

>[!success] Должно получиться так
> ```c
> // platform_adc_busy(): АЦП не свободен
>
> // platform_capture_done(): захват запускали, и набраны все отсчёты
>
> // platform_capture_get(): адрес отсчётов, их число и период;
> // по разностям соседних времён — наименьший и наибольший интервал;
> // доля обработчика — его общее время в процентах от времени
> // между первым и последним отсчётом;
> // у одного отсчёта интервалов нет, тогда всё это нули
> ```

Доля обработчика здесь — только время внутри `on_capture()`. Вход в прерывание, выбор будильника в пуле SDK и возврат она не учитывает, поэтому настоящая цена захвата для ядра выше.

### 2. Добавить команды

`cap_start` запускает захват и сразу отвечает. `cap_dump` печатает итог, первой строкой интервалы и долю обработчика, затем коды строками `cap:` по 16. Пока АЦП занят, `get_voltage`, `get_temp` и `tm_start` отвечают `error: adc busy`, а `cap_start` не запускается и во время телеметрии.

>[!success] Должно получиться так
> ```c
> // cmd_cap_start(): аргументов не два или не числа — error: usage cap_start <N> <period_us>
> // N = 0, N > PLATFORM_CAPTURE_MAX или период меньше 10 мкс —
> //     error: N must be 1..2000, period_us at least 10
> // идёт телеметрия или platform не начал захват — error: adc busy
> // ответ capture: started, <N> samples, period <период> us
>
> // cmd_cap_dump(): захвата не было — error: no capture
> // строка capture: <N> samples, period <период> us, interval <мин>..<макс> us, handler <доля> %
> // коды строками cap: по 16
>
> // get_voltage, get_temp, tm_start: АЦП занят — error: adc busy
> ```

| Что нужно написать | Где это разбиралось |
| --- | --- |
| два числовых аргумента | `led_period`, [[п2.3.2 Задача светодиода#^intro\|п2.3.2]] |
| структура, которую заполняет функция | `device_get_info()`, [[п2.3.5 Данные вместо печати#^intro\|п2.3.5]] |
| `float` в ответе с одним знаком | `get_temp`, [[п3.1.2 Измерение температуры#^intro\|п3.1.2]] |

### 3. Сравнить захват с периодом 125 и 23 мкс

Соберите проект, запишите прошивку и захватите тысячу отсчётов с периодом 125 мкс, это 8 кГц, частота телефонии.

>[!success] Должно получиться так
> ```
> cap_start 1000 125
> capture: started, 1000 samples, period 125 us
> cap_dump
> capture: 1000 samples, period 125 us, interval 121..126 us, handler 1.6 %
> cap: 1165 1173 1171 1170 1169 1179 1172 1166 1160 1162 1152 1144 1134 1121 1107 1116
> ...
> ```

Интервалы гуляют на несколько микросекунд, обработчик занимает полтора процента времени ядра. Коды плавают, потому что вход GP26 пока никуда не подключён и ловит наводки. Для 8 кГц это терпимо. Теперь попробуйте частоту, близкую к 44,1 кГц.

>[!success] Должно получиться так
> ```
> cap_start 2000 23
> capture: started, 2000 samples, period 23 us
> cap_dump
> capture: 2000 samples, period 23 us, interval 4..42 us, handler 8.7 %
> ...
> ```

Посмотрите на три числа. Первое — сам период. Будильник ставится в целых микросекундах, а шаг 44,1 кГц равен 22,68 мкс. 23 мкс дают 43 478 отсчётов в секунду, на 1,4 % меньше, и запись прозвучит быстрее и выше. Второе — интервалы от 4 до 42 мкс при периоде 23. Ядро входит в обработчик не мгновенно, а когда освободится от другого прерывания, например обслуживания USB. Опоздавший вызов SDK догоняет следующими, и шаг рвётся. Третье — почти 9 % времени ядра только внутри обработчика, а с входом в прерывание и работой пула заметно больше. Всё это ядро платит за то, что умеет делать сам АЦП. Его делитель держит шаг с точностью до такта 48 МГц и не трогает ядро вовсе. Этим вы займётесь в следующем задании.
