Среди признаков удачной архитектуры в разделе [[т2.3.2 Признаки удачной архитектуры#^intro|Признаки удачной архитектуры]] было изменение одного решения в одном месте, и примером служил формат командной строки: если строку разбирает одно место, а обработчики получают готовые аргументы, смена формата не выходит за пределы этого места. Там же мы отметили, что в прошивке чаще всего меняется вид, в котором прибор обменивается данными с внешним миром. До сих пор приём строки, её разбор и выполнение команды были у нас одним куском кода, и этому признаку он не отвечал. Чтобы разделить такой код, нужно сначала записать, по каким правилам прибор обменивается командами, а затем решить, какой модуль отвечает за какое правило. Какие правила должен закрепить протокол прибора и где в прошивке реализуется каждое из них?
^intro

## Правила текстового протокола

Текст, который прибор и компьютер передают по каналу связи, сам решает две задачи разметки: перевод строки отмечает конец сообщения, а пробел отделяет одно слово от другого. Остальное текст не задаёт: какое слово считать именем команды, сколько аргументов допустимо, как отличить отказ от обычного ответа, как узнать, какие команды есть у прибора. Пока эти правила не записаны, их знает только код прошивки, и человек за терминалом или программа на компьютере узнают их пробами. Записанные правила обмена и составляют **протокол** (*англ. protocol*).

![[Протокол#^def]]

Протокол нашего прибора состоит из семи правил:

| № | Правило | Пример |
| --- | --- | --- |
| 1 | строка — одна команда, конец строки — символ `\r` или `\n` | `led_enable` |
| 2 | слова разделены пробелами: первое слово — имя команды, остальные — аргументы | `led_period 500`: имя `led_period`, аргумент `500` |
| 3 | в строке не больше 63 символов, у команды не больше четырёх аргументов; строку сверх предела прибор не выполняет | `error: command longer than 63 characters or 4 arguments` |
| 4 | прибор повторяет принятые символы и по Backspace стирает последний | — |
| 5 | ответ — одна или несколько строк текста | `led: blink, period 500 ms` |
| 6 | ответ об ошибке начинается с `error:` и подсказывает, что ввести | `error: usage led_period <period_ms>` |
| 7 | команда `help` перечисляет команды прибора с краткой справкой | `led_enable       turn led on` |

Три правила из таблицы определяют устройство кода, поэтому поясним их. Предел длины нужен потому, что принятую строку прошивка хранит в буфере постоянного размера, и символы сверх него теряются. Префикс `error:` позволяет отличить отказ от ответа, не зная заранее текста каждого сообщения. Это важно не только человеку: прибором может управлять и скрипт на **Python**, который раз в секунду отправляет команду и сохраняет ответ в файл, и такому скрипту достаточно проверить начало строки. Команда `help` позволяет узнать набор команд у самого прибора, не открывая исходный код прошивки, а значит, рядом с каждой командой прошивка должна хранить её краткое описание.

## Разделение протокола и API

Правила из таблицы относятся к двум разным предметам. Правила 1–4 описывают, как принять команду: где кончается строка, чем разделены слова, сколько в ней может быть символов. Правила 5–7 вместе с самим набором команд описывают, как прибор отвечает и что он умеет. Первые меняются вместе со способом обмена, вторые — вместе с функциями прибора. Чтобы каждое из этих решений менялось в одном месте, на пути команды стоят два модуля: протокол реализует приём и не знает ни одной команды, а модуль команд знает команды и не знает, как их приняли.

Протокол превращает принятые символы в имя команды и список аргументов. Похожую пару вы получали в программе на компьютере: функция `main` в **C** может принимать `int argc, char *argv[]` — число слов командной строки и массив указателей на сами слова, а в **Python** те же слова лежат в списке `sys.argv`. Строку `gcc main.c -o main` делит на слова командная оболочка, и программа не знает, как оболочка обращалась с пробелами и кавычками. Наш протокол отдаёт команду в таком же виде:

```c
// команда, принятая из одной строки
typedef struct
{
    const char *name;
    uint32_t argc;
    const char *argv[STDIO_TEXT_PROTOCOL_MAX_ARGS];

    // строка длиннее буфера или аргументов больше, чем помещается в argv:
    // команда принята не целиком, выполнять её нельзя
    bool truncated;
} command_t;
```

В отличие от `argv` в `main`, имя команды лежит в отдельном поле, а `argv[0]` — уже первый аргумент.

Набор команд, которые прибор выполняет по запросу снаружи, называют его **API** (*англ. Application Programming Interface*). Тот, кто пользуется API, знает имена команд, их аргументы и ответы, но не знает, как прошивка устроена внутри. Модуль, который хранит набор команд и выполняет их, так и называется — `api`.

![[API#^def]]

Протокол об `api` не знает ничего, а `api` знает о протоколе только тип `command_t`. Вызывать друг друга им незачем: команду из одного модуля в другой передаёт `main.c`. В суперцикле это три строки:

```c
// принятая строка становится командой, команда — действием прибора
const command_t *command = stdio_text_protocol_handle();
if (command != NULL)
{
    api_handle(command);
}
```

![[Путь команды.excalidraw|100%]]

Новая команда при таком делении не затрагивает протокол. А если команды начнут приходить в другой записи, например в двоичном виде от другого микроконтроллера, заменится протокол, а команды прибора останутся прежними.

## Приём строки протоколом

Символы протокол получает через стандартный ввод-вывод. Канал, USB или UART, выбирает настройка сборки, а код с `getchar()` и `printf()` от него не зависит ([[т1.3.6 Стандартный ввод-вывод в прошивке#^intro|Стандартный ввод-вывод в прошивке]]). Из SDK протоколу нужна одна функция — `getchar_timeout_us(0)`. Она возвращает символ, если он уже пришёл, и `PICO_ERROR_TIMEOUT`, если не пришёл, тогда как `getchar()` ждал бы символа сколько угодно ([[т2.2.4 Блокирующий и неблокирующий код#^intro|Блокирующий и неблокирующий код]]). Ждать протоколу нельзя: это задача из раздела [[т2.3.3 Программная задача#^intro|Программная задача]], и его обработчик `stdio_text_protocol_handle()` вызывается на каждой итерации суперцикла наравне с задачами светодиода и кнопки.

За один вызов обработчик обрабатывает не больше одного символа, и действие определяется самим символом:

| Принятый символ | Действие | Результат вызова |
| --- | --- | --- |
| символа нет | — | `NULL` |
| обычный символ, в буфере есть место | положить в буфер, повторить в канал | `NULL` |
| обычный символ, буфер полон | не сохранять, пометить строку как переполненную | `NULL` |
| Backspace, код `0x08` или `0x7F` | убрать из буфера последний символ, стереть его на экране | `NULL` |
| `\r` или `\n`, строка пуста | — | `NULL` |
| `\r` или `\n`, в строке есть символы | разделить строку на слова, очистить буфер | команда |

Принятый символ протокол повторяет в канал, чтобы в терминале было видно, что набрано: обычно терминал выводит на экран только то, что прислал прибор. Конец строки терминалы отмечают по-разному: одни присылают `\r`, другие `\n`, третьи оба символа подряд. Поэтому концом строки считается любой из них, а второй символ пары приходит уже к пустой строке и ничего не делает.

Backspace требует отдельного правила. Терминал отправляет каждую клавишу сразу после нажатия и исправить уже отправленный символ не может. Клавиша Backspace уходит в канал таким же символом, как буквы, — с кодом `0x08` или `0x7F`, в зависимости от терминала и его настроек. Если протокол не обработает этот символ, он ляжет в буфер: опечатка `uptimx`, исправленная на `uptime`, придёт как `uptimx`, код Backspace и `e`, и прибор ответит, что такой команды нет. Поэтому протокол сам убирает из буфера последний символ и печатает три символа `"\b \b"`: шаг курсора назад, пробел поверх стираемого символа и снова шаг назад. Так в буфере остаётся ровно то, что видно на экране. Терминалы, которые отправляют строку целиком по нажатию Enter, как монитор порта Arduino IDE, редактируют её у себя, и Backspace в канал не попадает.

Символ, для которого в буфере нет места, протокол не сохраняет и не повторяет, а запоминает, что строка принята не целиком. Backspace снимает эту пометку: на экране видны только символы из буфера, и после стирания строка снова совпадает с тем, что набрано.

## Деление строки на слова

Когда приходит конец строки, протокол делит её на имя команды и аргументы. Слова при этом не копируются: они остаются в буфере, а протокол записывает нулевой символ на место каждого пробела. Причина в том, как устроена строка в **C**. Строка — это последовательность символов, которая заканчивается нулевым символом `'\0'`; длина строки нигде не хранится, и функции вроде `strcmp()` и `printf()` читают символ за символом, пока не встретят ноль. Значит, если записать ноль сразу после слова, указатель на первую букву слова можно передать любой строковой функции, и она прочитает только это слово.

Деление выполняется одним проходом по буферу:

1. В конец принятой строки записывается нулевой символ.
2. Каждый пробел заменяется нулевым символом.
3. Символ, который не является пробелом, начинает слово, если он стоит первым в строке или перед ним стоит нулевой символ. Указатель на начало слова запоминается.
4. Первое слово становится именем команды, следующие — аргументами. Слово сверх четвёртого аргумента не сохраняется, а команда помечается как принятая не целиком.

Пробелы подряд превращаются в нули подряд, но слово начинается только на символе, который не пробел. Поэтому лишние пробелы в начале строки, в конце и между словами пустых слов не дают, а строка из одних пробелов не даёт ни одного слова, и протокол возвращает `NULL`.

![[Буфер строки протокола.excalidraw|100%]]

Из такого деления следует ограничение, которое должен знать каждый, кто получает команду. Имя и аргументы — указатели внутрь буфера протокола, а указатель хранит только адрес и не мешает изменить данные, на которые указывает. Следующий принятый символ протокол запишет в начало того же буфера, поверх имени команды. Поэтому команда действительна только до следующего вызова протокола, и это условие записано в заголовке рядом с функцией:

```c
// Читает один символ, не ожидая его. Когда строка закончена, возвращает
// команду, иначе NULL. Команда действительна до следующего вызова.
const command_t *stdio_text_protocol_handle(void);
```

`main.c` передаёт команду в `api` в той же итерации суперцикла, сразу после вызова протокола, и условие выполняется. Обработчик, которому аргумент понадобится позже, должен скопировать его или сразу перевести в число.

Остаётся строка, которая не поместилась: длиннее 63 символов или с аргументами сверх четырёх. Выполнять её нельзя: если бы у команды `led_period 50000` потерялись последние символы, прибор выполнил бы `led_period 50`, то есть другую команду. Отбросить её молча тоже нельзя: человек за терминалом не поймёт, почему прибор не ответил. Сообщение об ошибке протокол не печатает, потому что в [[т2.3.7 Границы модулей#^intro|прошлом разделе]] мы решили, что модули возвращают данные, а ответы печатает одно место. Поэтому протокол возвращает такую команду с полем `truncated`, равным `true`, а отказ печатает `api`.

## Выполнение команды в API

Модуль `api` получает от протокола готовую команду и находит, что с ней делать, по таблице команд. Таблицу «имя — обработчик» вы уже составляли в задании П2.1.2, где она заменила цепочку сравнений строк. Теперь у записи таблицы три поля, и каждое нужно для одного из правил протокола:

```c
// обработчик команды: получает имя и аргументы
typedef void (*api_callback_t)(const command_t *command);

// команда прибора: имя, справка для help и обработчик
typedef struct
{
    const char *name;
    const char *help;
    api_callback_t callback;
} api_command_t;
```

- `name` — имя, по которому команда ищется в таблице (правило 2);
- `help` — краткая справка, которую печатает команда `help` (правило 7);
- `callback` — обработчик, который выполняет команду и печатает ответ (правила 5 и 6).

В П2.1.2 обработчик не принимал параметров, и команду с аргументом вроде `led_period 1000` в таблицу было не положить. Теперь у всех обработчиков одна сигнатура: обработчик получает команду целиком и находит аргументы в `command->argv`, а обработчики команд без аргументов этот параметр не используют. Изменились и имена типов: в П2.1.2 тип `command_t` описывал запись таблицы, а здесь так называется принятая команда, а запись таблицы — `api_command_t`.

Функция `api_handle()` проверяет команду в постоянном порядке:

1. Команда помечена `truncated` — печатается сообщение об ошибке, команда не выполняется.
2. Имя команды — `help` — печатаются имена и справка всех команд таблицы.
3. Команда с таким именем есть в таблице — вызывается её обработчик.
4. Команды нет в таблице — печатается `error: unknown command '<имя>', try help`.

Команду `help` функция обрабатывает сама, а не через таблицу: такая команда нужна любому прибору, и печатает она содержимое самой таблицы. Шаги 3 и 4 — цикл по таблице:

```c
for (uint32_t i = 0; i < api_command_count; i++)
{
    if (strcmp(command->name, api_commands[i].name) == 0)
    {
        api_commands[i].callback(command);
        return;
    }
}

printf("error: unknown command '%s', try help\n", command->name);
```

Обработчик — [[Обратный вызов#^def|обратный вызов]] из раздела [[т2.1.7 Указатели на функции#^intro|Указатели на функции]]: `api_handle()` вызывает его через таблицу и знает о нём только сигнатуру. Сам обработчик проверяет аргументы, вызывает функции модулей и печатает ответ. Логики прибора и работы с железом в нём нет: светодиод включает задача светодиода, а обработчик передаёт ей команду и сообщает результат.

Код модуля `api` разделён на две части. Проверки из списка выше одинаковы для любого прибора и лежат в `api.c`. Обработчики и таблица описывают команды этого прибора и лежат в `api-callbacks.c`, в одном файле, чтобы новая команда добавлялась одной правкой: обработчик и строка таблицы. Обработчики определены со `static`: таблица видит их, потому что лежит в том же файле, а остальной прошивке они не видны. Таблицу и тип её записи `api.c` получает через внутренний заголовок `api-commands.h`, где таблица объявлена с `extern const`. Подключают его только два файла модуля, а остальной проект знает лишь `api.h` с функцией `api_handle()`. Сборка эту границу не проверяет: модуль `api` входит в библиотеку логики, и её папка открыта всем пользователям библиотеки, поэтому внутренний заголовок узнают по имени и комментарию в его начале.

## Разбор числового аргумента

Протокол отдаёт аргумент таким, каким его набрали, — строкой `"500"`. Что это число миллисекунд, знает только обработчик `led_period`, и перевести строку в число — его работа. Запись числа обработчик принимает при трёх условиях:

- запись начинается с цифры;
- после цифр в строке ничего нет;
- число помещается в `uint32_t`.

Если хотя бы одно условие нарушено, прибор отвечает отказом с подсказкой и период не меняет. Так должны заканчиваться `led_period` без аргумента, `led_period 5x`, `led_period -1` и `led_period 99999999999`.

Число из строки читает стандартная функция `strtoul()`. Через второй параметр она сообщает, где кончилось число, поэтому второе условие проверить легко. Первое и третье она не проверяет. Знак минус `strtoul()` принимает и обращает результат по правилам беззнакового типа: из `-1` получится 4294967295, и прибор согласится мигать с периодом почти в 50 суток. Число, которое не поместилось в тип, она заменяет наибольшим значением и сообщает об этом через переменную `errno`. Обе проверки приходится делать самим:

```c
// Число без знака из десятичной записи. false — в записи не только цифры
// или число не помещается в uint32_t.
static bool parse_u32(const char *text, uint32_t *value)
{
    // strtoul приняла бы и знак: из "-1" получилось бы 4294967295
    if (!isdigit((unsigned char)text[0]))
    {
        return false;
    }

    char *end;
    errno = 0;
    unsigned long number = strtoul(text, &end, 10);

    // после числа остались символы или число не поместилось
    if (*end != '\0' || errno == ERANGE || number > UINT32_MAX)
    {
        return false;
    }

    *value = (uint32_t)number;
    return true;
}
```

Функция проверяет только запись числа. Годится ли число как период, решает задача светодиода: в разделе о программном модуле мы договорились, что значение проверяет модуль, который владеет данными, и нулевой период задача не принимает, сообщая об отказе результатом. Обработчику остаётся ответить на оба отказа:

```c
static void cmd_led_period(const command_t *command)
{
    uint32_t period_ms;

    if (command->argc != 1 || !parse_u32(command->argv[0], &period_ms))
    {
        printf("error: usage led_period <period_ms>\n");
        return;
    }

    // годится ли такой период, решает задача светодиода
    if (!led_task_set_period_ms(period_ms))
    {
        printf("error: period_ms must be greater than 0\n");
        return;
    }

    // ответ: состояние и период светодиода
    print_led_state();
}
```

Разобрать число можно было бы и одной строкой `sscanf()`, но функция форматного ввода разбирает любой формат и приносит в образ весь этот код. Цену удобной библиотечной функции, как и в занятии 2.1, показывает размер образа.

Модуль 2 начался с того, как прошивка устроена в памяти, продолжился временем как ресурсом прибора и закончился устройством проекта. Итог модуля — шаблон, в котором у каждого знания есть своё место, и новая периферия встаёт в него по той же схеме: выводы и запуск блока — в `platform`, общий для приборов код — библиотека в `libs/`, поведение — задача в `logic/`, управление снаружи — команда в `api`. Саму внутреннюю периферию RP2040 разберём в модуле 3.
