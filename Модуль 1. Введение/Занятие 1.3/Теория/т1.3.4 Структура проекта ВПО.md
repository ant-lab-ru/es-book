В прошлом разделе мы проследили, как набор инструментов компиляции превращает исходный код в прошивку, и всё это время говорили о входе конвейера обобщённо — «исходный код проекта». Пора посмотреть на него вблизи. Проект ВПО — это не один файл с кодом, а набор файлов с определённой структурой, и код в нём устроен не так, как программы, которые вы писали раньше. Разберём и то и другое на примере знакомого проекта `101-blink`.

## Из чего состоит проект ВПО

Откройте папку `101-blink`, которую вы создали на занятии 1.1, и посмотрите, что в ней лежит. Файлов немного, но написали вы далеко не все: часть скопировали из SDK готовыми, часть появилась сама при сборке. Разделить их удобно как раз по этому признаку — что вы пишете сами, что берёте готовым и что порождается инструментами.

| Файл или папка | Назначение | Откуда берётся |
| -------------- | ---------- | -------------- |
| `main.c` | код программы — то, ради чего проект существует | пишете сами |
| `CMakeLists.txt` | описание сборки: какие файлы компилировать и какие библиотеки SDK подключить | пишете сами |
| `.gitignore` | перечень того, что не хранить в репозитории | пишете сами |
| `pico_sdk_import.cmake` | вспомогательный сценарий: находит SDK на диске | копируется из SDK |
| `memmap_default.ld` | скрипт компоновщика: какие области памяти есть у RP2040 | копируется из SDK |
| `build/` | всё, что порождает сборка: `.o`, `.elf`, `.uf2`, `.map` | появляется при сборке |

В проекте побольше первая группа разрастётся: `main.c` перестанет вмещать всю программу, и код разойдётся по нескольким файлам `.c` и `.h` — отдельно драйвер датчика, отдельно разбор команд, отдельно прикладная логика. Как проводить эти границы, мы разберём в модуле 2. Остальные две группы от размера проекта почти не зависят: заимствованных файлов как было два, так и останется, а в `build` просто станет больше объектных файлов.

![[SDK (Набор инструментов разработки)#^def]]

Pico SDK вы склонировали на занятии 1.1 один раз и в отдельную папку, а путь к ней записали в переменную среды `PICO_SDK_PATH`. По этой переменной сценарий `pico_sdk_import.cmake` и находит SDK при конфигурации сборки. Внутрь проекта **SDK** не копируется — он один на все ваши проекты, и это разумно: вместе с подмодулями он занимает больше сотни мегабайт, а обновляют его отдельно от прикладного кода.

Отсюда важное свойство проекта ВПО: он описывает, из чего собрать прошивку, но не содержит всего, из чего она собирается. Ваши файлы — это код приложения и инструкция по сборке; остальное подтягивается со стороны. Значит, для повторной сборки проекта мало скопировать его папку — нужны ещё SDK и toolchain на машине, где сборка идёт. Об этом стоит помнить, когда вы передаёте проект другому человеку.

## Скелет исходного кода: инициализация и суперцикл

Смысл программы содержится в одном файле — `main.c`. В `blink` он умещается в полтора десятка строк, поэтому посмотрим на него целиком:

```c
// объявления функций SDK: gpio_*, sleep_ms
#include "pico/stdlib.h"

int main(void)
{
    // подключить вывод к блоку GPIO
    gpio_init(PICO_DEFAULT_LED_PIN);
    // настроить вывод на выход
    gpio_set_dir(PICO_DEFAULT_LED_PIN, GPIO_OUT);

    // суперцикл: повторяется, пока подано питание
    while (true) {
        // высокий уровень — светодиод горит полсекунды
        gpio_put(PICO_DEFAULT_LED_PIN, 1);
        sleep_ms(500);

        // низкий уровень — светодиод погас на полсекунды
        gpio_put(PICO_DEFAULT_LED_PIN, 0);
        sleep_ms(500);
    }
}
```

Файл распадается на три части, и в таком же порядке устроено большинство программ микроконтроллера. *Первая* — единственная строка `#include`, которой в текст втягивается содержимое чужого файла.

![[Заголовочный файл#^def]]

Заголовочный файл `pico/stdlib.h` приносит в `main.c` объявления функций SDK; без него компилятор остановится на вызове `gpio_init()`, потому что описания такой функции в файле не окажется. Оттуда же берётся `PICO_DEFAULT_LED_PIN` — макрос, который для Raspberry Pi Pico равен 25, номеру вывода со встроенным светодиодом. Обратите внимание, что в коде нет числа 25: SDK описывает не только чип, но и плату, и тот же самый `main.c` соберётся под другую плату семейства, где светодиод подключён иначе.

*Вторая часть* — инициализация. Два вызова переводят вывод в режим GPIO и задают ему направление «выход»; выполняются они один раз, до начала полезной работы. Это тот самый первый пункт из списка обязанностей ВПО, который мы составили в начале занятия: привести аппаратуру в рабочее состояние. В `blink` настраивать почти нечего, но в проектах занятия 1.3 к этим строкам добавится ещё одна — `stdio_init_all()`, включающая вывод текста через USB.

*Третья часть* — всё остальное, и оно заключено в бесконечный цикл (суперцикл). Такой цикл в программе микроконтроллера необходим, и причина нам уже известна: программе некуда завершаться. На Raspberry Pi скрипт с `while True` вы прерывали по Ctrl+C, и операционная система прибирала за ним; здесь прерывать некому и прибирать некому, а дошедшая до конца программа означает остановившийся прибор. У такого цикла есть собственное название.

![[Суперцикл#^def]]

Пока достаточно относиться к суперциклу буквально: это главный бесконечный цикл, внутри которого повторяется вся работа программы. В `blink` работы немного — зажечь, подождать, погасить, подождать, — но общий принцип виден уже здесь: настройка выполняется однократно, полезные действия повторяются, пока на плату подано питание. Вместе с точкой входа `main()` это и есть скелет, на который нанизывается любая программа микроконтроллера.

Стоит сразу отметить одну особенность этого кода. Вызов `sleep_ms(500)` останавливает ядро на полсекунды: всё это время оно не выполняет ничего другого. Для мигания одним светодиодом это незаметно, но, как только дел станет больше одного — читать кнопку, принимать команды из терминала, обновлять индикатор, — пауза внутри цикла начнёт мешать: нажатие кнопки, случившееся во время задержки, будет обработано с опозданием или потеряно. Как строить суперцикл, чтобы ни одно дело не ждало другого, — тема занятия 2.3, там мы к этому вернёмся всерьёз. Но простейший случай встретится вам уже в заданиях этого занятия: светодиодом будут управлять и кнопка, и команды из терминала, и ни один из двух источников не должен заставлять другой себя ждать.

## Как подключается SDK

От всего SDK в `main.c` видна одна строка `#include`. Но чтобы вызов `gpio_put()` превратился в машинные команды, которые лягут в образ, одного `#include` мало — и понять почему проще всего через этапы сборки из прошлого раздела.

Препроцессор подставляет в текст содержимое заголовочного файла, и оттуда компилятор берёт объявление функции: как она называется, сколько принимает аргументов и какого типа. Этого хватает, чтобы правильно собрать вызов, но не хватает, чтобы его выполнить: сам код `gpio_put()` лежит в другом файле SDK и компилируется отдельно. Найти нужный объектный файл и связать с ним место вызова должен компоновщик — а для этого ему надо сообщить, какие библиотеки SDK участвуют в сборке. Это и делает `CMakeLists.txt`:

```cmake
cmake_minimum_required(VERSION 3.13)

# найти SDK на диске по PICO_SDK_PATH
include(pico_sdk_import.cmake)

# имя проекта и используемые в нём языки
project(blink C CXX ASM)

# подключить SDK к проекту
pico_sdk_init()

# цель сборки blink собирается из main.c
add_executable(blink main.c)

# взять карту памяти RP2040 из скрипта компоновщика
pico_set_linker_script(blink ${CMAKE_CURRENT_LIST_DIR}/memmap_default.ld)

# библиотеки SDK, нужные проекту
target_link_libraries(blink pico_stdlib)

# получить дополнительно .uf2, .bin, .hex, .map, .dis
pico_add_extra_outputs(blink)
```

Здесь стоит задержаться на трёх строках. `add_executable` объявляет цель сборки и перечисляет исходные файлы, из которых она собирается; имя цели заодно определяет имена файлов в папке `build` — отсюда и `blink.elf` с `blink.uf2`, которые мы разбирали в прошлом разделе, хотя папка проекта называется `101-blink`. `pico_add_extra_outputs` отвечает за то, что кроме `.elf` появляются остальные форматы образа: без этой строки компоновка выполнится, а копировать на плату будет нечего. Главная же здесь — `target_link_libraries`: именно она перечисляет библиотеки SDK, которые войдут в сборку. `pico_stdlib` — сборная библиотека с самым необходимым: GPIO, задержки, тактирование, стандартный ввод-вывод.

Получается, что SDK подключается в двух местах: в системе сборки и в исходном коде, и обе строки нужны вместе. Правило простое: на каждую группу возможностей SDK приходится свой заголовочный файл в коде и своя библиотека в CMake.

![[Подключение SDK.excalidraw|100%]]

| Что нужно проекту | Строка в `main.c` | Библиотека в `CMakeLists.txt` |
| ----------------- | ----------------- | ----------------------------- |
| базовые функции: GPIO, задержки, ввод-вывод | `#include "pico/stdlib.h"` | `pico_stdlib` |
| аппаратный SPI | `#include "hardware/spi.h"` | `hardware_spi` |
| АЦП | `#include "hardware/adc.h"` | `hardware_adc` |

Пары из этой таблицы понадобятся вам в модулях 3 и 4, когда дойдёт дело до периферии. Пока важно запомнить сам принцип: добавили в код обращение к новой части SDK — допишите библиотеку в `target_link_libraries`, иначе сборка остановится.

>[!NOTE] Из практики
>Забыть одну из двух строк — самая частая ошибка при подключении новой библиотеки, и по сообщению об ошибке видно, какую именно. Если забыт `#include`, компилятору не встретится объявление, и сборка остановится на первом же вызове: `implicit declaration of function 'adc_init'`. Если забыта библиотека в `target_link_libraries`, ошибка приходит раньше и выглядит неожиданно: `fatal error: hardware/adc.h: No such file or directory`. Дело в том, что библиотека SDK приносит проекту не только код, но и путь к своим заголовочным файлам, — без неё препроцессору просто негде взять `adc.h`, и до вызова дело не доходит. Отсюда правило: не найден заголовочный файл — правьте `CMakeLists.txt`, не найдено объявление — правьте `main.c`.

Заметьте, чего в проекте `blink` нет вовсе: ни одного обращения к регистрам блока GPIO, хотя в конечном счёте вся работа сводится именно к ним. Разбираться, какой бит какого регистра переключает направление вывода, вам не пришлось — это сделал код SDK, вызванный из `gpio_set_dir()`. В обмен на удобство вы согласились не видеть, что происходит на уровне регистров, и это осознанный выбор уровня, на котором пишется программа.

## Свои файлы в сборке

Пока весь код проекта помещается в `main.c`, `CMakeLists.txt` можно больше не трогать. Но уже в заданиях этого занятия часть кода придётся вынести наружу — работа со светодиодом обрастёт функциями и станет мешаться под ногами у остальной логики, — и тогда о новых файлах надо будет сообщить системе сборки. Где именно проводить границы между файлами, мы обсудим в модуле 2; сейчас разберём механику, которая от выбора границ не зависит.

Модуль на **C** — это пара файлов. В заголовочном файле лежат объявления: имена функций с типами аргументов, константы, макросы — всё, что нужно знать тому, кто модулем пользуется. В файле `.c` лежит код этих функций и внутренние переменные — то, что пользователю модуля знать не обязательно. Пусть проект обзавёлся модулем `led` из файлов `led/led.h` и `led/led.c`: в заголовочном файле объявлены `led_init()` и `led_toggle()`, в `led.c` — их код и номер вывода, к которому подключён светодиод. Тогда в `main.c` появится строка

```c
#include "led.h"
```

— в двойных кавычках, а не в угловых скобках: так препроцессор ищет файл сначала среди файлов проекта и лишь потом среди системных путей.

Одного `#include` снова не хватит, и по той же причине, что и с SDK. Препроцессор подставит объявления, компилятор соберёт вызов — а кода вызываемой функции в сборке не окажется: `led.c` компилируется отдельно, и о нём надо сказать явно. В `CMakeLists.txt` для этого меняются две строки:

```cmake
# теперь цель собирается из двух исходных файлов
add_executable(blink main.c led/led.c)

# где искать заголовочные файлы проекта
target_include_directories(blink PRIVATE led)
```

`add_executable` перечисляет исходные файлы цели: на каждый из них компилятор сделает свой объектный файл, а компоновщик соберёт их вместе. Заголовочные файлы в этом списке не упоминаются — сами по себе они не компилируются и попадают в сборку через `#include`. Правило простое: файл `.c` — в `add_executable`, папку с файлами `.h` — в `target_include_directories`. Слово `PRIVATE` означает, что путь нужен только этой цели и дальше не передаётся; для прикладного проекта так и надо.

Диагностика здесь ровно та же, что с библиотеками SDK, и правило из врезки выше работает без изменений. Забыт путь — препроцессору негде взять заголовочный файл: `fatal error: led.h: No such file or directory`. Забыт исходный файл в `add_executable` — все файлы скомпилируются успешно, а споткнётся уже компоновщик, которому нечего связать с местом вызова: `undefined reference to 'led_toggle'`.

## Проект в системе версионирования

Проект собран и работает — осталось решить, что из него хранить. Ответ мы уже подготовили в прошлом разделе: в [[Система контроля версий#^def|систему контроля версий]] кладут то, что нельзя восстановить, и не кладут то, что выводится из хранимого. По этому признаку папка `build` в репозиторий не попадает: удалите её, повторите `cmake` и `make` — и получите ровно те же файлы. Именно поэтому на занятии 1.1 вы завели в проекте `.gitignore` и первой же строкой внесли туда `build`.

Тот же признак объясняет и остальное. Сам SDK в репозитории проекта не хранят: у него собственный репозиторий и собственная история, а вы им только пользуетесь. А вот `pico_sdk_import.cmake` и `memmap_default.ld` хранить нужно, хотя писали их не вы: эти файлы лежат внутри проекта, и без них он не соберётся ни у вас на другой машине, ни у коллеги.

Стоит понимать, зачем всё это нужно именно для ВПО. Обычную программу на компьютере легко обновить: пользователь скачивает новую версию, старая перестаёт существовать. Прибор с прошивкой уезжает к заказчику и работает годами, причём приборов этих десятки, и версии прошивки у них разные. Когда через год приходит сообщение «устройство иногда перестаёт отвечать», первый вопрос будет не «что в коде», а «какая там версия» — и разбираться придётся не с текущим состоянием исходников, а ровно с тем, из которого была собрана прошивка того прибора. Репозиторий с историей коммитов — единственное, что позволяет к этому состоянию вернуться, пересобрать его и воспроизвести ошибку.

Отсюда следует практика, с которой вы столкнётесь уже в заданиях этого занятия: сборку помечают версией, а прибор эту версию сообщает — например, выводит при запуске в терминал. Иначе связь между работающим устройством и точкой в истории репозитория теряется, и все преимущества версионирования вместе с ней. Как заставить прошивку рассказать о себе, разберём в конце занятия; пункт «выполнить `commit` проекта» в конце каждого практического задания курса — из той же логики, а не формальность.

## Итог

Проект ВПО — это ваши исходные файлы, описание сборки в `CMakeLists.txt` и пара заимствованных из SDK служебных файлов; сам SDK лежит снаружи и общий для всех проектов, а папка `build` целиком порождается инструментами. Код внутри `main.c` устроен одинаково почти всегда: подключение заголовочных файлов, однократная инициализация аппаратуры и суперцикл, в котором до отключения питания повторяется полезная работа. SDK при этом подключается с двух сторон — заголовочным файлом для компилятора и библиотекой в CMake для компоновщика; собственные файлы проекта подключаются так же в двух местах: директивой `#include` в коде и строками `add_executable` и `target_include_directories` в описании сборки.

Прошивка собрана и записана, светодиод мигает. Но светодиод сообщает ровно один бит: горит или не горит, — а обратно, из-за стола к прибору, не идёт вообще ничего. Как только программа станет сложнее мигания, этого перестанет хватать: понадобится и получать от неё текст, и отдавать ей команды. Ни экрана, ни клавиатуры у микроконтроллера нет, зато есть кабель USB, которым плата подключена к компьютеру. Как по этому кабелю устроить двусторонний обмен текстом — тема следующего раздела.
