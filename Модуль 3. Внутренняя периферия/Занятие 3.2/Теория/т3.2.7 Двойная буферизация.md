В прошлом разделе канал DMA захватил блок отсчётов в память, а ядро всё это время было свободно. Но блок рано или поздно заканчивается, а запись звука должна идти, пока её не остановят. И заполненные данные надо ещё успеть отправить на компьютер. Как принимать отсчёты без единого разрыва?

## Два буфера вместо одного

Блок фиксированной длины рекордеру не подходит, ему нужен непрерывный поток. Попробуем растянуть захват блока. Канал заполнил буфер, ядро отправляет его на компьютер, а затем перезапускает канал. Но отправка длится не нулевое время, и отсчёты, пришедшие за это время, пропадут. Можно и не останавливать канал, а сразу запустить его заново в тот же буфер. Тогда новые отсчёты затрут те, которые ядро ещё не успело отправить. Одного буфера на непрерывный поток не хватает.

Для подобных задач люди придумали каноничное решение — завести два буфера и работать с ними по очереди. Такой приём называют **двойной буферизацией**.

![[Двойная буферизация#^def]]

Пока DMA заполняет первый буфер, ядро отправляет второй, заполненный раньше. Затем они меняются ролями. На RP2040 для этого берут два канала и связывают их цепочкой. В регистре `CTRL` у каждого канала есть поле `CHAIN_TO`, номер канала, который запустится, когда этот закончит ([[RP2040 Datasheet.pdf#page=95|раздел «2.5.2.2. Chaining»]]). Канал A пишет в первый буфер и по окончании запускает канал B, канал B пишет во второй и запускает A. Запуск по цепочке аппаратный, поэтому следующий отсчёт сразу попадает в другой буфер, и ни один не теряется.

## Обслуживание буферов

Каналы переключаются сами, но без ядра поток не проживёт и двух кругов. Закончив передачи, канал оставляет адрес записи на конце своего буфера, и при следующем запуске он стал бы писать за его край. К тому же кто-то должен узнать, что буфер заполнен, и отправить его.

Адрес записи возвращает к началу буфера обработчик прерывания. Он же отмечает, что буфер заполнен, а отправляет его задача в суперцикле. Соберём эту схему целиком, она пригодится везде, где нужен непрерывный поток данных. В ней четыре части: данные, запуск каналов, обработчик и задача суперцикла.

### Данные

```c
#include "hardware/adc.h"
#include "hardware/dma.h"
#include "hardware/irq.h"

// номера двух каналов DMA
static int channel[2];

// два буфера, каждый на N отсчётов
static uint16_t buffer[2][N];

// буфер заполнен и ждёт отправки
static volatile bool buffer_ready[2];

// сколько раз суперцикл не успел отправить буфер
static volatile uint32_t overruns;
```

В Pico SDK канал DMA обозначается номером, числом от 0 до 11, так же как вывод GPIO обозначается номером вывода. Поэтому массив `channel` хранит обычные числа, а функции SDK вида `dma_channel_…` принимают такое число первым аргументом. В нашем случае у каналов A и B индексы в статических массивах будут 0 и 1 соответственно. У канала с индексом `i` свой номер аппаратного канала DMA `channel[i]`, буфер `buffer[i]` и свой флаг заполненности буфера `buffer_ready[i]`.

### Запуск каналов DMA

```c
void stream_start(void)
{
    // АЦП настроен, как в примере с блоком
    channel[0] = dma_claim_unused_channel(true);
    channel[1] = dma_claim_unused_channel(true);

    for (int i = 0; i < 2; i++)
    {
        dma_channel_config cfg = dma_channel_get_default_config(channel[i]);
        channel_config_set_transfer_data_size(&cfg, DMA_SIZE_16);
        channel_config_set_read_increment(&cfg, false);
        channel_config_set_write_increment(&cfg, true);
        channel_config_set_dreq(&cfg, DREQ_ADC);

        // номер следующего канала в цепочке
        int next_channel = channel[(i + 1) % 2];

        // по окончании запустить следующий канал
        channel_config_set_chain_to(&cfg, next_channel);

        // куда, откуда, сколько, false — пока не запускать
        dma_channel_configure(channel[i], &cfg, buffer[i], &adc_hw->fifo, N, false);

        // по окончании выставлять запрос DMA_IRQ_0
        dma_channel_set_irq0_enabled(channel[i], true);
    }

    irq_set_exclusive_handler(DMA_IRQ_0, on_dma);
    irq_set_enabled(DMA_IRQ_0, true);

    // первый канал запускаем сами, дальше работает цепочка
    dma_channel_start(channel[0]);
    adc_run(true);
}
```

Номера каналов выдаёт функция `dma_claim_unused_channel()`. Она занимает свободный канал и возвращает его номер, а аргумент `true` просит остановить прошивку с ошибкой, если свободных каналов нет. Каждый вызов занимает новые каналы, поэтому `stream_start()` вызывают один раз.

Настройка канала повторяет захват блока из прошлого раздела. Новое в ней вот что.

- `next_channel` хранит номер канала, который запустится следующим. Индекс этого канала даёт выражение `(i + 1) % 2`. Оператор `%` берёт остаток от деления, поэтому из 0 получается 1, а из 1 получается 0. Так каналы замыкаются в круг.
- `channel_config_set_chain_to()` записывает этот номер в поле `CHAIN_TO`.
- `dma_channel_configure()` получает `false`, потому что канал не должен стартовать сразу. Первый канал запускает `dma_channel_start()` в конце функции, второй запустит цепочка.
- `dma_channel_set_irq0_enabled()` разрешает каналу выставлять запрос `DMA_IRQ_0`.

Как мы говорили в разделе [[т3.2.4 Прерывания#^intro|о прерываниях]], запрос разрешают в двух местах. В модуле это делает `dma_channel_set_irq0_enabled()`, в контроллере прерываний `irq_set_enabled()`. Между ними `irq_set_exclusive_handler()` назначает обработчиком функцию `on_dma()`. В файле она должна быть описана выше `stream_start()`, иначе компилятор её не найдёт.

### Обработчик прерывания DMA

Ядро вызывает `on_dma()`, когда любой из каналов заполнил буфер. Запрос `DMA_IRQ_0` общий для обоих каналов, поэтому обработчик проверяет каждый.

```c
static void on_dma(void)
{
    for (int i = 0; i < 2; i++)
    {
        if (dma_channel_get_irq0_status(channel[i]))
        {
            dma_channel_acknowledge_irq0(channel[i]);
            dma_channel_set_write_addr(channel[i], buffer[i], false);

            // в следующий буфер уже идёт запись, а его ещё не отправили
            if (buffer_ready[(i + 1) % 2])
            {
                overruns++;
            }
            buffer_ready[i] = true;
        }
    }
}
```

- `dma_channel_get_irq0_status()` отвечает, выставил ли канал с этим номером запрос. Контроллер DMA держит по биту на канал в регистре `INTS0`, и функция проверяет нужный бит.
- `dma_channel_acknowledge_irq0()` сбрасывает этот бит. Как и у таймера, без сброса ядро сразу после возврата снова вошло бы в обработчик.
- `dma_channel_set_write_addr()` записывает адрес начала буфера в регистр `WRITE_ADDR` канала. Последний аргумент `false` означает, что запускать канал не нужно, это сделает цепочка. Число передач перезаписывать тоже не нужно, канал сам берёт его заново при каждом запуске ([[RP2040 Datasheet.pdf#page=93|раздел «2.5.1.2. Transfer Count»]]).
- `buffer_ready[i] = true` отмечает, что буфер готов к отправке.

### Задача суперцикла

```c
// какой буфер отправлять следующим
static int next_buffer;

void stream_task_handle(void)
{
    if (buffer_ready[next_buffer])
    {
        send_samples(buffer[next_buffer], N);
        buffer_ready[next_buffer] = false;
        next_buffer = (next_buffer + 1) % 2;
    }
}
```

Это знакомая схема с флагом из раздела [[т3.2.5 Обработчик прерывания#^intro|об обработчике прерывания]]. Буферы заполняются по очереди, поэтому и отправляются по очереди, и `next_buffer` запоминает, чей черёд. Как устроена отправка в `send_samples()`, разберём в следующем разделе.

### Переполнение

Флаг `buffer_ready[i]` помогает следить, успевает ли суперцикл. Двойная буферизация работает при одном условии — отправка буфера должна закончиться раньше, чем DMA заполнит другой и вернётся к этому. Задача опускает флаг, только когда отправила буфер. Если канал закончил, а флаг следующего буфера всё ещё поднят, значит, в этот буфер уже пишет следующий канал, хотя суперцикл не успел его отправить, и отсчёты затираются. Такое событие называют переполнением. Обработчик считает переполнения в `overruns`, и мы узнаём о потере, а не теряем данные молча.

## Размер буфера

Сколько отсчётов класть в буфер? Это то же правило, что для восьми отсчётов в буфере АЦП из раздела о режимах работы АЦП, только в другом масштабе. Время заполнения буфера сравнивают с худшим временем, за которое суперцикл успевает его забрать. Буфер на 512 отсчётов заполняется за 11,6 мс. За это время задача должна дождаться своей очереди в суперцикле и отправить 1 КБ в порт. Худшая итерация нашего прибора с расчётом π укладывается в полмиллисекунды, а отправка килобайта по USB занимает порядка миллисекунды, так что запас многократный.

Буфер побольше даёт больший запас, но занимает больше памяти и увеличивает задержку, с которой звук попадает на компьютер. Буфер поменьше заставляет ядро входить в обработчик и отправлять кадры чаще. 512 отсчётов, два раза по килобайту памяти и 86 прерываний в секунду — разумная середина для рекордера. Сравните с 44 100 прерываниями, если бы ядро забирало каждый отсчёт само.

Теперь работа рекордера поделена так, как требовал бюджет из раздела [[т3.2.1 Цифровой звук#^intro|о цифровом звуке]]. Время держит делитель АЦП, отсчёты в память переносит DMA, а ядро 86 раз в секунду получает готовый килобайт. Осталось отправить его на компьютер. До сих пор прибор передавал только текст, а здесь нужно передать именно числа, причём так, чтобы скрипт на компьютере мог заметить потерю. Как это сделать, разберём в следующем разделе.
