Это приложение к разделу [[т2.1.3 Линкер-скрипт#^intro|«Линкер-скрипт»]]. Там мы научились читать блоки `MEMORY` и `SECTIONS` в собранном и упрощённом виде и брать символы линкера в программу. Здесь разберём настоящий текст скрипта из Pico SDK 2.3.0: как он собран из фрагментов, откуда берутся числа регионов, что делает каждая секция и каждое служебное слово, какие символы скрипт оставляет коду и как SDK позволяет всё это переопределить. Материал не нужен для выполнения заданий занятия 2.1 — он для тех, кто хочет открыть любой фрагмент из папки `script_include` и понять его без пропусков.
^intro

## Как собран скрипт

Файл `memmap_default.ld`, который лежит в проекте, состоит из одной рабочей строки и комментария:

```text
INCLUDE "memmap_default.incl"
```

Комментарий под ней — дерево включений, сгенерированное скриптами SDK. Сами фрагменты лежат в двух папках: общие для RP2040 и RP2350 — в `src/rp2_common/pico_standard_link/script_include/`, особенные для RP2040 — в `src/rp2040/pico_platform/script_include/`. Обе папки SDK передаёт компоновщику ключами `-L` при сборке любого проекта, поэтому `INCLUDE` находит фрагмент по короткому имени. Первый включённый файл, `memmap_default.incl`, задаёт весь порядок:

```text
INCLUDE "set_memory_locations.incl"

INCLUDE "memory_flash.incl"
INCLUDE "memory_psram.incl"
INCLUDE "memory_xip_ram.incl"
INCLUDE "memory_ram.incl"
INCLUDE "memory_scratch.incl"
INCLUDE "memory_generated.incl"
INCLUDE "memory_extra.incl"

INCLUDE "memory_aliases_flash.incl"

ENTRY(_entry_point)

INCLUDE "sections_default.incl"
```

Порядок здесь тот же, что в любом линкер-скрипте: сначала числа и регионы, затем точка входа, затем секции. Директива `ENTRY` называет символ, с которого отладчик начинает исполнение при загрузке `.elf`; для Boot ROM она не имеет значения — тот входит в образ по таблице векторов. Файл `sections_default.incl` в свою очередь включает два десятка фрагментов по одной-две секции в каждом, чередуя их с пустыми файлами-заглушками вида `section_extra_post_text.incl`. Заглушки существуют ради переопределения: функция CMake `pico_add_linker_script_override_path()` добавляет папку проекта в список путей поиска раньше папок SDK, и любой фрагмент с тем же именем, положенный в эту папку, подменяет штатный. Так в скрипт можно добавить регион или секцию, не копируя и не правя весь файл. Файлы `*_generated_*.incl` оставлены для самого SDK и переопределению не подлежат, о чём в них написано прямо.

Рядом с `memmap_default.ld` лежат ещё три скрипта верхнего уровня: `memmap_copy_to_ram.ld` копирует при запуске в ОЗУ весь код, а не только помеченный; `memmap_no_flash.ld` собирает образ, который целиком живёт в ОЗУ и загружается отладчиком; `memmap_blocked_ram.ld` переносит регион `RAM` на адрес `0x21000000`, где та же SRAM видна не чередующимися, а сплошными банками. Все они собраны из тех же фрагментов, отличаются набором включений и псевдонимами регионов.

## Откуда берутся числа регионов

Для RP2040 числа лежат в файле `default_locations.ld`, который SDK передаёт компоновщику отдельным ключом `--script` ещё до основного скрипта:

```text
RAM_ORIGIN_DEFAULT = 0x20000000;
RAM_LENGTH_DEFAULT = 256k;
SCRATCH_X_ORIGIN_DEFAULT = 0x20040000;
SCRATCH_X_LENGTH_DEFAULT = 4k;
SCRATCH_Y_ORIGIN_DEFAULT = 0x20041000;
SCRATCH_Y_LENGTH_DEFAULT = 4k;
XIP_RAM_ORIGIN_DEFAULT = 0x15000000;
XIP_RAM_LENGTH_DEFAULT = 16k;
```

Фрагмент `set_memory_locations.incl` переносит их в рабочие имена без суффикса, и делает это дважды одинаковым по смыслу способом:

```text
PROVIDE( RAM_ORIGIN = RAM_ORIGIN_DEFAULT);
RAM_ORIGIN = DEFINED(RAM_ORIGIN) ? RAM_ORIGIN : RAM_ORIGIN_DEFAULT;
```

Обе строки означают одно: если символ `RAM_ORIGIN` уже определён, оставить его, иначе взять значение по умолчанию. Двойная запись — обход ошибок в разных версиях GNU ld и LLVM, о чём говорит комментарий в самом файле. Ради этой развилки всё и затеяно: функция CMake `pico_set_linker_script_var()` передаёт компоновщику ключ `--defsym`, которым можно задать `RAM_ORIGIN`, `RAM_LENGTH` и остальные имена из проекта, не трогая ни одного файла скрипта. Дальше фрагменты `memory_ram.incl`, `memory_scratch.incl` и `memory_xip_ram.incl` объявляют регионы через эти имена:

```text
MEMORY
{
    RAM(rwx) : ORIGIN =  RAM_ORIGIN, LENGTH = RAM_LENGTH
}
```

Блоков `MEMORY` в скрипте оказывается несколько, и это допустимо: компоновщик складывает регионы из всех блоков в один список. Флеш объявлена особо. Фрагмент `memory_flash.incl` включает файл `pico_flash_region.ld`, которого в исходниках SDK нет: CMake создаёт его в папке `build` из шаблона, подставляя константу `PICO_FLASH_SIZE_BYTES` из заголовка платы:

```text
FLASH(rx) : ORIGIN = 0x10000000, LENGTH = (2 * 1024 * 1024)
```

Регион `XIP_RAM` на 16 КБ по адресу `0x15000000` — память кэша [[XIP#^def|XIP]]. Если кэш отключить, эти 16 КБ читаются и пишутся как обычная SRAM, и SDK держит для них регион и секцию `.xip_ram` на случай, если проект этим воспользуется; в сборке по умолчанию секция пуста. Фрагменты `memory_psram.incl` и `sections_psram.incl` для RP2040 состоят из одного комментария: внешней PSRAM у этого чипа нет, а файлы нужны, чтобы общий порядок включений совпадал с RP2350.

Последний файл из группы `memory_*` — `memory_aliases_flash.incl`:

```text
REGION_ALIAS("TEXT_STORE", FLASH);
REGION_ALIAS("RAM_STORE", FLASH);
REGION_ALIAS("SCRATCH_X_STORE", FLASH);
REGION_ALIAS("SCRATCH_Y_STORE", FLASH);
```

`REGION_ALIAS` даёт региону второе имя. Секции ниже пишутся не «хранить во `FLASH`», а «хранить в `RAM_STORE`», и в варианте `copy_to_ram` или `no_flash` достаточно подменить один файл псевдонимов, чтобы те же секции хранились в другом месте. Результат чтения всей группы можно увидеть в начале файла `.map`, в разделе `Memory Configuration`:

```text
Name             Origin             Length             Attributes
FLASH            0x10000000         0x00200000         xr
XIP_RAM          0x15000000         0x00004000         xrw
RAM              0x20000000         0x00040000         xrw
SCRATCH_X        0x20040000         0x00001000         xrw
SCRATCH_Y        0x20041000         0x00001000         xrw
```

## Секции во флеш

Порядок секций задаёт `sections_default_text.incl` из папки RP2040: он ставит `.boot2` перед `.text`, потому что образ для RP2040 обязан начинаться с загрузчика второй стадии. Первой идёт секция без содержимого — `.flash_begin` из `section_flash_begin.incl`, единственная задача которой — запомнить начало образа в символе `__flash_binary_start`. За ней `.boot2`:

```text
.boot2 : {
    __boot2_start__ = .;
    KEEP (*(.boot2))
    __boot2_end__ = .;
} > TEXT_STORE

ASSERT(__boot2_end__ - __boot2_start__ == 256,
    "ERROR: Pico second stage bootloader must be exactly 256 bytes")
```

Слово `KEEP` защищает содержимое от удаления. Компоновщик SDK вызывает с ключом `--gc-sections`: всё, на что нет ссылок из кода, выбрасывается из образа, а на загрузчик из кода никто не ссылается. Проверка `ASSERT` вычисляет выражение и, если оно ложно, останавливает сборку с текстом из второго аргумента; здесь она гарантирует ровно 256 байт, потому что именно столько Boot ROM копирует из флеш в SRAM при старте.

Секция `.text` из `section_default_text.incl` — самая длинная в скрипте, и в ней несколько слоёв:

```text
.text : {
    __logical_binary_start = .;
    KEEP (*(.vectors))
    KEEP (*(.binary_info_header))
    __binary_info_header_end = .;
    KEEP (*(.embedded_block))
    __embedded_block_end = .;
    KEEP (*(.reset))
    *(.init)
    *(EXCLUDE_FILE(*libgcc.a: *libc.a: *lib*_a-mem*.o *libm.a:) .text*)
    *(.fini)
    ...
    . = ALIGN(4);
} > TEXT_STORE
```

Первым в секцию попадает `.vectors` — таблица векторов, которую Boot ROM ожидает сразу за загрузчиком; за ней `.binary_info_header`, заголовок с описанием прошивки для `picotool`, и `.reset` — начало [[Стартап-код#^def|стартап-кода]]. Каждый из них обёрнут в `KEEP` по той же причине, что и загрузчик. Дальше идёт код: `*(.text*)` собирает секции `.text` и `.text.имя_функции` из всех объектных файлов, но с исключением, вынесенным в `default_text_excludes.incl`. Конструкция `EXCLUDE_FILE(...)` перечисляет файлы, чьи секции *не* берутся: библиотеки компилятора `libgcc.a`, стандартная библиотека `libc.a`, объектные файлы функций `mem*` и математическая `libm.a`. Их код в `.text` не попадает и остаётся несобранным, а ниже, в записи `.data`, его подберёт строка `*(.text*)` без исключений. Так SDK отправляет в ОЗУ функции вроде `memcpy` и арифметику с плавающей точкой, не помечая их по одной. Опущенная часть секции собирает списки конструкторов и функций инициализации `.init_array`, обрамляя каждый символами `__init_array_start` и `__init_array_end`; стартап-код проходит по этому списку перед вызовом `main()`.

`.rodata` описана так же, с тем же исключением библиотек. Следом фрагмент `sections_arm_ex.incl` кладёт во флеш две секции `.ARM.extab` и `.ARM.exidx` — таблицы для раскрутки стека при исключениях **C++**; в проекте на **C** они пусты. Замыкает флеш-часть `.binary_info` — блок сведений о прошивке, который `picotool info` читает из образа: имя программы, версия SDK, назначение выводов.

## Секции в ОЗУ

Раздел ОЗУ открывает `.ram_vector_table` из `section_ram_vector_table.incl` — 192 байта под копию таблицы векторов, которую SDK переносит в ОЗУ, чтобы обработчики прерываний можно было подменять во время работы. У секции стоит пометка `NOLOAD`: компоновщик отводит ей адреса, но в образ ничего не записывает, заполнит её стартап-код. Именно из-за неё `.data` в сборке `blink` начинается не с `0x20000000`, а с `0x200000c0`. За ней `.uninitialized_data` — тоже `NOLOAD`, для переменных, которые не нужно ни копировать, ни обнулять: SDK помечает так буфер, переживающий перезапуск.

Главная запись раздела — `.data` из `section_default_data.incl`:

```text
.data : {
    __data_start__ = .;
    *(vtable)
    *(.time_critical*)
    *(.text*)
    . = ALIGN(4);
    *(.rodata*)
    . = ALIGN(4);
    *(.data*)
    *(.sdata*)
    . = ALIGN(4);
    *(.after_data.*)
    . = ALIGN(4);
    PROVIDE_HIDDEN (__mutex_array_start = .);
    KEEP(*(SORT(.mutex_array.*)))
    KEEP(*(.mutex_array))
    PROVIDE_HIDDEN (__mutex_array_end = .);
    *(.jcr)
    . = ALIGN(4);
} > RAM AT> RAM_STORE
```

Строки читаются сверху вниз как порядок содержимого. `.time_critical*` — секции функций, помеченных `__not_in_flash_func()` или `__time_critical_func()`: макрос через атрибут `section` компилятора кладёт функцию в секцию с именем `.time_critical.имя`, и эта строка собирает их вместе. Затем `*(.text*)` и `*(.rodata*)` подбирают то, что выше было исключено из флеш, и только потом идут собственно данные `.data*`. Записи `. = ALIGN(4);` между группами выравнивают точку на границу слова. Список `.mutex_array` — таблица мьютексов SDK, которые нужно инициализировать при старте; `SORT` упорядочивает входные секции по имени, чтобы порядок не зависел от порядка объектных файлов, а `PROVIDE_HIDDEN` создаёт символ, видимый только внутри образа. Секция `.tdata` и следующая за ней `.tbss` с блоком `.tls0`/`.tls1` — поддержка переменных, у которых своя копия на каждое ядро; в проектах курса они пусты, и разбирать их запись здесь не будем.

После `.data` скрипт фиксирует её границы:

```text
PROVIDE(__data_end__ = .);
__etext = LOADADDR(.data);
```

`LOADADDR` возвращает адрес хранения секции — то самое `load address` из `.map`. Имя `__etext` историческое, «конец текста»: в классических скриптах копия `.data` лежит сразу за кодом, и её адрес хранения совпадает с концом `.text`; SDK сохранил имя ради совместимости со стартап-кодом. Стартап-код читает три слова — `__etext`, `__data_start__`, `__data_end__` — и копирует байты в цикле; так же он поступает с парами символов для `.scratch_x` и `.scratch_y`.

Запись `.bss` мы видели в статье; полный вид отличается сортировкой и строкой `*(COMMON)` — так называются общие переменные из старых диалектов **C**, объявленные без `extern` в нескольких файлах. Далее `.persistent_data` (`NOLOAD`) для данных, которые должны пережить программный сброс, и куча:

```text
.heap DEFINED(HEAP_LOC) ? HEAP_LOC : . (NOLOAD):
{
    __end__ = .;
    end = __end__;
    KEEP(*(.heap*))
} > RAM
__HeapLimit = DEFINED(HEAP_LIMIT) ? HEAP_LIMIT : ORIGIN(RAM) + LENGTH(RAM);
```

Секция `.heap` резервирует `PICO_HEAP_SIZE` байт, по умолчанию 2 КБ, но только для проверки места: аллокатор `malloc()` берёт память от `__end__` и растёт до `__HeapLimit`, а тот в SDK 2.3.0 равен концу региона `RAM`, если проект не задал `HEAP_LIMIT`. Стек описан зеркально: секции `.stack1_dummy` в `SCRATCH_X` и `.stack_dummy` в `SCRATCH_Y` резервируют по `PICO_STACK_SIZE` байт, тоже 2 КБ, и нужны компоновщику, чтобы вычислить `__StackBottom`, а не чтобы что-то в них положить. Замыкает флеш секция `.flash_end` с символом `__flash_binary_end`; запись `=0xaa` после региона задаёт байт-заполнитель для промежутков.

Границы стеков и кучи сведены во фрагменте `section_end.incl`:

```text
__StackLimit = ORIGIN(RAM) + LENGTH(RAM);
__StackOneTop = ORIGIN(SCRATCH_X) + LENGTH(SCRATCH_X);
__StackTop = ORIGIN(SCRATCH_Y) + LENGTH(SCRATCH_Y);
__StackOneBottom = __StackOneTop - SIZEOF(.stack1_dummy);
__StackBottom = __StackTop - SIZEOF(.stack_dummy);
PROVIDE(__stack = __StackTop);

ASSERT(__StackLimit >= __HeapLimit, "region RAM overflowed")
```

Имя `__StackLimit` обманчиво: это не граница стека, а конец региона `RAM`, и комментарий в самом файле называет его «плохо названным». Проверка `ASSERT` под ним в SDK 2.3.0 стала тождественной, потому что оба символа теперь равны концу `RAM`; настоящую защиту от переполнения даёт длина региона, о чём сказано в статье. Последняя проверка скрипта лежит в `section_platform_end.incl` и требует, чтобы заголовок `.binary_info_header` уместился в первые 256 байт после загрузчика — там его ищет `picotool`.

## Секции сводной таблицей

| Секция | Регион | Хранится | Что содержит |
| --- | --- | --- | --- |
| `.flash_begin` | `FLASH` | — | только символ `__flash_binary_start` |
| `.boot2` | `FLASH` | `FLASH` | загрузчик второй стадии, ровно 256 байт |
| `.text` | `FLASH` | `FLASH` | таблица векторов, заголовок `binary_info`, стартап-код, код проекта и SDK без библиотек |
| `.rodata` | `FLASH` | `FLASH` | константы и строки без библиотек |
| `.ARM.extab`, `.ARM.exidx` | `FLASH` | `FLASH` | таблицы исключений **C++**, в проектах на **C** пусты |
| `.binary_info` | `FLASH` | `FLASH` | сведения о прошивке для `picotool` |
| `.ram_vector_table` | `RAM` | `NOLOAD` | копия таблицы векторов, 192 байта |
| `.uninitialized_data` | `RAM` | `NOLOAD` | переменные, которые не копируют и не обнуляют |
| `.data` | `RAM` | `FLASH` | код `.time_critical`, библиотеки, переменные с начальным значением |
| `.tdata`, `.tbss`, `.tls0`, `.tls1` | `RAM` | `FLASH` / `NOLOAD` | переменные с копией на каждое ядро, в проектах курса пусты |
| `.bss` | `RAM` | `NOLOAD` | переменные без значения или с нулём |
| `.persistent_data` | `RAM` | `NOLOAD` | данные, переживающие программный сброс |
| `.heap` | `RAM` | `NOLOAD` | резерв под кучу, `PICO_HEAP_SIZE` |
| `.scratch_x`, `.scratch_y` | `SCRATCH_X`, `SCRATCH_Y` | `FLASH` | код и данные, явно помещённые в банки-заглушки |
| `.stack1_dummy`, `.stack_dummy` | `SCRATCH_X`, `SCRATCH_Y` | `NOLOAD` | резерв под стеки ядер 1 и 0, `PICO_STACK_SIZE` |
| `.flash_end` | `FLASH` | — | только символ `__flash_binary_end` |

## Символы сводной таблицей

Значения приведены для сборки `blink` с переменными из раздела Т2.1.2; помечены символы, которые зависят только от `MEMORY` и в любой сборке для Pico одинаковы.

| Символ | Значение | Что означает | Кто пользуется |
| --- | --- | --- | --- |
| `__flash_binary_start` | `0x10000000` | начало образа | `picotool`, код проекта |
| `__boot2_start__`, `__boot2_end__` | `0x10000000`, `0x10000100` | границы загрузчика | `ASSERT` |
| `__logical_binary_start` | `0x10000100` | начало `.text`, адрес таблицы векторов | Boot ROM, `ASSERT` |
| `__etext` | `0x10001918` | адрес хранения `.data` | стартап-код |
| `__flash_binary_end` | `0x10001a90` | конец образа | код проекта |
| `__data_start__`, `__data_end__` | `0x200000c0`, `0x20000238` | границы `.data` в ОЗУ | стартап-код |
| `__bss_start__`, `__bss_end__` | `0x20000238`, `0x20000650` | границы `.bss` | стартап-код |
| `__end__`, `end` | `0x20000650` | начало кучи | аллокатор `malloc()` |
| `__HeapLimit` | `0x20040000`, только `MEMORY` | верхняя граница кучи | аллокатор |
| `__StackLimit` | `0x20040000`, только `MEMORY` | конец региона `RAM`, несмотря на имя | `ASSERT` |
| `__StackOneBottom`, `__StackOneTop` | `0x20041000`, `0x20041000` | стек ядра 1; пока ядро 1 не запущено, секция пуста и границы совпадают | SDK при запуске ядра 1 |
| `__StackBottom`, `__StackTop` | `0x20041800`, `0x20042000`, вершина — только `MEMORY` | стек ядра 0 | таблица векторов, слово 0 |
| `__scratch_x_source__`, `__scratch_x_start__`, `__scratch_x_end__` | копия и границы `.scratch_x` | — | стартап-код |
| `__binary_info_start`, `__binary_info_end` | границы `.binary_info` | — | `picotool` |

| Запись | Смысл |
| --- | --- |
| `INCLUDE "файл"` | подставить содержимое файла; ищется по путям `-L` |
| `MEMORY { ИМЯ(права) : ORIGIN = a, LENGTH = n }` | объявить регион; права `r`, `w`, `x` |

| `EXCLUDE_FILE(список) .имя*` | шаблон секций из всех файлов, кроме перечисленных |

## Как управлять размещением из проекта

SDK даёт три уровня вмешательства, от простого к сложному. Первый — атрибуты в коде: макрос `__not_in_flash_func(f)` переносит функцию в ОЗУ через секцию `.time_critical`, макрос `__scratch_x("группа")` кладёт объект в банк `SCRATCH_X`, `__uninitialized_ram(x)` — в `.uninitialized_data`. Второй — переменные скрипта: `pico_set_linker_script_var(цель RAM_LENGTH 128k)` в `CMakeLists.txt` меняет число, не трогая файлов, а константы `PICO_STACK_SIZE` и `PICO_HEAP_SIZE` задаются через `target_compile_definitions()`. Третий — переопределение фрагментов: папка проекта с файлом `memory_extra.incl`, подключённая через `pico_add_linker_script_override_path()`, добавит регион, а файл `section_extra_post_text.incl` — секцию во флеш после `.text`; пример с дополнительным регионом флеш приведён в комментарии штатного `memory_extra.incl`. Копировать `memmap_default.ld` в проект, как это сделано в курсе, при таком устройстве уже не обязательно: `pico_set_linker_script()` нужен лишь для того, чтобы файл лежал в репозитории на виду.

## Что изменилось со времён SDK 1.5

До версии 2.3 скрипт для RP2040 был одним файлом на две сотни строк, `src/rp2_common/pico_standard_link/memmap_default.ld`, и именно его разбирал предыдущий курс. Блок `MEMORY` в нём записан ровно так, как показано в статье, с числами прямо в тексте. Из отличий по существу стоит знать три. Символ `__HeapLimit` тогда стоял в конце секции `.heap`, то есть на 2 КБ выше `__end__`, а теперь равен концу региона `RAM`; из-за этого проверка `__StackLimit >= __HeapLimit` перестала что-либо проверять. Регионы получили псевдонимы `*_STORE`, и запись `AT> FLASH` в новых фрагментах выглядит как `AT> RAM_STORE`. И появился регион `XIP_RAM` вместе с секцией `.xip_ram`. Всё остальное — имена секций, имена символов, порядок размещения — сохранилось, поэтому старые статьи и примеры остаются верными по смыслу.

Проверить сказанное на своей сборке можно тремя командами в папке `build`: `arm-none-eabi-size -A имя.elf` покажет размер и адрес каждой секции, `arm-none-eabi-nm имя.elf | grep __` перечислит символы линкера со значениями, а файл `.map` в разделе `Linker script and memory map` покажет, из какого объектного файла пришла каждая входная секция и куда легла.
