В прошлом разделе состояние задачи стало переменной, которую меняет только функция смены состояния. Но это требование пока держится на аккуратности разработчика: язык не мешает другому файлу изменить переменную напрямую. Код прошивки мы уже делим на файлы исходников и заголовков, однако само деление ещё не решает, что одному файлу видно в другом. В этом разделе разберём, как в языке **C** устроен модуль и как он открывает одно и закрывает другое.

## Раздельная компиляция и программный модуль

Модулей как понятия в языке **C** нет — есть файлы `.c` и `.h`. Как мы видели в разделе [[т1.3.3 От исходного кода к прошивке#^intro|От исходного кода к прошивке]], каждый файл `.c` компилируется отдельно, в свой [[Объектный файл#^def|объектный файл]], а [[Компоновщик#^def|компоновщик]] связывает их между собой по именам. Для компоновщика имена всех функций и всех переменных, объявленных вне функций, лежат в одном общем списке на весь образ, и из какого файла пришло имя, роли не играет. Если функция `init()` есть и в `led.c`, и в `button.c`, сборка остановится: двух объектов с одним именем в образе быть не может.

Раз файлы компилируются порознь, компилятор, собирая `main.c`, не видит ни тела функции из `led-task.c`, ни её переменных. Чтобы составить вызов функции или обращение к переменной, ему достаточно знать, что такое имя существует и какого оно типа, — это сообщает объявление. Сам объект создаёт определение: функции оно даёт тело, переменной — память ([[т2.1.2 Состав образа ВПО. Секции#^intro|Состав образа ВПО. Секции]]). Для задачи светодиода из прошлого раздела это выглядит так:

| | Объявление | Определение |
| --- | --- | --- |
| функция | `void led_task_init(void);` | `void led_task_init(void) { … }` |
| переменная | `extern led_state_t led_state;` | `led_state_t led_state;` |

Объявление функции в первой строке таблицы называют её прототипом.

![[Прототип функции#^def]]

Отличить прототип от определения просто: у прототипа нет тела. С переменной ошибиться легче: строка `led_state_t led_state;` вне функций выглядит как простое сообщение о том, что переменная есть, но это определение — под переменную отводится память в `.bss`, как под переменные из раздела Т2.1.2. Объявлением она становится только со словом `extern`. С ним вы уже встречались в разделе [[т2.1.3 Линкер-скрипт#^intro|Линкер-скрипт]], когда получали символы линкера, — там тоже объявлялось имя, определённое в другом месте. Объявлений одного имени может быть сколько угодно, по одному в каждом файле, который им пользуется, а определение у него ровно одно: его компоновщик и ищет, связывая обращения к имени.

Поэтому модуль в **C** собирают из договорённостей. Имена разных частей прошивки различают общим префиксом: все функции задачи светодиода называются `led_task_…`, все функции задачи кнопки — `button_task_…`. Объявления того, чем модуль разрешает пользоваться, собирают в заголовочный файл с именем модуля, а определения — в файлы реализации. Язык ничего из этого не проверяет. Слово «модуль» в этом смысле мы используем с модуля 1 курса, и пора дать ему определение.

![[Программный модуль#^def]]

Чаще всего файл реализации у модуля один и называется так же, как заголовок, но не всегда: бывает, что модуль удобнее разложить на несколько файлов, и тогда у него появляются внутренние заголовки, которые нужны только его собственным файлам. Такой модуль мы встретим в разделе [[т2.3.8 Протокол и API прибора#^intro|Протокол и API прибора]].

## Правила оформления заголовочного файла

[[Заголовочный файл#^def|Заголовочный файл]] модуля — это его [[Интерфейс#^def|интерфейс]]: всё, чем другие модули могут пользоваться, объявлено в нём. Для задачи светодиода из прошлого раздела он выглядит так:

```c
// led-task.h — задача светодиода: выключен, горит или мигает
#pragma once

#include <stdbool.h>
#include <stdint.h>

typedef enum {
    LED_STATE_OFF,
    LED_STATE_ON,
    LED_STATE_BLINK,
} led_state_t;

void led_task_init(void);
void led_task_handle(void);

void led_task_set_state(led_state_t state);
led_state_t led_task_get_state(void);

// false — период не принят
bool led_task_set_period_ms(uint32_t period_ms);
```

Текст заголовка [[Препроцессор#^def|препроцессор]] вставляет в каждый файл, который его подключил, и из этого следуют правила, по которым заголовки пишут:

1. *В заголовке — только то, без чего не обойдётся вызывающий код:* прототипы функций, типы из их сигнатур, константы, которые вызывающему нужно передавать. Перечисляемый тип `led_state_t` здесь потому, что без него не объявить `led_task_set_state()`; метки времени и функция, которая пишет в вывод, вызывающему не нужны и остались в `.c`. Проверить, где место строке, можно вопросом: если убрать её из заголовка, сломается ли код того, кто модулем пользуется? Если нет, строке место в `.c`.

2. *В заголовке — только объявления, без определений.* Определение из заголовка окажется в каждом файле, который его подключил, и компоновщик получит несколько объектов с одним именем. С телом функции так ошибаются редко: сразу видно, что это код. С переменной — часто, потому что строка без `extern`, как мы видели, уже определение. Так выглядит сборка, в которой в `led-task.h` записали `led_state_t led_state;`, а заголовок подключают `led-task.c` и `main.c`:

   ```text
   ld.exe: CMakeFiles/module.dir/led-task.c.obj:led-task.h:9: multiple
   definition of `led_state'; CMakeFiles/module.dir/main.c.obj:led-task.h:9:
   first defined here
   ```

   Ни один из двух файлов `.c` ничего неправильного не содержит — ошибка в строке заголовка. Типы и макросы этому правилу не мешают: они не создают объектов в памяти и существуют только в тексте файла. По той же причине через `#include` подключают только заголовки, а не файлы `.c`.

3. *Заголовок защищён от повторного включения.* Заголовки подключают и другие заголовки: заголовок модуля команд подключает заголовок протокола ради типа команды, а `main.c` — оба. Тогда текст заголовка протокола попадёт в `main.c` дважды, тип будет объявлен два раза, и компилятор остановится с ошибкой `conflicting types for 'command_t'`. Директива `#pragma once` в первой строке велит препроцессору вставлять файл в каждый `.c` только один раз. В стандарт языка она не входит, но её понимают GCC и другие распространённые компиляторы; стандартный способ, который вы встретите в SDK, — защитные макросы `#ifndef LED_TASK_H`, `#define LED_TASK_H` … `#endif`. От ошибки из предыдущего пункта не спасает ни то ни другое: защита действует внутри одного `.c`, а переменная из заголовка определяется в разных.

4. *Заголовок самодостаточен:* он подключает всё, что нужно ему самому. В `led-task.h` встречаются `bool` и `uint32_t`, поэтому в нём стоят `<stdbool.h>` и `<stdint.h>`; иначе заголовок собирался бы, только если пользователь заранее подключил их сам. И наоборот, заголовок не подключает того, что нужно только реализации: функции SDK нужны `led-task.c`, а не тем, кто вызывает задачу. Почему это важно, разберём в разделе [[т2.3.7 Границы модулей#^intro|Границы модулей]].

5. *Файл `.c` подключает свой заголовок первым.* Если заголовок не самодостаточен, ошибка появится при сборке самого модуля, а не в чужом файле. Кроме того, компилятор сверит каждый прототип из заголовка с определением: объяви заголовок `led_task_set_period_ms(uint32_t)`, а `.c` — с `uint16_t`, сборка остановится на `conflicting types`. Без своего заголовка такое расхождение прошло бы молча, потому что компоновщик связывает вызов с функцией только по имени и типы не сравнивает.

6. *Заголовок подключают с именем модуля:* `#include "logging/log.h"`, `#include "led-task/led-task.h"`. Когда модулей и библиотек много, одинаковые имена файлов — `log.h`, `config.h` — встречаются в нескольких местах, и препроцессор молча берёт тот, что найдёт первым. Имя модуля в пути исключает совпадение и показывает, откуда пришёл заголовок. Как сборка находит такие пути, разберём в разделе [[т2.3.6 Библиотека в сборке#^intro|Библиотека в сборке]].

Эти правила не придуманы для курса: почти в том же виде они записаны в стандартах оформления кода для встраиваемых систем, например в главе «Module Rules» стандарта BARR-C Майкла Барра. Заголовок определяет, что модуль показывает другим. Но, как мы увидим дальше, отсутствие имени в заголовке ещё не закрывает его.

## Доступ к функциям и переменным файла

Модулю нужны данные, с которыми он работает, — у задачи светодиода это текущее состояние, полупериод, метка прошлого переключения, — и он должен сам решать, кто и как к ним обращается. В языках с классами для этого есть слова `public` и `private`. В **C** их нет, и доступ регулирует то, как компоновщик видит имена.

Имена всех функций и всех переменных, объявленных вне функций, компилятор по умолчанию передаёт компоновщику, и пользоваться ими может любой файл образа. Такое свойство имени называют внешним связыванием.

![[Внешнее связывание#^def]]

Заголовок в этом ничего не меняет: он лишь избавляет от необходимости писать объявления самому, но запретить их писать не может. Любой файл может объявить `void led_set(bool on);` и вызвать функцию, которой в заголовке нет, или объявить `extern led_state_t led_state;` и записать в переменную задачи своё значение, — компоновщик найдёт оба имени. Функцию можно вызвать даже вовсе без объявления: GCC предупредит об этом (`implicit declaration of function`), но сборку не остановит. С типами и макросами иначе: компоновщику они не передаются, и тип, объявленный в `led-task.c`, другому файлу недоступен — в его тексте этого типа просто нет.

Изменить связывание позволяет ключевое слово `static`. Перед функцией или переменной вне функций оно задаёт внутреннее связывание: имя действует только внутри своего файла `.c` вместе с заголовками, которые в него вставил препроцессор, и компоновщику не передаётся.

![[Внутреннее связывание#^def]]

Файл задачи светодиода со `static` начинается так:

```c
#include "led-task.h"

#include "pico/stdlib.h"

// Состояние задачи: внутреннее связывание, только для этого файла
static led_state_t led_state;
static uint64_t half_period_us;
static uint64_t last_toggle_us;

// Вспомогательная функция: из других файлов её не вызвать
static void led_set(bool on)
{
    gpio_put(PICO_DEFAULT_LED_PIN, on);
}

bool led_task_set_period_ms(uint32_t period_ms)
{
    // С нулевым полупериодом светодиод переключался бы
    // на каждой итерации: такой период не принимается
    if (period_ms == 0) {
        return false;
    }

    half_period_us = (uint64_t)period_ms * 1000 / 2;
    return true;
}
```

Если теперь объявить в `main.c` `extern led_state_t led_state;` и присвоить переменной значение, компилятор `main.c` поверит объявлению — он видит только свой файл. Остановит сборку компоновщик, которому имени `led_state` никто не передал:

```text
ld.exe: CMakeFiles/module.dir/main.c.obj: in function `main':
main.c:10: undefined reference to `led_state'
```

Обход функции смены состояния, о котором шла речь в конце прошлого раздела, стал невозможен. А поскольку имена с внутренним связыванием компоновщик не сравнивает, в двух модулях могут быть одноимённые `static`-переменные, и префикс нужен только тому, что модуль открывает.

Отсюда правило, которое записано во многих стандартах оформления кода для встраиваемых систем: функции и переменные вне функций, которые не нужны другим файлам, определяются со `static`. По умолчанию у них внешнее связывание, и имя доступно всему образу, даже если в заголовке его нет; `static` делает видимость имени такой, какой она задумана в интерфейсе. Заодно компилятор получает больше сведений. Все вызовы `static`-функции находятся в её файле, поэтому GCC с включёнными предупреждениями (ключ `-Wall`) сообщит о такой функции, если её никто не вызывает, а небольшую функцию встроит прямо в место вызова. Правило относится и к задаче расчёта π из раздела [[т2.3.3 Программная задача#^intro|Программная задача]]: её переменные получают `static`, а снаружи остаются `pi_task_start()`, обработчик и `pi_task_get_result()`.

С памятью `static` вне функций ничего не делает: переменная лежит в `.data` или `.bss` по правилам раздела Т2.1.2 и существует всё время работы прибора, как и без него. Внутри функции у того же слова другое действие — оно продлевает жизнь локальной переменной с одного вызова на всё время работы. Вне функций переменная и так живёт всё время, поэтому там `static` меняет только связывание.

Сведём, как закрыть и как открыть каждую часть модуля:

| Что | Закрыть | Открыть |
| --- | --- | --- |
| функция | определить со `static` в `.c` | прототип в заголовке |
| переменная | определить со `static` в `.c` | `extern` в заголовке, определение в `.c` |
| тип, макрос | объявить в `.c` | объявить в заголовке |

Уровней видимости в таблице два: имя видно либо своему файлу, либо всему образу. Промежуточного уровня — «только файлам своего модуля» — в **C** нет, и для модуля из нескольких файлов это важно: то, чем его файлы пользуются друг у друга, приходится оставлять с внешним связыванием. Объявления таких имён собирают во внутренний заголовок, который подключают только файлы самого модуля. Публичный заголовок внутренний не подключает, иначе внутренние объявления получил бы каждый пользователь модуля. Закрыть эти имена от остальной прошивки язык не может, поэтому через внутренний заголовок открывают как можно меньше, а граница держится договорённостью и именем файла, по которому видно, что заголовок внутренний. Как сделать, чтобы чужой файл не смог его подключить, разберём в разделе [[т2.3.6 Библиотека в сборке#^intro|Библиотека в сборке]], а модуль, устроенный так, — в разделе Т2.3.8.

Открывать функции — обычное дело, а изменяемую переменную через `extern` не открывают. Записать в неё сможет любой файл, который подключил заголовок, и по коду модуля уже не понять, кто и когда её меняет; для `led_state` это был бы тот самый обход функции смены состояния, разрешённый самим модулем. Вместо этого модуль даёт функции доступа: `led_task_get_state()` для чтения, `led_task_set_state()` и `led_task_set_period_ms()` для изменения. Функция, через которую значение попадает внутрь, проверяет его: нулевой период модуль не принимает и сообщает об отказе результатом. Проверять должен именно модуль — он владеет данными и знает, какие значения для них недопустимы, а вызывающему достаточно обработать отказ. Исключение — данные, которые можно только читать: таблицу с `extern const` открывают в заголовке, и записать в неё не даст компилятор (`assignment of read-only location`). Так открыта таблица команд прибора, которую мы разберём в разделе Т2.3.8.

Закрытость не бесплатна: к закрытой переменной обращаются вызовом функции, а вызов дольше прямого обращения. На участке, который выполняется много раз за итерацию, функцию доступа можно определить прямо в заголовке со словами `static inline`, и компилятор встроит её в место вызова, но для этого состояние модуля придётся открыть всем — такое нарушение границы делают сознательно и только там, где замер показал, что вызов действительно дорог.

Итак, `static` закрывает имя от компоновщика, а заголовок определяет, что модуль открывает другим. Но сам заголовок остаётся доступным всем: в одной цели сборки любой файл может подключить любой заголовок — чужого модуля или SDK, — потому что пути поиска заголовков у всех файлов цели общие. Ничто не мешает задаче, которой положено работать с железом только через свой модуль, подключить `pico/stdlib.h` и вызвать `gpio_put()` напрямую. Может ли сборка сама следить за тем, кому какие заголовки видны, разберём в следующем разделе.
