**Результат** — рекордер `321-audio-recorder` непрерывно передаёт отсчёты на компьютер. Два канала DMA по очереди заполняют два буфера, прибор отправляет каждый заполненный буфер двоичным кадром, а скрипт `rec_audio.py` принимает кадры и считает, не потерялся ли хоть один. Пока идёт поток, мигает индикатор записи.
^intro

![[Двойная буферизация.excalidraw|100%]]

Пока DMA заполняет один буфер, суперцикл отправляет другой. Отправка должна успеть за 11,6 мс, иначе DMA застанет буфер неотправленным.

## Задание

### Что должно получиться

- [ ] Два канала DMA цепочкой заполняют два буфера по очереди, обработчик прерывания DMA отмечает готовый буфер
- [ ] Задача `logic/stream-task` отдаёт каждый готовый буфер кадром по [[ТЗ 3.2 Приложение А. Кадр потока|приложению А]]
- [ ] Кадры уходят в порт без замены `\n` на `\r\n`
- [ ] `stream_start` запускает поток и индикатор, `stream_stop` останавливает и сообщает число кадров, отсчётов и переполнений
- [ ] `rec_audio.py` принял поток за 5 с без пропусков, итог в `stream.log`, коммит отправлен, проверка `3.2.4` зелёная

### Как проверить

1. **Поток идёт без потерь.** `rec_audio.py --seconds 5` печатает около 430 кадров и ноль пропущенных.
2. **Итог лежит в проекте.** Скрипт записывает его в `stream.log`.
3. **Автоматическая проверка курса принимает задание.** В коде она ищет цепочку каналов, возврат адреса записи в обработчике, отправку без замены `\n`, синхрослово `0x5aa5` и функцию для кадра у задачи потока. В `stream.log` она проверяет, что поток шёл не меньше 3 с и около 86 кадров в секунду, в каждом 512 отсчётов, без пропусков и переполнений, со скоростью от 43 000 до 45 500 отсчётов в секунду.

## Ход работы

Это задание выполняет требования Р1.2, Р3, Н3 и Н4 [[ТЗ 3.2 Рекордер|ТЗ на рекордер]]. Двойная буферизация и цепочка каналов разобраны в [[т3.2.7 Двойная буферизация#^intro|т3.2.7]], кадры и перевод строки — в [[т3.2.8 Двоичная передача данных#^intro|т3.2.8]].

### 1. Заполнять два буфера по очереди

Добавьте в `platform.h` интерфейс потока.

```c
// поток: два буфера по PLATFORM_STREAM_BYTES байт по очереди; false — АЦП занят
#define PLATFORM_STREAM_BYTES 1024
bool platform_stream_start(uint8_t bits);
void platform_stream_stop(void);

// следующий заполненный буфер по порядку или NULL, если он ещё не готов;
// samples — число отсчётов в буфере
const uint8_t *platform_stream_next(uint32_t *samples);

// буфер отправлен, его можно заполнять снова
void platform_stream_release(void);

// сколько раз DMA застал буфер неотправленным
uint32_t platform_stream_overruns(void);

// отправляет байты в порт как есть, без замены \n на \r\n
void platform_write(const void *data, uint32_t bytes);
```

Параметр `bits` пока принимает только 16. Разрядность 8 появится в дополнительном задании [[п3.2.7д Запись в 8 бит#^intro|п3.2.7д]]. В `adc_user_t` добавьте `ADC_STREAM`. Дальше новый код `platform.c`. Каналы потока пишут каждый в свой буфер и по окончании запускают друг друга. Обработчик прерывания отмечает буфер готовым и возвращает каналу адрес начала буфера.

```c
static int stream_channels[2];
static uint8_t stream_buffers[2][PLATFORM_STREAM_BYTES] __attribute__((aligned(4)));
static volatile bool stream_ready[2];
static volatile uint32_t stream_overruns;
static uint32_t stream_samples;
static uint32_t stream_next;

// обработчик прерывания DMA_IRQ_0: канал заполнил свой буфер
static void on_stream_buffer(void)
{
    for (int i = 0; i < 2; i++)
    {
        if (dma_channel_get_irq0_status(stream_channels[i]))
        {
            dma_channel_acknowledge_irq0(stream_channels[i]);

            // адрес записи дошёл до конца буфера, вернуть его к началу
            dma_channel_set_write_addr(stream_channels[i], stream_buffers[i], false);

            // в следующий буфер уже идёт запись, а его ещё не отправили
            if (stream_ready[(i + 1) % 2])
            {
                stream_overruns++;
            }
            stream_ready[i] = true;
        }
    }
}

bool platform_stream_start(uint8_t bits)
{
    if (adc_user != ADC_FREE || bits != 16)
    {
        return false;
    }

    stream_samples = PLATFORM_STREAM_BYTES / 2;
    adc_free_running();

    // канал i пишет в буфер i и по окончании запускает другой канал
    for (int i = 0; i < 2; i++)
    {
        // номер следующего канала в цепочке
        int next_channel = stream_channels[(i + 1) % 2];

        dma_channel_config cfg = dma_channel_get_default_config(stream_channels[i]);
        channel_config_set_transfer_data_size(&cfg, DMA_SIZE_16);
        channel_config_set_read_increment(&cfg, false);
        channel_config_set_write_increment(&cfg, true);
        channel_config_set_dreq(&cfg, DREQ_ADC);
        channel_config_set_chain_to(&cfg, next_channel);
        dma_channel_configure(stream_channels[i], &cfg, stream_buffers[i], &adc_hw->fifo,
                              stream_samples, false);
        dma_channel_set_irq0_enabled(stream_channels[i], true);
        stream_ready[i] = false;
    }

    stream_overruns = 0;
    stream_next = 0;
    adc_user = ADC_STREAM;
    dma_channel_start(stream_channels[0]);
    adc_run(true);
    return true;
}

void platform_stream_stop(void)
{
    if (adc_user != ADC_STREAM)
    {
        return;
    }

    // сначала остановить отсчёты, затем каналы и их прерывания
    adc_run(false);

    // RP2040-E13: передача, начатая до прерывания канала, завершается как обычная
    // и запускает канал из цепочки. Поэтому цепочка сначала разрывается: каждый
    // канал указывает сам на себя, иначе один из них останется взведённым
    for (int i = 0; i < 2; i++)
    {
        dma_channel_config cfg = dma_get_channel_config(stream_channels[i]);
        channel_config_set_chain_to(&cfg, stream_channels[i]);
        dma_channel_set_config(stream_channels[i], &cfg, false);
    }

    for (int i = 0; i < 2; i++)
    {
        dma_channel_set_irq0_enabled(stream_channels[i], false);
        dma_channel_abort(stream_channels[i]);
        dma_channel_acknowledge_irq0(stream_channels[i]);
    }
    adc_one_shot();
    adc_user = ADC_FREE;
}

void platform_write(const void *data, uint32_t bytes)
{
    // false, false — без перевода строки в конце и без замены \n на \r\n
    stdio_put_string((const char *)data, (int)bytes, false, false);
}
```

>[!bug] Почему цепочку разрывают перед остановкой
>Канал прерывают записью в регистр `CHAN_ABORT`. Если в этот момент у канала есть передача «в полёте», уже прочитанная, но ещё не записанная, она доходит до конца, и DMA считает её обычным завершением ([[RP2040 Datasheet.pdf#page=630|RP2040 Datasheet, RP2040-E13]]). Обычное завершение запускает канал, указанный в `CHAIN_TO`. Прерываем канал 0, он запускает канал 1, прерываем канал 1, он снова запускает канал 0. Канал 0 остаётся взведённым на запросе АЦП, с выключенным прерыванием. Следующий захват блока снова запустит АЦП, канал 0 заполнит свой буфер, по цепочке запустит канал 1, а тот начнёт писать с адреса, на котором остановился, и уйдёт за конец буфера, по чужой памяти. На рекордере это проявлялось так. После записи `dma_cap` раз в несколько попыток вешал прибор, причём вместе с USB, потому что портились данные USB-стека. Разрыв цепочки перед прерыванием убирает причину.

Буфер объявлен массивом байтов, потому что в 8-битном потоке в нём будет 1024 отсчёта по байту, а в 16-битном 512 по два. Атрибут `aligned(4)` кладёт его по адресу, кратному четырём, чтобы 16-битные передачи DMA попадали на границы слов.

В конце `platform_init()` заведите два канала и обработчик `DMA_IRQ_0`, как канал блока в [[п3.2.3 Захват блока через DMA#1. Захватить блок в platform|п3.2.3]]. Прерывание каждого канала разрешает `platform_stream_start()`, здесь его не включайте. Функция `on_stream_buffer()` должна быть описана в файле выше `platform_init()`, как `on_block_done()`.

>[!success] Должно получиться так
> ```c
> // два канала потока сообщают о заполненном буфере через DMA_IRQ_0
> stream_channels[0] = dma_claim_unused_channel(true);
> stream_channels[1] = dma_claim_unused_channel(true);
> irq_set_exclusive_handler(DMA_IRQ_0, on_stream_buffer);
> irq_set_enabled(DMA_IRQ_0, true);
>
> // platform_stream_next(): буфер stream_next не готов — NULL;
> // иначе число отсчётов в samples и адрес буфера
>
> // platform_stream_release(): снять отметку готовности с буфера stream_next,
> // stream_next — на другой буфер
>
> // platform_stream_overruns(): вернуть stream_overruns
> ```

Флаг готовности обработчик ставит, а суперцикл снимает, но каждый из них делает одну запись `bool` в память, а такая запись атомарна. Счётчик `stream_overruns` меняет только обработчик. Поэтому критическая секция здесь не нужна ([[т3.2.5 Обработчик прерывания#Атомарность|т3.2.5]]).

### 2. Отдавать буферы кадрами

Задача `logic/stream-task` на каждой итерации спрашивает у `platform` следующий буфер. Если он готов, задача собирает заголовок кадра и отдаёт заголовок и буфер функции, полученной при запуске. Заголовок — это структура из трёх 16-битных полей. Промежутков между ними компилятор не оставит, а поля лягут в память младшим байтом вперёд. Отправить заголовок — значит отправить байты этой структуры, как они лежат в памяти.

```c
// stream-task.h — задача потока: забирает у platform заполненные буферы
// отсчётов по порядку и отдаёт каждый кадром функции, переданной при запуске.
// Как кадр попадёт на компьютер, задача не знает.

#pragma once

#include <stdbool.h>
#include <stdint.h>

typedef enum {
    STREAM_STATE_IDLE,
    STREAM_STATE_RUN,
} stream_state_t;

// синхрослово: в памяти и в канале байты a5 5a
#define STREAM_SYNC_WORD 0x5aa5

// заголовок кадра по приложению А ТЗ: синхрослово, номер, число отсчётов;
// три поля по 16 бит, младший байт первым, без промежутков
typedef struct {
    uint16_t sync_word;
    uint16_t number;
    uint16_t count;
} stream_header_t;

// функция, которой задача отдаёт заголовок и данные каждого кадра
typedef void (*stream_task_callback_t)(const stream_header_t *header, const uint8_t *data,
                                       uint32_t bytes);

void stream_task_init(stream_task_callback_t on_frame);

// вызывается на каждой итерации суперцикла, не ждёт
void stream_task_handle(void);

// bits — 16 или 8; false — АЦП занят или разрядность не та
bool stream_task_start(uint8_t bits);
void stream_task_stop(void);

stream_state_t stream_task_get_state(void);
uint8_t stream_task_get_bits(void);

// итог потока с последнего запуска
uint32_t stream_task_get_frames(void);
uint32_t stream_task_get_samples(void);
uint32_t stream_task_get_overruns(void);
```

>[!success] Должно получиться так
> ```c
> // stream_task_init(): запомнить функцию для кадров, состояние IDLE
>
> // stream_task_start(): поток уже идёт или platform его не начал — false;
> // запомнить разрядность, номер кадра и итог — с нуля, состояние RUN
>
> // stream_task_stop(): остановить поток в platform, состояние IDLE
>
> // stream_task_handle(): в состоянии RUN, если platform отдал буфер:
> //     заголовок — синхрослово STREAM_SYNC_WORD, номер, число отсчётов
> //     байтов — отсчётов × 2 при 16 битах, отсчётов при 8
> //     отдать заголовок и буфер функции, буфер вернуть platform
> //     номер, число кадров и отсчётов — вперёд
> ```

### 3. Отправлять кадры и добавить команды

Кадр отправляет `api`. Функция отправки новая, вот она целиком. Объявите её в `api.h`, а в `main.c` передайте задаче потока при запуске.

```c
void api_send_frame(const stream_header_t *header, const uint8_t *data, uint32_t bytes)
{
    // байты заголовка и отсчётов как они лежат в памяти
    platform_write(header, sizeof(*header));
    platform_write(data, bytes);
}
```

### 4. Принять поток скриптом

Скопируйте [[rec_audio.py]] в папку проекта. Скрипт отправляет `stream_start`, читает ответ текстом, а дальше разбирает байты на кадры по правилам [[ТЗ 3.2 Приложение А. Кадр потока#А.2. Приём|приложения А]]. Главное в нём — класс `Receiver`. Его метод `feed()` получает очередную порцию байтов из порта, ищет синхрослово `a5 5a`, проверяет число отсчётов и раскладывает кадр модулем `struct`.

```python
sync_word, number, count = HEADER.unpack_from(self.buffer)
```

Здесь `HEADER` — это `struct.Struct("<HHH")`, три беззнаковых 16-битных числа младшим байтом вперёд. Разницу номеров соседних кадров скрипт складывает в счётчик пропусков. Байты вне кадров, эхо команды и текстовый ответ на `stream_stop`, он пропускает и считает отдельно.

Запустите запись на 5 секунд.

``` bash
python rec_audio.py --seconds 5
```

>[!success] Должно получиться так
> ```
> Плата на порту COM5, пишу 5.0 с
> Кадров 432, отсчётов 221184, пропущено кадров 0
> Итог записан в stream.log
> ```
> Файл `stream.log`
> ```
> задание: 3.2.4
> проект: 321-audio-recorder
> ...
> --> stream_start
> <-- stream: started, 44100 Hz, 16 bit
> принято: кадров 432, отсчётов 221184, пропущено кадров 0, байтов вне кадров 70
> скорость: 44206 отсчётов в секунду за 5.00 с
> отсчёты: наименьший 6, наибольший 74, средний 49.6
> --> stream_stop
> <-- stream: stopped, 432 frames, 221184 samples, 0 overruns
> ```

Прибор отправил 432 кадра, скрипт принял все 432, переполнений ноль. 70 байт вне кадров — это эхо команды `stream_stop` и ответ на неё. Скорость скрипт считает по часам компьютера, поэтому она отличается от 44 100 на доли процента, на время, за которое кадры доходят по USB.

### 5. Проверить время задачи потока

Требование Н3 ограничивает обработчик задачи потока 2 мс. Сбросьте секундомеры, запишите поток скриптом и спросите профилирование в терминале.

>[!success] Должно получиться так
> ```
> profiling
> loop       count 1007534    mean 8.46 us  max 1475 us
> ...
> stream     count 1007534    mean 0.98 us  max 1465 us
> ```

Худший вызов задачи потока длится 1,47 мс, почти всё это время уходит на отправку кадра в 1030 байт по USB. Это восьмая часть от 11,6 мс, за которые DMA заполняет другой буфер, и запас многократный.

Наберите в терминале во время потока `uptime`. Прибор ответит, а вокруг ответа терминал покажет случайные символы. Это байты кадров, которые терминал по-прежнему показывает как символы ASCII.

>[!warning] Если пропуски есть
>Пропуски при нуле переполнений означают, что байты меняются по пути. Проверьте, что кадры уходят через `platform_write()`, а не через `printf()` или `fwrite()`. Те заменяют каждый байт `0a` парой `0d 0a`, и ошибка проявится, только когда такой байт встретится в данных ([[т3.2.8 Двоичная передача данных#Перевод строки в стандартном выводе|т3.2.8]]).
