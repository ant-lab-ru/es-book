В прошлом разделе мы выяснили, что задача между вызовами обработчика помнит, где остановилась: докуда дошла долгая работа и когда сработал прошлый период. Пока такая память сводится к паре переменных, о ней можно не думать специально. Но у прибора бывают режимы работы, и от режима зависит всё сразу: что задача делает на каждой итерации, что она сделает, получив команду, и в какой режим перейдёт после неё. Если режим хранить россыпью флагов, задача по-прежнему работает, но понять по её переменным, что она делает сейчас, становится всё труднее. Как описать поведение задачи так, чтобы на этот вопрос всегда был один ответ?

## Флаги режима и машина состояний

Возьмём светодиод, который бывает выключен, горит или мигает. Первое, что приходит в голову, — два флага: горит ли светодиод и мигает ли он. Обработчик задачи с ними выглядит так:

```c
bool led_on = false;
bool led_blinking = false;
uint64_t last_toggle_us = 0;

void led_task_handle(void)
{
    if (led_blinking) {
        // Мигание: переключать светодиод каждый полупериод
        if (period_elapsed(&last_toggle_us, 500000)) {
            gpio_put(PICO_DEFAULT_LED_PIN, !gpio_get(PICO_DEFAULT_LED_PIN));
        }
    } else {
        gpio_put(PICO_DEFAULT_LED_PIN, led_on);
    }
}
```

Два флага дают четыре сочетания значений, а режимов у светодиода три. Что значит «горит и мигает одновременно»? Обработчик на этот вопрос отвечает по-своему — при поднятом `led_blinking` значение `led_on` он не читает, — но после того как мигание выключат, светодиод загорится или погаснет в зависимости от того, что лежало в `led_on` до мигания. Код, который меняет режим, должен держать в голове все флаги сразу: команда «включить» обязана не только поднять `led_on`, но и опустить `led_blinking`, и если об этом забыть в одном месте, светодиод продолжит мигать. Следить за тем, чтобы бессмысленное сочетание не возникло, некому — компилятор о нём ничего не знает. С каждым новым флагом сочетаний вдвое больше, а осмысленных среди них всё меньше. Та же картина и у задачи расчёта π из прошлого раздела: флаги `pi_running` и `pi_ready` дают четыре сочетания, а осмысленных три — «не запускался», «считает» и «готово».

Посмотрим на это шире. Значения всех переменных, которые задача хранит между вызовами, в каждый момент и составляют её состояние, хотим мы того или нет. Вопрос только в том, описано ли оно явно. Если перечислить допустимые режимы и хранить номер текущего в одной переменной, недопустимых сочетаний не остаётся: переменная с тремя значениями означает ровно три режима. На Raspberry Pi эту работу за вас делала библиотека: вызов `LED.blink()` из gpiozero переводил светодиод в режим мигания, и где этот режим хранится, вас не касалось. В прошивке режим — часть вашего кода, и описывать его приходится самим. Такое описание поведения называют машиной состояний.

![[Машина состояний#^def]]

Поведение машины определяют две вещи: текущее состояние и входные данные. Одни входные данные приходят вызовом функции задачи вместе с его аргументами — так другая часть прошивки передаёт команду. Другие обработчик читает сам на каждом вызове — уровень на выводе, показание часов. Одна и та же команда в разных состояниях может приводить к разному, а одно и то же состояние при разных входных данных — по-разному продолжаться. Поэтому машину описывают перечнем состояний, переходов между ними и действий, которые выполняются в каждом состоянии и при каждом переходе. Чтобы такой перечень можно было записать в коде, нужен способ дать состояниям имена.

## Перечисляемый тип для имён состояний

Состояния можно было бы пронумеровать и хранить номер в обычной целой переменной, а номерам дать имена через `#define`. В **C** для этого есть средство удобнее — перечисляемый тип:

```c
typedef enum {
    LED_STATE_OFF,
    LED_STATE_ON,
    LED_STATE_BLINK,
} led_state_t;

led_state_t led_state = LED_STATE_OFF;
```

Ключевое слово `enum` объявляет набор именованных целых констант: компилятор нумерует их по порядку с нуля, так что `LED_STATE_OFF` равно 0, `LED_STATE_BLINK` — 2. Вместе с `typedef` получается тип `led_state_t`, и по нему видно, какие значения допустимы. Чем это лучше трёх `#define`, видно по сигнатуре функции: `void led_task_set_state(led_state_t state)` сама говорит, что принимает одно из состояний светодиода, а `void led_task_set_state(int state)` — только то, что принимает число.

Защиты от чужого значения перечисляемый тип при этом не даёт: в **C** переменной `led_state_t` можно присвоить и 7, и компилятор промолчит. Его польза — в именах, а не в проверке во время работы.

## Переходы и действие при входе в состояние

Состояния названы, теперь нужны переходы. У светодиода их источники внешние: команды «включить», «выключить», «мигать» переводят его в названное состояние из любого другого, а нажатие кнопки переводит по кругу — из «выключен» в «горит», из «горит» в «мигает» и обратно в «выключен».

![[Машина состояний светодиода.excalidraw|100%]]

Переход — это не только присваивание новой переменной `led_state`. При переходе в «горит» светодиод нужно включить, в «выключен» — выключить, а при переходе в «мигает» — сбросить отсчёт полупериода, иначе первое переключение придётся ждать столько, сколько осталось от давно забытой метки. Всё это делается один раз, в момент перехода, и называется действием при входе в состояние. Чтобы о нём нельзя было забыть, все переходы проводят через одну функцию смены состояния, и действия при входе пишут в ней:

```c
void led_task_set_state(led_state_t state)
{
    led_state = state;

    // Действие при входе: выполняется один раз, в момент перехода
    switch (led_state) {
    case LED_STATE_OFF:
        gpio_put(PICO_DEFAULT_LED_PIN, false);
        break;
    case LED_STATE_ON:
        gpio_put(PICO_DEFAULT_LED_PIN, true);
        break;
    case LED_STATE_BLINK:
        // Первое переключение — на ближайшей итерации
        last_toggle_us = 0;
        break;
    }
}
```

Команда «включить» теперь сводится к вызову `led_task_set_state(LED_STATE_ON)`, и тот же вызов делает функция инициализации задачи, задавая начальное состояние. В обработчике остаётся только то, что происходит внутри состояния, пока задача в нём находится:

```c
void led_task_handle(void)
{
    switch (led_state) {
    case LED_STATE_OFF:
    case LED_STATE_ON:
        // Светодиод установлен при входе в состояние, делать нечего
        break;
    case LED_STATE_BLINK:
        if (period_elapsed(&last_toggle_us, 500000)) {
            gpio_put(PICO_DEFAULT_LED_PIN, !gpio_get(PICO_DEFAULT_LED_PIN));
        }
        break;
    }
}
```

Сравните с обработчиком на флагах: там вывод записывался на каждой итерации, хотя менялся только при смене режима. Работает и так, но у действия при входе есть преимущества, которые к экономии тактов не сводятся. Светодиод загорается в момент команды, а не на ближайшем вызове обработчика. А главное, бывают действия, которые по своей природе можно выполнить только однажды: сброс метки полупериода, выполненный на каждой итерации, означал бы, что светодиод не мигнёт никогда. Обратите внимание и на то, что горит ли светодиод внутри «мигает», состоянием машины не считается. Машина называет то, что определяет поведение задачи, а метка времени и уровень на выводе — данные, с которыми работает одно из состояний.

## Переходы по времени на примере подавления дребезга

У светодиода время меняет происходящее внутри состояния, но не само состояние. Бывают машины, в которых время вызывает переход. Вспомним кнопку и дребезг контактов из занятия 1.2. Подавить дребезг значит принять новый уровень на выводе, только если он продержался некоторое время, скажем 20 мс. Проще всего, обнаружив новый уровень, подождать 20 мс и прочитать вывод ещё раз. Но ожидание, как мы выяснили в разделе [[т2.2.4 Блокирующий и неблокирующий код#^intro|Блокирующий и неблокирующий код]], держит суперцикл, и 20 мс на каждом нажатии — это 20 мс, в течение которых прибор не отвечает на команды и не мигает.

Без ожидания то же правило записывается машиной из четырёх состояний: «отпущена», «нажатие?», «нажата», «отпускание?». В состоянии «отпущена» обработчик проверяет уровень на выводе, и как только тот сменился, машина переходит в «нажатие?» и запоминает момент перехода. Из «нажатие?» два выхода. Если уровень вернулся раньше, чем прошло 20 мс, это был дребезг или помеха, и машина возвращается в «отпущена». Если уровень продержался 20 мс, нажатие состоялось, и машина переходит в «нажата». Отпускание устроено так же, через «отпускание?». Входные данные этой машины — уровень на выводе и показание часов, и обработчик на каждом вызове только читает их, сверяет с условиями переходов текущего состояния и сразу возвращается.

Действие при переходе в «нажата» — сообщить о нажатии — выполняется так же однократно, как включение светодиода при входе в «горит». Именно это даёт свойство, которого мы ждём от кнопки: одно нажатие — одно событие, сколько бы итераций кнопку ни держали нажатой.

## Отдельная машина состояний для каждой задачи

Кнопка и светодиод — две машины, и каждая живёт в своей задаче. Светодиод не знает, в каком состоянии кнопка, а кнопке всё равно, горит ли светодиод: нажатие для светодиода — такие же входные данные, как команды. Почему их не объединяют в одну, видно по счёту. Если описывать обе одной машиной, её состояниями станут все сочетания — три состояния светодиода на четыре состояния кнопки, двенадцать, — и каждую команду светодиода пришлось бы описывать для каждого состояния кнопки. Раздельно состояний семь, и каждое касается только своей задачи. Число состояний при объединении перемножается, а при разделении складывается, поэтому прибор с десятком задач описывают десятком небольших машин, а не одной огромной. Как при этом передать нажатие от одной задачи другой, не связывая их кодом друг с другом, разберём в разделе [[т2.3.7 Границы модулей#^intro|Границы модулей]].

Поведение задачи теперь описано: у неё есть состояния, переходы и действия при входе, а команды переводят её из состояния в состояние вызовом одной функции. Но держится это описание на договорённости. Переменная `led_state` лежит в файле задачи, и ничто не мешает коду из другого файла присвоить ей новое значение напрямую, в обход `led_task_set_state()`. Тогда действие при входе не выполнится: машина будет считать, что светодиод горит, а вывод останется в прежнем положении. Чем больше в прошивке задач и файлов, тем больше мест, откуда может прийти такое присваивание. Что в языке **C** позволяет задаче закрыть своё состояние от остальной прошивки, разберём в следующем разделе.
