## Задание

### Что должно получиться

- [ ] В вашем личном аккаунте хранилища репозиториев создан публичный репозиторий `es-student`
- [ ] Заданы имя и почта автора коммитов
- [ ] Репозиторий склонирован в папку `pico`, рядом с `pico-sdk`
- [ ] В корне репозитория лежит `.gitignore`, исключающий `build/`, `.vscode/` и `.DS_Store`
- [ ] Проект `112-blink` и файл `tools.log` выгружены в репозиторий

### Как проверить

1. **Своими глазами.** На странице репозитория видны четыре файла проекта: `main.c`, `CMakeLists.txt`, `memmap_rp2040.ld`, `pico_sdk_import.cmake`. Директории `build` там нет.
2. **Состав коммита.** Команда `git ls-files` перечисляет ровно то, что попало под контроль версий: шесть файлов и ни одного из `build`.
3. **Чистое дерево.** После отправки `git status` отвечает `nothing to commit, working tree clean` — значит на сервере лежит то же, что у вас на диске.

## Ход работы

>[!info] Если git подзабылся
>Порядок работы с репозиториями, ключами и коммитами разобран в курсе инженерной подготовки: https://github.com/ant-lab-ru/ant-get. Здесь даны только шаги, нужные для курса.

### 1. Создать репозиторий

Создайте в своём личном аккаунте публичный репозиторий с названием `es-student`. Он будет один на весь курс.

![[Создание репозитория es-student.png|700]]

Настройки, которые нужно выставить именно так:

- **Owner** — ваш личный аккаунт, **Repository name** — `es-student`;
- **Choose visibility** — `Public`, иначе проверки курса не увидят репозиторий;
- **Add README** — `On`;
- **Add .gitignore** и **Add license** — оставьте `No`.

Поле **Description** необязательное, но заполнить его стоит: это единственное, что видно рядом с названием в списке ваших репозиториев. Через год оно и напомнит, что такое `es-student`.

`.gitignore` мы создадим руками на шестом шаге: готовый шаблон принёс бы сотню строк про чужие среды разработки, а нам нужны две свои.

>[!info] Зачем нужен README
>Отметка создаёт в репозитории первый коммит. Без неё репозиторий остаётся пустым, а с пустым связано лишнее: у него нет ни одной ветки, и первая отправка требует особой команды. Репозиторий с README ведёт себя обычным образом с самого начала. В рабочей практике эту отметку почти всегда оставляют включённой — README и есть то место, где объясняют, что лежит в репозитории.

Каждый проект, то есть каждое решение нового задания, будет лежать в репозитории отдельной папкой с конкретным названием и со своими исходными файлами. Сегодня это `112-blink`, дальше рядом появятся остальные. Эти папки будут независимы друг от друга до тех пор, пока мы не научимся писать переиспользуемые библиотеки.

### 2. Представиться git

Каждый коммит подписывается именем и почтой автора. Пока они не заданы, `git commit` отказывается работать — это первое, обо что спотыкаются на чистой машине.

``` bash
git config --global user.name "Имя Фамилия"
git config --global user.email "почта@пример.ру"
```

Почта должна совпадать с той, что указана в вашем аккаунте хранилища репозиториев, — иначе коммиты не свяжутся с вашим профилем.

Проверьте, что значения записались. Соберите файл `git.log` в папке `pico`, рядом с `tools.log`. В macOS и Linux:

``` bash
{ git --version; git config --get user.name; git config --get user.email; } > git.log 2>&1
```

В Windows:

``` powershell
& { git --version; git config --get user.name; git config --get user.email } *> git.log
```

>[!success] Должно получиться так
>
>Три непустые строки — версия, имя, почта:
>
> ```
> git version 2.50.1
> Иван Петров
> ivan.petrov@example.com
> ```

>[!warning] Пустая строка означает, что значение не задано
>`git config --get` ничего не выводит, если настройки нет. Если во второй или третьей строке пусто — вернитесь к командам выше и задайте значение заново.

`git.log` нужен только вам и только сейчас, для этой проверки. В репозиторий его выгружать не нужно — пусть остаётся в папке `pico`.

### 6. Исключить из версионирования лишнее

Создайте в корне репозитория файл `.gitignore` и впишите в него три строки:

```
build/
.vscode/
.DS_Store
```

>[!warning] Имя файла — в точности `.gitignore`
>Это зарезервированное имя, с точкой в начале и без расширения. Файл с другим именем Git просто не заметит.

Первая строка исключает директории сборки, и здесь проходит граница, которую стоит удерживать до конца курса: **под контролем версий хранится только то, что написано человеком**. Файл `main.c`, описание сборки `CMakeLists.txt`, скрипт компоновщика — исходники. Всё, что появилось в `build`, — объектные файлы, `.elf`, `.bin`, `.uf2` — производные: они порождены инструментами из исходников и восстанавливаются в любой момент командами `cmake` и `make`. Поэтому их не хранят: пользы никакой, а история репозитория засоряется — при каждой сборке эти файлы меняются целиком.

При этом у каждого проекта своя папка `build` — внутри его собственной папки. Поэтому строка записана шаблоном, без пути. Она исключает папки `build` и их содержимое во всех проектах репозитория разом, включая те, которых ещё нет.

Вторая строка исключает `.vscode` — директорию с настройками редактора, которые касаются только вашего компьютера. Подробнее — [[Исключение файлов из версионирования#^def|Исключение файлов из версионирования]].

Третья строка нужна тем, кто работает в macOS. `.DS_Store` — служебный файл Finder: система заводит его в каждой папке, которую вы хотя бы раз открыли в окне, и хранит там положение значков и размер окна. К проекту он отношения не имеет, но лезет в репозиторий наравне с исходниками. Строка записана без пути и исключает такие файлы во всех папках сразу. В Windows и Linux она просто ничего не делает.

>[!info] Как избавиться от `.DS_Store` во всех репозиториях разом
>Мусор операционной системы касается вашего компьютера, а не проекта, поэтому его удобнее исключить один раз для всех репозиториев — своим личным списком исключений:
>
> ``` bash
> git config --global core.excludesfile ~/.gitignore_global
> echo ".DS_Store" >> ~/.gitignore_global
> ```
>
>После этого `.DS_Store` перестанет попадаться вам в любом проекте. В `.gitignore` курса строку всё равно оставляем: личный список есть только у вас, а репозиторий читают и другие.

### 7. Сделать коммит и отправить в репозиторий

Прежде чем коммитить, посмотрите, что именно уйдёт:

``` bash
git status
```

В списке должны быть шесть файлов — `.gitignore`, `tools.log` и четыре файла проекта. Директории `build` в нём нет: её отсекает `.gitignore`.

``` bash
git add .
git commit -m "Сделана п1.1.4"
git push
```

>[!success] Должно получиться так
>На странице репозитория:
>
> ```
> es-student
> ├── .gitignore
> ├── README.md
> ├── tools.log
> └── 112-blink
>     ├── main.c
>     ├── CMakeLists.txt
>     ├── memmap_rp2040.ld
>     └── pico_sdk_import.cmake
> ```
>
>Директории `build` в репозитории нет.

Обновите страницу репозитория — там появились ваши файлы:

![[Репозиторий es-student после отправки.png|700]]

Обратите внимание на счётчик коммитов: их два. Первый сделал GitHub, когда создавал `README.md`, второй — ваш. Рядом с каждым файлом стоит сообщение того коммита, которым файл добавлен, — так по странице видно, что и когда появилось.

Репозиторий курса заведён, и первая работа в нём. Дальше — задание [[п1.1.5 Настройка автоматической проверки#^intro|п1.1.5 Настройка автоматической проверки]]: подключим к репозиторию проверки курса и убедимся, что прошивка собирается не только у вас на столе.
