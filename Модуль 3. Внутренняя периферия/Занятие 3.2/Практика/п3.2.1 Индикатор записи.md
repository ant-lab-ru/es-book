### Как проверить

1. **Светодиод мигает, пока прибор считает.** В терминале запустите мигание и сразу `pi_start 3000000`. Расчёт идёт несколько секунд, а светодиод всё это время мигает ровно и прибор отвечает на `uptime`.
2. **Лог прогона лежит в проекте.** Скрипт задания записывает обмен в `device-3-2-1.log`.
3. **Автоматическая проверка курса принимает задание.** В коде она ищет будильник `add_repeating_timer_ms()` и его снятие в `platform.c`, проверяет, что обработчик не печатает и не ждёт, а переменные, общие с ним, объявлены с квалификатором `volatile`. Логика по-прежнему не подключает SDK. В логе она сравнивает число переключений с периодом и временем между командами, с точностью 15 %, и ищет ответы на команды во время мигания.

### 2. Мигать по будильнику в platform

Будильник таймера — железо, поэтому мигание живёт в `platform`. Добавьте в `platform.h` две функции. Тип `uint32_t` в этом файле появляется впервые, поэтому рядом с `<stdbool.h>` подключите `<stdint.h>`.

```c
#include <stdint.h>

// индикатор: светодиод мигает по будильнику, независимо от суперцикла;
// false — период меньше 10 мс или больше 60 000 мс
bool platform_blink_start(uint32_t period_ms);

// гасит светодиод и возвращает число переключений с запуска
uint32_t platform_blink_stop(void);
```

В `platform.c` будильник ставится функцией SDK `add_repeating_timer_ms()`. Ей передают период, функцию-обработчик и переменную типа `repeating_timer_t`, в которой SDK хранит состояние будильника. Переменная должна жить, пока работает будильник, поэтому она объявлена вне функций.

```c
static repeating_timer_t blink_timer;
static bool blink_running;
static volatile bool blink_on;
static volatile uint32_t blink_toggles;

// обработчик будильника индикатора
static bool on_blink(repeating_timer_t *timer)
{
    blink_on = !blink_on;
    gpio_put(LED_PIN, blink_on);
    blink_toggles++;

    // true — вызвать снова через тот же период
    return true;
}

bool platform_blink_start(uint32_t period_ms)
{
    if (period_ms < 10 || period_ms > 60000)
    {
        return false;
    }

    platform_blink_stop();
    blink_toggles = 0;

    // минус перед периодом — отсчитывать от начала прошлого вызова
    blink_running = add_repeating_timer_ms(-(int32_t)period_ms, on_blink, NULL, &blink_timer);
    return blink_running;
}

uint32_t platform_blink_stop(void)
{
    if (blink_running)
    {
        cancel_repeating_timer(&blink_timer);
        blink_running = false;
    }

    blink_on = false;
    gpio_put(LED_PIN, 0);
    return blink_toggles;
}
```

Функцию `on_blink()` вызывает обработчик прерывания будильника, посреди чужой итерации суперцикла. Поэтому в нём три строки и ни одного вывода в порт. Счётчик `blink_toggles` меняет обработчик, а читает `platform_blink_stop()`, и без квалификатора `volatile` компилятор вправе держать его копию в регистре ([[т3.2.5 Обработчик прерывания#Общие данные и квалификатор `volatile`|т3.2.5]]). Запись и чтение 32-битного слова атомарны, поэтому критическая секция здесь не нужна. Знак минус перед периодом ставит вызовы на ровную сетку, как отсчёт от прошлой метки в задачах шаблона.

Функцию `on_blink()` вы передаёте в SDK по адресу. Это тот же приём, что таблица команд из [[п2.1.2 Таблица команд#^intro|п2.1.2]], только вызывает функцию не ваша программа, а обработчик прерывания таймера.

### 3. Добавить команды

Команды разбирает `api-callbacks.c`. Светодиод теперь может включать и задача светодиода, и будильник. Чтобы они не спорили, после запуска мигания команда переводит задачу светодиода в состояние «выключен», в котором та светодиод не трогает.

>[!success] Должно получиться так
> ```c
> // cmd_timer_blink_start(): аргумент не один или не число — error: usage
> // platform не принял период — error: period_ms must be 10..60000
> // задачу светодиода — в состояние «выключен»
> // ответ timer_blink: started, period <период> ms
>
> // cmd_timer_blink_stop(): ответ timer_blink: stopped, <число> toggles
>
> // в таблице команд
> { "timer_blink_start", "blink led by timer: timer_blink_start <period_ms>", cmd_timer_blink_start },
> { "timer_blink_stop", "stop timer blink, number of toggles", cmd_timer_blink_stop },
> ```

| Что нужно написать | Где это разбиралось |
| --- | --- |
| обязательный числовой аргумент | `led_period <period_ms>`, [[п2.3.2 Задача светодиода#^intro\|п2.3.2]] |
| проверку, которую делает сам модуль | `led_task_set_period_ms()`, [[п2.3.2 Задача светодиода#^intro\|п2.3.2]] |
| строку в таблице команд | [[п2.3.1 Протокол и API#^intro\|п2.3.1]] |

### 4. Проверить в терминале

Соберите проект, запишите прошивку и запустите мигание вместе с долгим расчётом.

>[!success] Должно получиться так
> ```
> timer_blink_start 250
> timer_blink: started, period 250 ms
> pi_start 3000000
> pi: started, 3000000 terms
> uptime
> uptime: 6163 ms
> pi
> pi: running
> timer_blink_stop
> timer_blink: stopped, 24 toggles
> ```

Светодиод мигает четыре раза в секунду, пока идёт расчёт, и `uptime` отвечает сразу. Между `timer_blink_start` и `timer_blink_stop` здесь прошло 6,2 с, при периоде 250 мс это 24 переключения. Будильнику всё равно, чем занят суперцикл. Расчёт π и без того идёт порциями, но будильник продолжал бы мигать, даже если бы суперцикл завис. Эту опасность вы разберёте в задании [[п3.2.6 Сторожевой таймер#^intro|п3.2.6]].
