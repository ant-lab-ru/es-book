**Результат** — к репозиторию курса подключены автоматические проверки, они проходят успешно, и прошивка собирается из свежей копии репозитория.
^intro

## Задание

### Что должно получиться

- [ ] В корне репозитория есть директория `.github/workflows` с пятью файлами проверок курса
- [ ] Проверки запустились и отмечены зелёным
- [ ] Прошивка собрана из заново склонированной копии репозитория, светодиод мигает

### Как проверить

1. **Своими глазами.** На вкладке `Actions` страницы репозитория видны запуски проверок, все со значком успеха.
2. **Отчёт проверки.** Внутри каждого запуска — список пунктов на русском языке; все отмечены галочкой. Значок ⚠️ означает замечание: задание засчитано, но что-то стоит поправить.
3. **Сборка из свежей копии.** Удалите локальную папку `es-student`, склонируйте репозиторий заново, соберите прошивку из полученных файлов и запишите её на плату — светодиод мигает.

## Ход работы

>[!info] Что происходит при проверке
>Проверки курса находятся не у вас, а в открытом репозитории `ant-lab-ru/es-test`. В свой репозиторий вы кладёте только несколько коротких файлов-вызовов: они говорят GitHub, когда запускать проверку и какую именно. Сама проверка берёт ваши исходные файлы, собирает из них прошивку на виртуальной машине и сверяет результат с требованиями задания.

### 1. Создать файлы проверок

В корне репозитория создайте папку `.github`, а в ней — папку `workflows`:

``` bash
cd ~/Repositories/pico/es-student
mkdir -p .github/workflows
```

>[!info] Почему имя папки начинается с точки
>`.github` — зарезервированное имя: описания автоматических задач GitHub ищет только в нём. Имя с точки в начале означает скрытый файл, и в файловом менеджере такая папка по умолчанию не видна. Чтобы увидеть её, включите показ скрытых файлов: `Cmd+Shift+.` в macOS, «Скрытые элементы» на вкладке «Вид» в Windows. В боковой панели VS Code такие папки видны всегда.

Создайте в `workflows` пять файлов — по одному на каждое задание занятия. Тексты приведены целиком: копируйте как есть, править в них ничего не нужно.

`check-1-1-1.yml`:

``` yaml
name: 1.1.1 Установка инструментов

on:
  push:
  workflow_dispatch:

jobs:
  check:
    uses: ant-lab-ru/es-test/.github/workflows/check-1-1-1.yml@master
    secrets:
      ES_ACCOUNT_SECRET: ${{ secrets.ES_ACCOUNT_SECRET }}
```

Разберём первый файл по строкам, остальные устроены так же:

- `name` — как запуск будет называться на вкладке `Actions`;
- `on: push` — запускать при каждой отправке в репозиторий, `workflow_dispatch` — разрешить запуск вручную кнопкой;
- `jobs` — перечень задач, которые GitHub выполняет по этому файлу; здесь она одна;
- `check` — имя задачи, его придумывает автор файла. Оно появляется на вкладке `Actions` слева от названия проверки: `check / Установка инструментов`;
- `uses` — где взять саму проверку: репозиторий курса `ant-lab-ru/es-test`, файл нужной проверки, ветка `master`. Номер в этой строке и определяет, какая проверка запустится;
- `secrets` — что передать проверке из настроек вашего репозитория;
- `ES_ACCOUNT_SECRET` — секрет подписи результатов: слева от двоеточия имя, под которым его ждёт проверка, справа — имя, под которым он лежит у вас. Пока секрета нет, строки можно оставить как есть: проверка отработает, а отправку результата пропустит.

`check-1-1-2.yml`:

``` yaml
name: 1.1.2 Первый проект

on:
  push:
  workflow_dispatch:

jobs:
  check:
    uses: ant-lab-ru/es-test/.github/workflows/check-1-1-2.yml@master
    secrets:
      ES_ACCOUNT_SECRET: ${{ secrets.ES_ACCOUNT_SECRET }}
```

`check-1-1-3.yml`:

``` yaml
name: 1.1.3 Запуск прошивки

on:
  push:
  workflow_dispatch:

jobs:
  check:
    uses: ant-lab-ru/es-test/.github/workflows/check-1-1-3.yml@master
    secrets:
      ES_ACCOUNT_SECRET: ${{ secrets.ES_ACCOUNT_SECRET }}
```

`check-1-1-4.yml`:

``` yaml
name: 1.1.4 Создание репозитория курса

on:
  push:
  workflow_dispatch:

jobs:
  check:
    uses: ant-lab-ru/es-test/.github/workflows/check-1-1-4.yml@master
    secrets:
      ES_ACCOUNT_SECRET: ${{ secrets.ES_ACCOUNT_SECRET }}
```

`check-1-1-5.yml`:

``` yaml
name: 1.1.5 Настройка автоматической проверки

on:
  push:
  workflow_dispatch:

jobs:
  check:
    uses: ant-lab-ru/es-test/.github/workflows/check-1-1-5.yml@master
    secrets:
      ES_ACCOUNT_SECRET: ${{ secrets.ES_ACCOUNT_SECRET }}
```

>[!warning] Отступы в YAML значат ровно столько же, сколько слова
>Формат `.yml` различает уровни вложенности по отступу. Сдвинутая строка меняет смысл файла или делает его нечитаемым, а GitHub сообщит об этом невнятно. Отступы — только пробелы, табуляция запрещена. Поэтому копируйте блок целиком, а не набирайте по памяти.

Проверьте себя: эта команда покажет строку `uses` из всех пяти файлов разом.

``` bash
grep -h uses .github/workflows/*.yml
```

>[!success] Должно получиться так
>
>Пять разных номеров, по возрастанию:
>
> ```
> uses: ant-lab-ru/es-test/.github/workflows/check-1-1-1.yml@master
> uses: ant-lab-ru/es-test/.github/workflows/check-1-1-2.yml@master
> uses: ant-lab-ru/es-test/.github/workflows/check-1-1-3.yml@master
> uses: ant-lab-ru/es-test/.github/workflows/check-1-1-4.yml@master
> uses: ant-lab-ru/es-test/.github/workflows/check-1-1-5.yml@master
> ```
>
>Если номер где-то повторился — этот файл запустит чужую проверку. Поправьте строку `uses`, чтобы номер совпадал с именем файла.

>[!success] Должно получиться так
>
> ```
> es-student
> └── .github
>     └── workflows
>         ├── check-1-1-1.yml
>         ├── check-1-1-2.yml
>         ├── check-1-1-3.yml
>         ├── check-1-1-4.yml
>         └── check-1-1-5.yml
> ```

Самих проверок в вашем репозитории нет — только вызовы. Так сделано намеренно: проверка одна на всех, живёт в репозитории курса и правится в одном месте. Если бы каждый носил её копию, у трёх десятков человек оказалось бы три десятка разных проверок.

### 2. Завести секрет

>[!info] Подпись результатов
>Чтобы получить оценку или зачёт по программе «Встраиваемые системы», нужно отправлять результаты проверки заданий в базу данных ant-lab. В этом случае вы с преподавателями сможете отслеживать прогресс в личном кабинете.

На странице репозитория: `Settings` → `Secrets and variables` → `Actions`. Раздел `Repository secrets` поначалу пуст.

![[Страница секретов репозитория.png]]

Нажмите `New repository secret`. Имя — `ES_ACCOUNT_SECRET`, значение — строка из вашего личного кабинета на [es.ant-lab.ru](https://es.ant-lab.ru).

![[Форма нового секрета.png]]

После `Add secret` значение больше не показывается никогда — ни вам, ни кому-либо ещё. Забыли, что вписали, — не вспоминайте, а заведите заново: кабинет выдаёт вашу строку столько раз, сколько нужно.

### 3. Отправить файлы в репозиторий

Проверки не запускаются с вашего компьютера — они работают на серверах GitHub. Поэтому файлы нужно отправить:

``` bash
git add .
git commit -m "Сделана п1.1.5"
git push
```

### 4. Посмотреть результат

Откройте страницу репозитория и перейдите на вкладку **Actions**. Там появятся запуски проверок — по одному на каждый созданный файл. Первый запуск начнётся сразу после отправки.

![[Вкладка Actions после отправки.png|700]]

Слева перечислены все пять проверок занятия, справа — история запусков. Каждый запуск подписан сообщением вашего коммита, а под ним — название проверки и время работы. Жёлтый кружок означает «идёт», зелёная галочка — «прошла», красный крест — «не прошла».

Щёлкните по названию запуска — откроется отчёт со списком пунктов на русском языке: что проверялось и что получилось. Красный пункт называет, чего не хватает.

![[Отчёт проверки 1.1.1.png|700]]

Это отчёт проверки 1.1.1: она прочитала `tools.log` из репозитория и нашла в нём десять требуемых вещей.

Отчёт 1.1.3 идёт дольше остальных — больше минуты против нескольких секунд. Причина в том, что эта проверка не просто читает файлы, а собирает из них прошивку:

![[Отчёт проверки 1.1.3.png|700]]

Эта проверка выполняется на виртуальной машине GitHub, которая специально создаётся для того, чтобы выполнить проверку. Ни компилятора для микроконтроллера, ни SDK на ней нет: проверка сама ставит их, клонирует ваш репозиторий и пытается собрать двоичный файл из исходных файлов вашего проекта. После проведения проверок виртуальная машина останавливается и уничтожается вместе со всем, что на ней осталось.

Папку `build` на вашем компьютере она не видит и не использует. Поэтому именно автоматическая проверка отвечает на вопрос, который вручную проверить трудно: соберётся ли проект не только на вашем компьютере.

Последняя строка отчёта обозначает границу возможностей: мигание светодиода проверяется на плате, проверить это можете только вы. Как говорится, руками и глазами.

>[!info] Проверка не видит то, что у вас на диске
>Она читает репозиторий, а не вашу папку. Если файл не отправлен, для проверки его не существует — даже когда на вашем компьютере всё на месте. Это та же граница, которую вы проводили в предыдущем задании, только теперь она проявляется наглядно.

>[!bug] Проверки не запустились вовсе
>Вкладка `Actions` пуста — значит файлы попали не туда. Проверьте, что путь в репозитории именно `.github/workflows/`, а не `github/workflows/` или `.github/`. Точка в начале обязательна.

### 4. Собрать прошивку из свежей копии репозитория

>[!warning] Выполняйте этот шаг только после зелёных проверок
>Приступайте к нему, когда все тесты автоматической проверки задания пройдены успешно.

1. Удалите локальную папку `es-student` со своего компьютера.
2. Склонируйте репозиторий заново, в ту же папку `pico`.
3. Соберите прошивку из полученных файлов и запишите её на плату.

Светодиод снова мигает — значит в репозитории лежит всё, что нужно для сборки, и ничего лишнего.

Проверять это стоит не ради галочки. Репозиторий должен собираться с нуля у любого человека на любой машине: только так работа переживает смену компьютера, передаётся коллеге и попадает в автоматическую сборку. Локальная папка, в которой «всё работает», такой гарантии не даёт — в ней могут лежать файлы, которые вы забыли выгрузить.
