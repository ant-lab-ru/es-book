У микроконтроллера RP2040 два ядра Arm Cortex-M0+. После старта программа входит в `main()` на ядре 0. Комплект разработки Pico SDK позволяет передать ядру 1 функцию и продолжить работу на ядре 0.
^intro

## Запустить мигание

**Задача.** Пусть ядро 1 мигает штатным светодиодом Pico, а ядро 0 считает время и отвечает за вывод на компьютер. Соберите отдельный опыт с библиотеками `pico_stdlib` и `pico_multicore`. Для вывода включите `pico_enable_stdio_usb(имя_цели 1)` в CMake.

```c
#include <stdio.h>
#include "pico/multicore.h"
#include "pico/stdlib.h"

static void blink(void)
{
    gpio_init(PICO_DEFAULT_LED_PIN);
    gpio_set_dir(PICO_DEFAULT_LED_PIN, GPIO_OUT);
    while (true)
    {
        gpio_put(PICO_DEFAULT_LED_PIN, 1);
        sleep_ms(500);
        gpio_put(PICO_DEFAULT_LED_PIN, 0);
        sleep_ms(500);
    }
}

int main(void)
{
    stdio_init_all();
    multicore_launch_core1(blink);
    for (unsigned seconds = 0; ; ++seconds)
    {
        printf("%u s\n", seconds);
        sleep_ms(1000);
    }
}
```

**Хорошая практика.** Для знакомства достаточно выделить второму ядру одну простую задачу. В [[п4.1.3 Ведомое устройство на втором ядре#^intro|п4.1.3]] мигание без ожидания позволяет позже добавить обработку запросов в тот же суперцикл.

## Передать команду между ядрами

**Задача.** Ядро 0 решает, гореть ли светодиоду, а его выводом общего назначения GPIO управляет ядро 1.

**Опасность.** Когда оба ядра записывают в одну переменную или в один регистр периферии, результат зависит от порядка операций. Даже простое увеличение общего счётчика состоит из чтения и записи. Квалификатор `volatile` этих действий не объединяет.

**Хорошая практика.** Выделите каждому ресурсу владельца, а команды передавайте через очередь SDK. Инициализируйте общую `queue_t commands` до запуска ядра 1. Для значений `bool` вызовите `queue_init(&commands, sizeof(bool), 4)` из `pico/util/queue.h`. На ядре 0 проверяйте результат `queue_try_add(&commands, &on)`. Если очередь полная, команда не поставлена. На ядре 1 применяйте только полученное значение.

```c
bool on;
if (queue_try_remove(&commands, &on))
{
    gpio_put(PICO_DEFAULT_LED_PIN, on);
}
```

## Обработать прерывание

**Задача.** Ядро 1 должно заметить нажатие кнопки, продолжая работу в своём цикле.

**Опасность.** У каждого ядра свой контроллер прерываний. Выключение прерываний на ядре 0 не остановит обработчик на ядре 1. Если один общий источник обслуживают сразу два обработчика, один может забрать байт, который ожидает другой.

**Хорошая практика.** Назначьте источнику одного владельца. В примере ядро 1 включает прерывание от кнопки между GP15 и землёй. Вывод подтянут к единице. При нажатии обработчик ставит флаг, а суперцикл вызывает `atomic_exchange()`, чтобы забрать событие и сбросить флаг одним действием. Несколько нажатий между проверками объединяются в одно событие.

```c
#include <stdatomic.h>

static atomic_bool pressed;

static void button_irq(uint gpio, uint32_t events)
{
    if (gpio == 15 && (events & GPIO_IRQ_EDGE_FALL))
    {
        atomic_store(&pressed, true);
    }
}
```

На ядре 1 настройте GP15 как вход с `gpio_pull_up(15)`. Вызовите `gpio_set_irq_enabled_with_callback(15, GPIO_IRQ_EDGE_FALL, true, button_irq)`. В суперцикле проверяйте `atomic_exchange(&pressed, false)`.

В [[п4.1.4 Доступ к ведомому устройству по I²C#^intro|п4.1.4]] вместо кнопки источником событий служит I²C1. Вызов `i2c_slave_init()` регистрирует обработчик на ядре 1. Обработчик забирает байт из очереди интерфейса и возвращает управление.

## Передать буфер с помощью DMA

**Задача.** Скопировать готовый блок отсчётов в другой буфер. Контроллер прямого доступа к памяти DMA выполняет копирование без поэлементной работы ядра.

**Опасность.** Ядро может прочитать недописанный буфер. Кроме того, два ядра могут попытаться настроить один канал DMA.

**Хорошая практика.** Владелец занимает канал через `dma_claim_unused_channel(true)` из `hardware/dma.h`, запускает перенос и ждёт завершения. Второе ядро получает буфер после завершения, например через очередь. Если вместо ожидания нужен IRQ, назначьте обработку завершения одному ядру и подтверждайте событие для своего канала.

Следующий фрагмент копирует четыре 32-битных слова. Для сборки добавьте `hardware_dma`. До завершения передачи не меняйте `src` и не читайте `dst`.

```c
static uint32_t src[] = {10, 20, 30, 40};
static uint32_t dst[4];

int ch = dma_claim_unused_channel(true);
dma_channel_config cfg = dma_channel_get_default_config(ch);
channel_config_set_transfer_data_size(&cfg, DMA_SIZE_32);
channel_config_set_read_increment(&cfg, true);
channel_config_set_write_increment(&cfg, true);
dma_channel_configure(ch, &cfg, dst, src, 4, true);
dma_channel_wait_for_finish_blocking(ch);
dma_channel_unclaim(ch);
```

В проекте 4.1 DMA не нужен. Ядро 0 владеет связью с компьютером и ведущими контроллерами. Ядро 1 владеет ведомыми контроллерами и светодиодом. Два устройства обмениваются данными по проводам. Это учебный пример того, как распределение ресурсов упрощает работу кода.

Подробнее о [многоядерном запуске и очередях в Pico SDK](https://www.raspberrypi.com/documentation/pico-sdk/high_level.html) и об [API прерываний и DMA](https://www.raspberrypi.com/documentation/pico-sdk/hardware.html).
