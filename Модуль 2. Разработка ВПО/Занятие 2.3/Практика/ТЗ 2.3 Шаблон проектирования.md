**Техническое задание, часть 2.** Шаблон проектирования прибора `231-firmware-template`: из каких частей состоит прошивка, что делает каждая часть и по каким правилам они связаны. Что прибор делает, описывает [[ТЗ 2.3 Прибор|часть 1, «Прибор»]].
^intro

## Зачем прибору шаблон

Прибор из части 1 можно написать одним файлом `main.c`. Он будет работать. Но в модулях 3–5 к нему добавятся АЦП, шины, датчики и дисплей. С каждой новой частью придётся искать, куда вписать её строки между чужими. Шаблон отвечает на этот вопрос заранее. Новая периферия подключается к нему по одной схеме и не затрагивает того, что уже работает.

Шаблон опирается на теорию занятия. Как работа распределена во времени, разбирают [[т2.3.3 Программная задача#^intro|т2.3.3]] и [[т2.3.4 Машина состояний#^intro|т2.3.4]]. Как код распределён по модулям, разбирают [[т2.3.5 Программный модуль на C#^intro|т2.3.5]]–[[т2.3.8 Протокол и API прибора#^intro|т2.3.8]]. Здесь те же решения записаны на примере этого прибора, с его именами папок, библиотек и функций.

Шаблон удался, если:

- новая команда — правка только в `api-callbacks.c`;
- новая задача — новый модуль в `logic/`, две строки в `main.c` и одна в `CMakeLists.txt`;
- новый проект — копия папки шаблона и новое имя в `CMakeLists.txt` и `firmware.h`;
- библиотеки логики собираются без SDK.

## Устройство кода

Этот раздел описывает, из каких частей состоит прошивка, что каждая из них делает и по каким правилам они связаны. Имена папок, библиотек, модулей и функций, указанные здесь, обязательны: на них опираются задания модулей 3–5. Внутреннее устройство модулей и функции, которых здесь нет, — на усмотрение студента.

### 1. Раскладка

```
libs/                         в корне репозитория, общие для проектов курса
├── CMakeLists.txt
├── stdio-text-protocol/
├── systime/
├── profiling/
├── device/
└── logging/
231-firmware-template/
├── CMakeLists.txt
├── firmware.h
├── main.c
├── platform/
│   ├── platform.h
│   └── platform.c
└── logic/
    ├── api/
    │   ├── api.h
    │   ├── api.c
    │   ├── api-commands.h
    │   └── api-callbacks.c
    ├── led-task/
    ├── button-task/
    └── pi-task/
```

Каждая библиотека в `libs/` устроена одинаково:

```
<имя>/
├── CMakeLists.txt
├── include/<имя>/<заголовок>.h
└── src/<реализация>.c
```

### 2. Библиотеки

| Библиотека | Назначение | Интерфейс | Зависимость от SDK |
| --- | --- | --- | --- |
| `stdio-text-protocol` | принимает кадр команды по протоколу приложения А части 1 и делит его на имя и аргументы; команд прибора не знает | тип `command_t` (поля `name`, `argc`, `argv`, `truncated`);<br>`stdio_text_protocol_init()`;<br>`stdio_text_protocol_handle()` — возвращает принятую команду или `NULL` | `PRIVATE` |
| `systime` | время с момента сброса и проверка периода для задач | `systime_us()`, `systime_ms()`;<br>`systime_period_elapsed(&last_us, period_us)` — по Ф3.4 части 1 | `PRIVATE` |
| `profiling` | секундомеры для участков кода, адресуемые номером | `profiling_stopwatch_init(номер, имя)`;<br>`profiling_start(номер)`, `profiling_stop(номер)`;<br>`profiling_get(номер, &результат)`, `profiling_reset()`;<br>макрос `PROFILING_ENABLED` | `PRIVATE` |
| `device` | сведения о плате и кристалле; сам их не печатает | тип `device_info_t`;<br>`device_get_info(&сведения)` | `PRIVATE` |
| `logging` | журнал прошивки по разделу 7 приложения А части 1 | макросы `LOG_ERR`, `LOG_INF`, `LOG_DBG`;<br>уровень `LOG_LEVEL` | нет |

`libs/CMakeLists.txt` добавляет к сборке каждую библиотеку строкой `add_subdirectory()`. Проект подключает `libs/` строкой `add_subdirectory(../libs ${CMAKE_BINARY_DIR}/libs)`.

### 3. Модули проекта

| Модуль | Назначение | Интерфейс | Зависимость от SDK |
| --- | --- | --- | --- |
| `firmware.h` | имя и версия прошивки, имя проекта, адрес репозитория | константы | нет |
| `platform` | железо этого прибора: номера выводов, подключение кнопки, запуск стандартного ввода-вывода, доступ к выводам в одну-две строки; логики не содержит | `platform_init()`;<br>`platform_led_set(включить)`;<br>`platform_button_read()` — нажата ли кнопка сейчас, без подавления дребезга | `PRIVATE`, библиотека `platform` |
| `logic/api` | механизм команд в `api.c`: поиск по имени, `help`, ответы на ошибки кадра; обработчики и таблица команд прибора в `api-callbacks.c`; тип записи таблицы и объявление таблицы во внутреннем заголовке `api-commands.h` | `api_handle(команда)` | нет |
| `logic/led-task` | поведение светодиода по Ф3 | на усмотрение студента | нет |
| `logic/button-task` | подавление дребезга кнопки по Ф4 части 1; уровень читает через `platform`; о нажатии сообщает функцией, переданной при запуске | тип `button_task_callback_t`;<br>`button_task_init(функция)`;<br>`button_task_handle()` — на каждой итерации суперцикла;<br>`button_task_is_pressed()`, `button_task_get_press_count()` | нет |
| `logic/pi-task` | расчёт π по порциям по Ф5 | на усмотрение студента | нет |
| `main.c` | запуск модулей, связи между ними, секундомеры, суперцикл | — | нет |

Модули `logic/` собираются одной библиотекой `logic`. Библиотеку `stdio_text_protocol` она подключает как `PUBLIC`: `api.h` подключает её заголовок ради типа `command_t`. Остальные библиотеки — как `PRIVATE`.

### 4. Правила

- **П1.** Формат команд знает только `stdio-text-protocol`, смысл команд — только `api`. Протокол и `api` друг друга не вызывают; команду из протокола в `api` передаёт `main.c`.
- **П2.** Новая команда добавляется правкой только `api-callbacks.c`. В `api.c` нет имён команд прибора, кроме `help`.
- **П3.** Модули возвращают данные и не печатают. Ответы на команды печатают только `api.c` и `api-callbacks.c`, журнал — только `logging`.
- **П4.** Вне библиотек SDK подключает только `platform`. Код в `logic/` и библиотека `logging` SDK не подключают, и `#include` заголовка SDK в них останавливает сборку.
- **П5.** Модуль, работающий с железом, подключает SDK как `PRIVATE`, и его заголовок не включает заголовков SDK.
- **П6.** Задачи не подключают заголовки друг друга. О событии задача сообщает функцией, переданной ей при запуске; связи задаёт `main.c`.
- **П7.** `main.c` только запускает модули, связывает их, заводит секундомеры и вызывает обработчики задач в суперцикле. Ни один модуль не подключает `main.c`. `main.c` не подключает заголовков SDK.
- **П8.** Зависимости по `#include` не образуют циклов.
- **П9.** Функции и переменные вне функций, которых нет в заголовке модуля, определены со `static`. Изменяемые переменные через `extern` не открываются; константная таблица — через `extern const`.
- **П10.** Заголовок защищён `#pragma once`, подключает всё, что нужно ему самому, и не подключает того, что нужно только реализации. Файл `.c` подключает свой заголовок первым.
- **П11.** Заголовок подключается с именем библиотеки или модуля: `#include "logging/log.h"`, `#include "led-task/led-task.h"`.
- **П12.** Модуль попадает в `libs/`, если пойдёт без правок в другой прибор курса, и в `logic/`, если принадлежит этому прибору.
- **П13.** Знание о железе — в `platform` и библиотеках, знание о задаче прибора — в `logic/`. Подавление дребезга и истолкование жестов (долгое или двойное нажатие) — в задачах `logic/`; какой уровень даёт нажатая кнопка, задача кнопки узнаёт от `platform`.

>[!quote] Из практики
>Состояние модуля в переменных файла со `static` существует в прошивке в одном экземпляре. Для журнала это верно: второй журнал прибору не нужен. Секундомеров нужно несколько, поэтому `profiling` держит их массивом, а функции получают номер секундомера — так же, как `gpio_put()` получает номер вывода, а не структуру с его состоянием. Проектируя модуль, спросите себя, может ли прибору понадобиться два таких модуля. Журнал — нет, секундомеры — да, два одинаковых датчика на одной шине — тоже да, и с ними мы встретимся в модуле 4.
